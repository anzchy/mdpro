# Design: `verify-feature` — Agent-fronted, reusable E2E verification loop for Tauri apps

Generated by /office-hours on 2026-06-10
Branch: master
Repo: anzchy/mdpro
Status: APPROVED
Mode: Builder

## Problem Statement

Every verification loop in mdpro today is **deterministic and human-gated at the
last mile**. `pnpm build` (tsc), `pnpm test:run` (Vitest, ~80 files), and
`cargo test` catch logic and type errors. The `tdd-guardian` workflow builds
*unit* tests. But two agents in the fleet (`test-runner`, `manual-test-author`)
literally instruct: *"ask the user to launch the app, then use Tauri MCP for
E2E."* The loop is **not closed** — a human still has to boot the app, click
through Milkdown/CodeMirror flows, watch the console, and eyeball layout.

The reference talk (Anthropic, "verification loops") names the missing piece:
encode the manual verification ritual as something the agent runs **on its own**
after a change — drive the real UI, capture visual evidence, watch the console,
check regressions — so the first response lands closer to intent and you stop
babysitting. The goal here is to build that as a **reusable, open-source unit**:
a "verify-feature for Tauri apps" others can drop in, with mdpro as the reference
implementation.

## What Makes This Cool

The "whoa" is the reference-doc moment: Claude adds an unrelated feature, notices
it touched the UI, runs the verification pass **unprompted-by-a-human-clicking**,
and reports back *"the feature works — but there's a layout shift on this page"*
that nobody asked it to look for, because checking that is part of the encoded
ritual. Coverage grows as you encode more of your workflow. The lateral cool
factor: the verdict comes from an **isolated agent** with fresh context that
didn't write the code, so it carries none of the implementer's "I just wrote
this, it works" optimism.

## Constraints

- **macOS-first (Apple Silicon).** This is the hard one: the official Tauri E2E
  path (`tauri-driver` + WebDriver) does **not support macOS** — WKWebView has no
  WebDriver implementation. The chosen harness **sidesteps this entirely**: it does
  NOT drive the shipped WKWebView app. It runs the *same React/Vite bundle* in
  Playwright's **Chromium** against `pnpm dev`, with the Tauri IPC layer faked. So
  the WKWebView WebDriver gap simply doesn't apply — at the cost that the rendering
  engine under test is **not the shipped one** (a fidelity caveat folded into P3).
- **Local files only**, no cloud. Verification must run fully local / CI-able.
- **Reusable as open-source** → app-specific verification steps must be *data*
  (a manifest), not hardcoded into a prompt.
- **Must layer above, not replace,** the existing deterministic gates and the
  existing agent fleet (`feature-workflow.md`, `ship.md`).
- Files under ~300 lines; existing conventions in `.claude/rules/`.

## Premises

- **P1 (revised) — Agent-fronted, not skill-alone.** The *invoker/judge* is an
  agent (fresh context → isolated, honest PASS/FAIL verdict, matching the
  reference doc's "second pair of eyes that didn't write the code"). The
  *reusable procedure* is a skill the agent invokes. This matches mdpro's own
  fleet convention that agents orchestrate while skills encode reusable
  procedure. (Note: `test-runner.md` is precedent for the *problem*, not the
  solution — it currently delegates E2E back to a human: *"ask the user to launch
  the app."* This design replaces that human step.)
- **P2 — Layers above deterministic gates, does not replace them.** Vitest /
  `cargo test` / tdd-guardian catch logic. This catches what unit tests
  structurally can't: real Milkdown/CodeMirror DOM rendering, console errors,
  visual layout, cross-mode (WYSIWYG↔source) flows.
- **P3 (accepted boundary) — fidelity ceiling, stated honestly.** The chosen
  harness fakes the Tauri IPC layer and runs the bundle in Chromium. What this
  actually is: a **React-bundle integration test in Chromium with a faked IPC
  layer** — call it "full-UI integration E2E," but do not over-trust a green run.
  Three structural blind spots, all out of scope: **(a)** real Rust IPC, encoding,
  file watcher, native dialogs; **(b)** WKWebView-specific rendering (we test
  Chromium, not the shipped engine); **(c)** anything the shim mocks wrong. The
  shim is a maintained first-class fixture. Native fidelity is **permanently** out
  of reach for the portable skill — Approach C (mdpro-only) is the *only* way to
  close (a), and it does NOT make the open-source skill more faithful. Do not treat
  C as a rescue for B.
- **P3a — The shim is more than `invoke`.** Tauri **v2** routes `invoke` through
  `window.__TAURI_INTERNALS__.invoke` (NOT the deprecated v1 `__TAURI__` global).
  The app also *detects* Tauri via `__TAURI_INTERNALS__` (`src/main.tsx`), so
  without it the services take their `isTauri === false` browser-fallback branches
  and never call the backend at all. The shim must therefore define
  `window.__TAURI_INTERNALS__ = { invoke, transformCallback, unregisterCallback,
  convertFileSrc, ... }` AND an **event channel**: several core flows
  (`menu:action`, `file:open`, `file:changed`, `theme:changed`) are driven by Rust
  → frontend events via `@tauri-apps/api/event` `listen()` in `useMenuEvents`,
  `useFileWatcher`, `useMcpEvents`, `useTheme` — the shim must be able to *emit*
  those, or those flows can't be exercised. `convertFileSrc` is needed for the
  paste-image flow.
- **P4 — Reusability requires data, not code (with one honest exception).** Generic
  driver (skill) + per-app `verify.manifest` (flows, **events**, selectors,
  assertions, screenshot points) + per-app `tauri-mock` shim. The exception:
  **stable selectors require per-app code** — mdpro has zero `data-testid` today
  and ProseMirror DOM is generated, so adoption means adding test handles in `src/`,
  not just writing manifest data. Adoption = manifest + shim + a few `data-testid`s.

## Approaches Considered

### Approach A: Agent-only `verify-feature` (minimal viable)
One agent (fresh context, Bash) whose prompt holds the procedure: boot `pnpm dev`,
run a Playwright driver over core flows with a `__TAURI_INTERNALS__` shim, capture
screenshots + console, return PASS/FAIL + findings.
- Effort: M. Risk: Low-Med.
- Pros: directly honors the isolated verdict; fewest moving parts; ships this week.
- Cons: procedure baked in prompt → least reusable as open-source; agent returns
  text only, so screenshot artifacts hand back awkwardly.

### Approach B: Agent (judge) + portable skill (driver + manifest) — CHOSEN
A `verify-runner` **agent** gives isolation; it invokes a reusable
`verify-feature` **skill** = generic Playwright driver that reads a per-app
`verify.manifest.{yaml,ts}` (flows, events, selectors, assertions, screenshot
points) + a per-app `tauri-mock.ts` shim scaffolded from registered commands.
mdpro is the reference implementation; the skill is publishable.
- Effort: L. Risk: Med.
- Pros: satisfies BOTH goals (isolation via agent, reusable-as-data via
  skill+manifest); the skill is the shareable open-source unit; the driver is
  testable on its own.
- Cons: more upfront design (manifest schema is the hard part); two artifacts to
  keep in sync.

### Approach C: Visual-regression-first via the real app (lateral)
Skip the mocked shim; agent drives the REAL running app through mdpro's existing
`mdpro_mcp` server for state mutation, with golden-screenshot diffs as pass/fail.
- Effort: M-L. Risk: Med-High.
- Pros: real Rust IPC → closes the P3 gap; golden screenshots catch the
  "layout shift you weren't looking for."
- Cons: assumes the app ships an MCP seam → NOT portable → fights the open-source
  goal; screenshot diffs are flaky (fonts/AA/macOS rendering). Best kept as
  mdpro's *own* future native-fidelity tier, not the open-source default.

## Recommended Approach

**Approach B**, built in two stages so you get value fast and reusability second:

**Stage 1 (build A inline as B's engine).** Implement the Playwright driver and a
hand-written `__TAURI_INTERNALS__` shim against mdpro's real flows. Prove the loop
closes end to end for one app.

**Stage 2 (extract the manifest = make it B).** Pull mdpro's flows/selectors/
assertions/screenshot points out of the driver into a declarative
`verify.manifest.ts`, and scaffold the shim from the registered command list.
Extraction mechanism (non-trivial — `handlers()` is a Rust `generate_handler!`
macro, ~38 commands as `module::command` paths): a regex pass over
`src-tauri/src/commands/mod.rs` extracting `module::command` identifiers (skipping
`//` comment lines), cross-checked against the TS service wrappers in
`src/services/`. Now a new Tauri app adopts the skill by writing a manifest + shim
+ a few `data-testid`s, not by editing the driver.

**Manifest schema (the seam — sketched so Stage 2 isn't invented from scratch):**

```ts
// verify.manifest.ts
export const manifest: VerifyManifest = {
  bootUrl: 'http://localhost:1420',
  consoleAllowlist: [/React DevTools/, /Download the Vue/], // expected dev noise
  flows: [{
    name: 'toggle-wysiwyg-source',
    invokeMocks: { get_preferences: prefsFixture, save_file: { ok: true } },
    eventEmits: [{ event: 'menu:action', payload: { action: 'view.source' } }],
    steps: [
      { type: 'click', selector: '[data-testid="mode-toggle"]' },
      { type: 'type',  selector: '[data-testid="cm-editor"]', text: '# Hi' },
    ],
    assert: [{ type: 'visible', selector: '[data-testid="milkdown-root"]' }],
    screenshot: ['after-toggle'],
  }],
};
```

**Report contract (driver → agent seam):**

```ts
// emitted as JSON to stdout/file
{ overall: 'PASS' | 'FAIL',
  flows: [{ name, status: 'PASS'|'FAIL', consoleErrors: string[],
            screenshots: string[], failedAssertion?: string }] }
```

Architecture:
- **`.claude/agents/verify-runner.md`** — the isolation layer. Fresh context,
  Bash + Read. Receives a brief (what changed, which flows to run), invokes the
  skill, reads the structured report + screenshots, renders an independent
  PASS / FAIL / verdict-with-findings. Mirrors `test-runner.md`.
- **`.claude/skills/verify-feature/`** — the reusable procedure: `SKILL.md`
  (how to boot the dev server, run the driver, interpret results) + a generic
  Playwright `driver.ts` that consumes the manifest + emits a structured JSON
  report (per-flow pass/fail, console errors, screenshot paths) and a
  human-readable summary.
- **`tests/e2e/verify.manifest.ts`** — mdpro's flows: open doc, type markdown,
  toggle WYSIWYG↔source, one table op, paste image; with selectors, assertions,
  and screenshot points.
- **`tests/e2e/tauri-mock.ts`** — the `window.__TAURI_INTERNALS__` shim (invoke +
  `transformCallback`/`convertFileSrc` + an **event-emit channel** so `listen()`
  hooks fire), scaffolded from the registered command list, returning realistic
  fixtures. Injected via Playwright `addInitScript` *before* the bundle loads so
  the app's `isTauri` detection takes the real branches.
- **`/verify` command** — thin on-demand entry that dispatches the
  `verify-runner` agent. (Per the trigger decision: explicit invocation, not
  auto-on-every-change.)

## Open Questions

1. **Shim drift detection.** How do we keep `tauri-mock.ts` honest vs. the real
   Rust commands? Candidate: a guard test that diffs the shim's mocked command
   names against `handlers()` and fails if a command is unmocked. Decide in
   Stage 2.
2. **Milkdown/CodeMirror selector stability.** ProseMirror DOM is generated;
   selectors may be brittle. Need a convention (data-testid hooks?) — may require
   small `src/` changes to add stable test handles.
3. **Console-error allowlist.** Some console noise is expected (dev warnings).
   The manifest needs an allowlist so the verdict isn't permanently red.
4. **Native-fidelity tier.** Approach C (mdpro-only, real backend via `mdpro_mcp`)
   is the ONLY way to cover the P3(a) real-IPC blind spot — and it does *not* make
   the portable skill more faithful. Defer it as an opt-in mdpro tier; document
   that the open-source skill permanently cannot close that gap. Decide later
   whether mdpro wants it at all.
5. **Screenshot baseline storage.** If/when visual regression is added, where do
   golden images live and how are they reviewed on update?

## Success Criteria

- `/verify` dispatches the agent; the agent boots `pnpm dev`, runs ≥5 core mdpro
  flows headless, and returns a structured PASS/FAIL with per-flow results,
  captured console errors, and screenshot paths — **no human clicks required**.
- Every run reports a **console-error count** and a **fixed-layout screenshot**
  for each flow as standing signals — so a regression outside the changed feature
  (console noise, layout shift) shows up even when no assertion targeted it. (This
  replaces the earlier untestable "surfaces a regression" wording with a concrete,
  always-on gate.)
- A shim-drift guard fails when a registered command is unmocked.
- Runs in CI (GitHub Actions) headless, green on a known-good commit.
- **Stretch (non-blocking — must NOT gate landing mdpro value):** a throwaway
  Tauri app verified by adding only a manifest + shim (+ its `data-testid`s) —
  zero edits to the driver or agent. Proves the open-source reuse claim.

## Distribution Plan

- The reusable unit ships as the **`verify-feature` skill directory** (+ the
  `verify-runner` agent) — the shareable artifact is the `.claude/skills/` /
  `.claude/agents/` pair, distributable via a repo, a skills marketplace, or the
  gstack-style team-skills mechanism.
- mdpro's manifest + shim live in-repo under `tests/e2e/` as the reference
  implementation and the in-project CI consumer.
- CI/CD: a GitHub Actions job runs the verify loop headless on PRs (wired after
  Stage 1 proves locally). Open-source release of the skill is a later, separate
  step once the manifest schema stabilizes.

## Next Steps

1. **Spike the harness (Stage 1, riskiest-first).** `npm i -D @playwright/test`
   (not currently installed). Stand up `pnpm dev` + a hand-written
   `__TAURI_INTERNALS__` shim (invoke + event-emit) injected via `addInitScript`,
   and drive ONE flow (open doc → type → toggle WYSIWYG → screenshot → read
   console). Two things to confirm here, both currently unproven: (a) the shim
   makes `isTauri` true so real branches run; (b) ProseMirror DOM is drivable —
   add the first `data-testid` handles. De-risks P3a and Open Question #2 before
   any agent/skill scaffolding. (human: ~1 day / CC: ~30–60 min)
2. **Write the structured report contract.** Define the JSON the driver emits
   (per-flow status, console errors, screenshot paths) — this is the seam between
   driver and agent. (CC: ~15 min)
3. **Build the `verify-feature` skill** around the proven driver: `SKILL.md` +
   `driver.ts`, reading flows inline first.
4. **Build the `verify-runner` agent** (clone `test-runner.md` structure) + the
   `/verify` command that dispatches it.
5. **Extract the manifest (Stage 2 → makes it Approach B).** Move flows to
   `verify.manifest.ts`; scaffold `tauri-mock.ts` from `handlers()`; add the
   shim-drift guard test.
6. **Wire CI** (GitHub Actions headless run) once local is green.
7. **Reusability validation:** verify a throwaway Tauri app via manifest-only.

## Recorded Obligation: the mocked OS-opener boundary has no lane (2026-09-14)

Recorded against this plan because this plan is the thing that would close it.
Tracked in the tdd-guardian artifacts for the link-guard security work as F3
(`coverage-20260913-194347.md`), T4 (`review-20260913-195849.md`) and T-11
(`review-20260914-140027.md`); all three say to record the deferral here, and
none of them had until now.

**The obligation.** `policy-core` rule 6 makes every mocked boundary owe a named
integration-lane test exercising the real path, and rule 5 requires security
properties specifically to be verified behaviorally in the integration lane.
Both link-guard suites mock `@tauri-apps/plugin-opener`
(`tests/milkdown-link-click-guard.test.ts`,
`tests/milkdown-link-click-guard.prod-origin.test.ts:37`).

**Why it is unmet.** `.claude/tdd-guardian/config.json` declares exactly two
lanes, `unit` and `rust`. There is no integration or e2e lane, so the obligation
is **structurally unmeetable** — not deferred by choice, but with nowhere to go.

**What is and is not proven.** The unit tests prove the *decision* is correct,
and prove it well: the predicates are pure functions and the hook's gates are
real DOM logic that jsdom runs for real. They cannot prove the *handoff* is
correct, because `openUrl` is a `vi.fn()`. The assertion that matters most — the
validated string actually reaches the OS opener, and `tauri://` is refused by
the `opener:default` capability — is verified only by `toHaveBeenCalledWith`
against a mock. ADR-0002 consequence (e) names the same gap from the other side:
production WKWebView verification is outstanding. Closing this by widening the
unit lane would be the coverage equivalent of a wiring-only test.

**This plan's Stage 1/2 would not close it either — which sharpens Open
Question 4.** The obligation names the *real OS handoff*, and P3 blind spot (a)
already concedes that the chosen harness fakes the Tauri IPC layer. A Playwright
lane built per Approach B would still shim the opener, so it would convert a
`vi.fn()` into a different fake rather than exercising the capability. Only
Approach C (the real backend via `mdpro_mcp`, Open Question 4) or a named manual
check against a real build can discharge this. Recording it here is therefore
evidence *for* eventually wanting the mdpro-only native-fidelity tier — it is
the first concrete obligation that only Approach C can satisfy — and not a new
Stage 1 requirement.

## What I noticed about how you think

- You didn't accept "make it a skill" just because the reference doc said skill —
  you said *"only end-to-end test can complete the loop"* and then pushed
  **"reconsider P1 — make it an agent."** You separated the *isolation* property
  from the *artifact*, which is the exact distinction the reference doc blurs.
  That's a real design instinct, not pattern-matching.
- You framed the ask as *"build an end-to-end verification loop"* but immediately
  flagged the gap in your existing tooling (*"tdd-guardian mainly builds unit
  tests"*). You're not chasing novelty — you're filling a hole you already
  located in your own pipeline.
- You picked the **portable** harness (dev-server + shim) over the
  higher-fidelity one without me arguing for it — you optimized for the
  open-source/reuse goal over local convenience, which is the harder, more correct
  call for a thing meant to be shared.
