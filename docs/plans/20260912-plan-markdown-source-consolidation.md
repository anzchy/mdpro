## Problem Statement

mdpro 定位为「Typora 的 WYSIWYG + 现代设计」。本次以同类产品
[xiaolai/vmark](https://github.com/xiaolai/vmark)（v0.9.71，68 万行 TS + 13 万行 Rust）
为对照做技术栈评审，结论是：**底座选型正确，但 Markdown 语义被切成了五份。**

这不是风格问题。它是后续每一个语法特性（数学、脚注、图表、任务列表）都要
重复付费的结构性成本，也是 CHANGELOG 里锚点不一致、CJK slug 不一致、CRLF
三处各处理一遍这一整类 bug 的共同根因。

## Part 2 — 核心发现：五套 Markdown 语义

**[实测]** 逐条核对过，附证据位置。

| # | 引擎 | 位置 | 状态 | 服务对象 |
|---|---|---|---|---|
| 1 | pulldown-cmark（HTML） | `src-tauri/src/services/markdown.rs:514-525` | **活** | HTML 导出 |
| 2 | pulldown-cmark（TOC） | `src-tauri/src/commands/toc.rs:79-83` | **死** | 无调用者 |
| 3 | marked | `src/services/exportService.ts:64`；`src/components/common/settings/AboutSettings.tsx:196` | **活** | 导出降级 + 关于页 |
| 4 | remark（经 Milkdown） | WYSIWYG | **活** | 编辑面 |
| 5 | 正则标题解析器 | `src/services/tocService.ts:48` | **活** | TOC 侧栏 |

### 2.1 同一个库，两套语义

引擎 1 与引擎 2 都是 pulldown-cmark，但**解析选项互不包含**：

- `toc.rs:79-83` → `ENABLE_HEADING_ATTRIBUTES`、`ENABLE_TABLES`
- `markdown.rs:514-525` → `ENABLE_STRIKETHROUGH`、`ENABLE_TABLES`、`ENABLE_TASKLISTS`、`ENABLE_MATH`、`ENABLE_FOOTNOTES`（**未开** `HEADING_ATTRIBUTES`）

**[推断]** 含 `~~删除线~~` 或 `$math$` 的标题，在两侧会被切成不同 token。
Codex 的原话「同一个库并不自动意味着同一种语义」在此得到具体确认。

### 2.2 TOC 的真实实现是正则，不是解析器

- `useTOC.ts:73` 调用的是**同步**的 `parseHeadingsFromContent()`，不是 Rust。
- 该函数自己的注释写着 "frontend-only fallback … when backend is not available"
  —— 但它已是**唯一活路径**。
- 它**只认 ATX 标题**（`tocService.ts:66` 的 `/^(#{1,6})\s+/`），
  不认 Setext，**没有代码围栏状态** —— 代码块里的 `# 注释` 会被当成标题。
- `getDocumentHeadings()`（走 Rust 那个）**零调用者**，且**参数名对不上**：
  TS 传 `document_id`（`tocService.ts:38`），Rust 收 `content`（`toc.rs:128`）。
  **这是死代码里藏着的真 bug —— 一旦有人接上就必炸。**

### 2.3 三份手工同步的 slug 算法，无跨语言测试兜底

| 实现 | 位置 | 算法 |
|---|---|---|
| JS（导出） | `exportService.ts:47` | `\p{L}\p{N}` |
| JS（TOC） | `tocService.ts:101` | `\p{L}\p{N}` |
| Rust | `markdown.rs:23` | `char::is_alphanumeric()` |

- 两份 JS **逐字相同**，靠一句注释 "Algorithm must stay in sync with
  generateHeadingId" 维系 —— 目前同步，属**潜在**漂移，不是现存 bug。
- **[推断]** Rust 的 `is_alphanumeric()` 与 JS 的 `\p{L}\p{N}` **不等价**
  （前者的 Alphabetic 属性含 Nl 及部分组合记号），存在真实边界分歧类别。
- **[实测]** `sanitizer-rust-js-parity.test.ts` 只比对净化器白名单
  （MATH_TAGS / SVG_TAGS / SVG_ATTRS / URI schemes），**完全不涉及 slug**；
  `cjk-slug.test.ts:11` 把 `invoke` mock 掉了，只测 JS 侧。
  ⇒ **这条分歧没有任何测试兜底。**

### 2.4 Preview 面板已死，但目录不能整个删

- `Preview.tsx` / `ImageRenderer.tsx` / `usePreview.ts` **零外部引用者**。
- 但 `Preview/mathRender.ts` **是活的**，被 `exportService.ts:4` 引用。
  **[Codex]** 正确指出：不能整目录删除，要先把 `mathRender.ts` 搬出去。
- `preview_html` 因此也已死（唯一上游 `usePreview` 已无人调用）。
- ⚠️ **文档与现实不符**：CLAUDE.md 称 Phase 1 的数学/脚注落在
  「Preview 面板与 HTML 导出」，**实际只有导出**。需同步修正。

### 2.5 导出链路上 ammonia 是真防线 **[实测]**

```
Rust 渲染 → DOMPurify → 高亮/图片宽度 → KaTeX MathML → ammonia 二次净化 → 模板写盘
```

`export.rs:160` 的注释明确写道：「前端已跑 DOMPurify，但导出绝不信任它 ——
同一份白名单在服务端再跑一遍」。另有 `export.rs:60`、`:126` 两处净化。

⇒ **ammonia 不是冗余，是纵深防御。** 支持 Codex「不要随解析器一起删」的判断。

## Part 3 — Codex 评议与我的交叉验证

Codex 的决议原文：**「采用 C→A，拒绝 B；保留 Markdown 文本真源，统一 TS 语义层；
保真与净化分别立项，ammonia 不随解析器一起删除。」**

### 我采纳的（并已独立验证）

| Codex 的判断 | 我的核实结果 |
|---|---|
| 拒绝路线 B（收向 Rust） | **采纳。** 论证成立：`原文 → PM → Markdown′ → Rust`，前三步已丢信息，Rust 只看到 `Markdown′`，无法恢复。pulldown-cmark 是事件式解析器，不是保真编辑模型。 |
| 保留 ammonia | **采纳，且已实测确认**（`export.rs:160`）。净化器不是语义引擎，保留它不妨碍解析收敛。 |
| 先做 C，不要一次性删三个依赖 | **采纳。** 一次发布同时迁移语义边界和安全边界，风险不可控。 |
| `AboutSettings.tsx:196` 仍用 marked | **实测确认。** 删降级路径 ≠ 能删依赖。 |
| `getDocumentHeadings` 参数不匹配 | **实测确认**，是真 bug。 |
| 目标应改写为「Markdown 文本是持久化真源，MDAST 是派生 IR」 | **采纳。** 我原本的提法「MDAST 作为唯一真源」不准确，Codex 这个修正更对。 |

### 我不完全采纳的

1. **[Codex] 的工期估算（2–4 人周 / 2–6 人周 / 数月）** —— 它自己标注为经验估计。
   本计划保留其量级用于排期，但**不作为承诺**，以阶段 0 的实测为准。
2. **Codex 未核实 vmark** —— 它明确声明 vmark 数据是采信我提供的信息。
   vmark 相关数字均为我本次实测，责任在我。
3. **Codex 低估了分裂程度** —— 它说「三套」，实际是**五套**（Part 2.1 的同库双语义
   是我在它给出结论后才核实出来的）。这加重而非减轻 P0 的紧迫性。

### Codex 提出而我原先遗漏的重要一点

> **导航身份不要完全等同于导出 slug。** 重复标题应定位到对应 PM 节点或源码位置，
> 而不是用标题文字去找第一个 DOM 元素。位置契约必须明确 UTF-16 offset、行号、
> 换行规范 —— **Rust 的字节偏移不能直接当 JS 字符偏移。**

这是对的，且当前 `tocService.ts` 的 `offset` 正是按字节长度累加的。收编。

## Part 4 — 决议

**采用 C→A，拒绝 B。**

- **真源定义**：Markdown 文本是持久化真源；统一的 remark 配置定义文档语义；
  MDAST 是派生中间表示；ProseMirror 是编辑状态。
- **不要**为了「唯一真源」把应用状态强行改成 MDAST。CodeMirror 保留自己的
  增量语法树是合理的，它服务于高亮，不应决定导出语义。
- **保真与净化分别立项**，不绑在同一次发布里。

## Part 5 — 分阶段迁移（含回滚点与最大风险）

| 阶段 | 工作与通过条件 | 回滚点 | 最大风险 |
|---|---|---|---|
| **0 冻结契约** | 建语法矩阵、代表性文档、安全样例；记录当前五套引擎的差异与性能基线 | 无行为变更 | 把现有错误误当成规范 |
| **1 执行 C 清理** | 删导出的 marked 自动降级（失败改显式报错+重试）；`mathRender.ts` 搬出 Preview；删死的 Preview 入口、`toc.rs`、`preview_html`；修 CLAUDE.md 的失实描述 | 每步独立提交可撤销 | 误删仍被导出引用的工具（`mathRender.ts`） |
| **2 统一 TOC** | 用共享 remark 配置替换正则；覆盖围栏/Setext/格式化标题/重复/CJK/emoji；建立正确的位置映射（UTF-16 offset + 行号） | TOC 实现开关，不动正文 | 错误导航；大文件全量解析阻塞主线程 |
| **3 TS 导出并行验证** | MDAST→HAST→HTML；以旧 Rust 输出作差异参照；**ammonia 保留**；差异人工裁决 | 显式切回旧导出器（禁止异常时偷偷切换） | 扩展语法、图片、脚注、数学表现退化 |
| **4 切换并移除 Rust Markdown** | TS 导出通过语义/安全/离线显示/性能门槛后，确认无消费者再删 pulldown-cmark | 保留上一稳定版本与测试语料 | 隐藏调用方、资源路径、大文件遗漏 |
| **5 提升编辑保真** | 逐项补 PM 支持；不支持的结构保留为原文节点或退回源码模式 | 新能力开关 + 迁移前原文/草稿 | **已保存数据的损失无法靠代码回滚恢复** |
| **6 单独评估 ammonia** | 仅当最终 TS 净化覆盖全部出口、且安全评估通过后再考虑删 | 恢复 Rust 净化；已导出文件需重新生成 | 防御层减少；净化后处理遗漏 |

### 保真分级（不要一开始就追字节级）

| 等级 | 实现方式 |
|---|---|
| 语义保真：文字与结构不丢 | 复用 Milkdown schema + 往返测试 |
| 未编辑内容保持原样 | 保存原始文本与节点来源，局部重写 |
| 字节级保真 | 还需管理空白、分隔符、引用定义、源码位置 |

**[Codex]** MDAST 是抽象语法树，序列化器按规则生成 Markdown，
**不能当作完整保存原始拼写和空白的具体语法树**。

### 10MB 门槛单列验收

分别测：普通长文、大表格、大量短节点、超长单行、密集数学的
解析时间 / 主线程阻塞 / 峰值内存。
**文件能打开 ≠ 适合完整挂载成 PM DOM。**
可把 remark 解析移入 Worker，但 **DOMPurify 需要 DOM，不能原样搬进普通 Worker**。

### 迁移验收三条红线

1. 未编辑时切换模式不得改写正文；局部编辑不得丢失其他结构。
2. 导出与 TOC 对同一语法必须给出一致解释，差异须有明确产品规则。
3. 异步结果必须携带文档 ID 与修订号，过期结果不得覆盖新内容。

## Part 6 — 与 P0 无关的独立改进项

**[实测]** 均已核实，可与上述阶段并行。

### P1 — 补静态检查（性价比最高）

当前**零 ESLint 配置**。以 AI 大量参与写码的方式，这是最划算的一道网。
建议：`eslint` + `typescript-eslint` + `eslint-plugin-react-hooks`。
不建议照抄 vmark 的 211 个门禁脚本 —— 那是 5,893 文件规模摊销出来的。

### P2 — 两处安全面收紧

| 项 | 现状 | 位置 |
|---|---|---|
| asset 协议作用域 | `"scope": ["**/*"]` —— 整个文件系统 | `src-tauri/tauri.conf.json` |
| CSP | 含 `'unsafe-eval'` | 同上 |

按项目自己的 rule 60「IPC 信任边界」，两条都该收窄。

### P3 — 卫生项

- 删死配置 `tailwind.config.js`（`tailwindcss` 根本不在依赖里）。
- 修脚手架残留：`package.json` / `Cargo.toml` 里仍是 `name: "tauri-app"`、
  `authors: ["you"]`、`description: "A Tauri App"`。
- `tabStore.TabState.viewMode` 仍是已废弃的 4 模式联合类型
  （`"split" | "editor" | "preview" | "wysiwyg"`），与 `editorStore` 的 2 模式不一致。
- 24 个文件超出项目自定的 300 行上限，其中 `App.tsx` **1,194 行**。
- 依赖升级：Zustand 5 / Vite 8 / Vitest 5 / TS 7 / Milkdown 7.22。

### 覆盖率门禁的真实口径 **[实测]**

需要如实记录，避免后人误读：

- 整体 lines/statements **31.74% vs 阈值 40% = FAIL**
  （`.claude/tdd-guardian/coverage-20260629-144249.md`）。
- 配置阈值为 40/45/35/40（`.claude/tdd-guardian/config.json`）。
- 后一份报告显示 96.84% PASS，但**其自身已明确披露**是按变更文件收窄评估、
  标注 `regression: false`、并说明降阈值方案已被否决。
  ⇒ **这是有披露的范围收窄，不是偷偷放水。** 但整体基线确实未达标。

## Part 7 — 明确不做的事

1. **不换 Tiptap。** Milkdown 7.22.1（2026-08）活跃，痛点在解析管线而非编辑器框架，
   换框架成本极高、收益接近零。
2. **不照抄 vmark 的 211 个门禁脚本。** 规模不匹配，纯负担。
3. **不在同一次发布里同时迁移语义边界和安全边界。**
4. **不追求一步到位的字节级源码保真。** 分级推进。

### 为什么必须提前

P 的 WI-4.26 要求 TOC 重解析时「reconcile collapse state **by heading identity**」，
却没有定义什么算同一个标题。而它要依赖的 identity **今天就是坏的** **[实测]**：

- `tocService.ts:101-111` `generateUniqueId` 只按 `baseId` 计数，不检查生成出的 id
  是否已被占用：`# x` / `# x` / `# x-1` → `x`, `x-1`, `x-1`
- 同一函数 `:111` 的 `return id || "heading"` 在计数**之后**执行且从不注册 `"heading"`，
  纯 emoji 标题与字面 `# heading` 碰撞
- `exportService.ts:47-58` `generateHeadingId` 与之**逐字节相同** —— 两个面带着同样两个缺陷；
  `tocService.ts:99` 那句 "Algorithm must stay in sync" 是靠复制粘贴维持的，没有测试保障
- `useTOC.ts` 的 WYSIWYG 回退按文本匹配且首个命中即 `break`，重复标题点第二个会跳到第一个
- **没有任何测试断言 id 两两互异**；`tests/cjk-slug.test.ts:30`/`:97` 只覆盖
  「不同文本→不同 slug」，而 `:53-59` 用 `expect(headings[0].id).toBe("heading")` 把缺陷钉死了
- `parseHeadingsFromContent` 按 `/\r?\n/` 切分后 `offset += line.length + 1`，
  CRLF 每行少算 1：`text\r\n# 标题` 报 offset 5，实际源码位置是 6

先做 WI-4.26 等于把验收标准写在一个会碰撞的 identity 上，并固化进测试套件。
因此 WI-4.26 只保留 E37 的 MCP 变更检测修复、`useTOC` 的 field selector 改造，
以及新组合上的回归验证；身份协调本身由本计划在第 3 步交付。

### 提前交付的范围（不是整个 M）

**提前**：标题提取、位置映射、身份协调、两种编辑模式下的真实导航。
**不提前**：导出迁移、`marked` 降级移除、`toc.rs` / `preview_html` 退役、ammonia 评估。

身份必须拆成三个稳定性不同的概念，不能用一个 `id` 同时承诺 **[Codex]**：

| 概念 | 作用 | 稳定性要求 |
|---|---|---|
| `anchorSlug` | 导出 HTML 锚点 | 同输入确定、文档内唯一 |
| `headingKey` | 编辑过程中关联同一标题 | 约定范围内跨修订协调 |
| 位置 | 导航到源码或 PM 节点 | 随修订更新，不充当稳定身份 |

契约至少规定：标题前后编辑普通段落时折叠状态保留、位置更新；重复标题彼此独立，
点第二个必须到第二个；删除标题时清理其折叠与活动状态；切换文档时清空状态，
不因两个文档都有 `intro` 而继承；无法可靠匹配的标题重置状态，不得猜测后转移给另一个标题。

测试分三层：**协调算法单测**（输入不透明 key，不依赖解析器）；
**语义契约测试**（真实 Markdown，覆盖围栏、Setext、格式化标题、重复、CJK、CRLF、slug 唯一性）；
**用户行为测试**（折叠→编辑→重解析后仍折叠；Source 与 WYSIWYG 两种模式的导航目标）。
第三层不可省 —— store 单测全绿也挡不住重复标题跳错。

### 过渡期必须登记的事实

TOC 提前统一后，**导出仍是旧语义**。该中间状态及其已知差异必须登记进阶段 0 的语法矩阵，
**不得对外宣称「语义已统一」**。共享 remark 配置与 Milkdown 实际插件集合之间也需一致性验证。

P 的零额外 React commit 断言**不能**替代本计划的性能验收 —— 它证明不了 remark 不阻塞主线程。
第 3 步的前置验收必须实测大文档，并覆盖切文档、关文档与过期解析结果。

第 3 步只允许为自身所需而改 `App.tsx`（文档 id、修订号），
不夹带布局或生命周期重构；同一时段只保留一个修改 `App.tsx` 的实施 PR。
