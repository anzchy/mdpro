## Problem Statement

mdpro 定位为「Typora 的 WYSIWYG + 现代设计」。本次以同类产品
[xiaolai/vmark](https://github.com/xiaolai/vmark)（v0.9.71，68 万行 TS + 13 万行 Rust）
为对照做技术栈评审，结论是：**底座选型正确，但 Markdown 语义被切成了五份。**

这不是风格问题。它是后续每一个语法特性（数学、脚注、图表、任务列表）都要
重复付费的结构性成本，也是 CHANGELOG 里锚点不一致、CJK slug 不一致、CRLF
三处各处理一遍这一整类 bug 的共同根因。

## Part 2 — 核心发现：五套 Markdown 语义

**[实测]** 逐条核对过，附证据位置。

| # | 引擎 | 位置 | 状态 | 服务对象 |
|---|---|---|---|---|
| 1 | pulldown-cmark（HTML） | `src-tauri/src/services/markdown.rs:514-525` | **活** | HTML 导出 |
| 2 | pulldown-cmark（TOC） | `src-tauri/src/commands/toc.rs:79-83` | **死** | 无调用者 |
| 3 | marked | `src/services/exportService.ts:64`；`src/components/common/settings/AboutSettings.tsx:196` | **活** | 导出降级 + 关于页 |
| 4 | remark（经 Milkdown） | WYSIWYG | **活** | 编辑面 |
| 5 | 正则标题解析器 | `src/services/tocService.ts:48` | **活** | TOC 侧栏 |

### 2.1 同一个库，两套语义

引擎 1 与引擎 2 都是 pulldown-cmark，但**解析选项互不包含**：

- `toc.rs:79-83` → `ENABLE_HEADING_ATTRIBUTES`、`ENABLE_TABLES`
- `markdown.rs:514-525` → `ENABLE_STRIKETHROUGH`、`ENABLE_TABLES`、`ENABLE_TASKLISTS`、`ENABLE_MATH`、`ENABLE_FOOTNOTES`（**未开** `HEADING_ATTRIBUTES`）

**[推断]** 含 `~~删除线~~` 或 `$math$` 的标题，在两侧会被切成不同 token。
Codex 的原话「同一个库并不自动意味着同一种语义」在此得到具体确认。

### 2.2 TOC 的真实实现是正则，不是解析器

- `useTOC.ts:73` 调用的是**同步**的 `parseHeadingsFromContent()`，不是 Rust。
- 该函数自己的注释写着 "frontend-only fallback … when backend is not available"
  —— 但它已是**唯一活路径**。
- 它**只认 ATX 标题**（`tocService.ts:66` 的 `/^(#{1,6})\s+/`），
  不认 Setext，**没有代码围栏状态** —— 代码块里的 `# 注释` 会被当成标题。
- `getDocumentHeadings()`（走 Rust 那个）**零调用者**，且**参数名对不上**：
  TS 传 `document_id`（`tocService.ts:38`），Rust 收 `content`（`toc.rs:128`）。
  **这是死代码里藏着的真 bug —— 一旦有人接上就必炸。**

### 2.3 五份手工同步的 slug 算法，无跨语言测试兜底

**原记「三份」，实测是五份** —— 遗漏了 `toc.rs` 与 `tocStore.ts` 各自的一份。

| 实现 | 位置 | 算法 | 状态 |
|---|---|---|---|
| JS（导出回退） | `exportService.ts:47` `generateHeadingId` | `\p{L}\p{N}` + 计数表 | 活 |
| JS（TOC 侧栏） | `tocService.ts:101` `generateUniqueId` | 同上，**函数体 md5 相同** | 活 |
| JS（未使用） | `tocStore.ts:120` `generateAnchorId` | `[^\w-]`（**剥除 CJK**）+ `while` 占用检查 | **死，零引用** |
| Rust（导出） | `markdown.rs:23` `generate_heading_id` | `char::is_alphanumeric()` + 计数表 | 活，导出锚点由它生成 |
| Rust（TOC） | `toc.rs:36` `generate_unique_id` | 逐字符映射后 split/filter/join | 死（见 2.2 的参数不匹配） |

- 两份 JS **函数体逐字节相同**（md5 相同），仅函数名不同，靠一句注释
  "Algorithm must stay in sync with generateHeadingId" 维系 —— 目前同步，属**潜在**漂移，不是现存 bug。
- **`generateAnchorId` 是五份里唯一防碰撞正确的实现，而它没有任何引用者。**
  它用 `while (existingIds.has(id))` 检查占用，因此不会产生下文 4.1 的合成/自然名冲突；
  但它用 `[^\w-]` 剥除全部 CJK，所以不能直接拿来当统一实现，只能作为去重逻辑的参照。
- **[推断]** Rust 的 `is_alphanumeric()` 与 JS 的 `\p{L}\p{N}` **不等价**
  （前者的 Alphabetic 属性含 Nl 及部分组合记号），存在真实边界分歧类别。
- **[实测]** `sanitizer-rust-js-parity.test.ts` 只比对净化器白名单
  （MATH_TAGS / SVG_TAGS / SVG_ATTRS / URI schemes），**完全不涉及 slug**；
  `cjk-slug.test.ts:11` 把 `invoke` mock 掉了，只测 JS 侧。
  ⇒ **这条分歧没有任何测试兜底。**

### 2.4 Preview 面板已死，但目录不能整个删 ✅ 已执行

**已执行**（2026-09-12）：`mathRender.ts` 先由 `e021f47` 搬到 `src/services/mathRender.ts`，
四个 Preview 文件随后由 `15b9d35` 删除；`src/components/Preview/` 目录已不存在。
下列描述是**决策当时**的现状，保留作依据，不再是对今天仓库的断言。

- `Preview.tsx` / `ImageRenderer.tsx` / `usePreview.ts` **零外部引用者**。
- 但 `Preview/mathRender.ts` **是活的**，被 `exportService.ts` 引用（搬移后的引用点为 `exportService.ts:6`）。
  **[Codex]** 正确指出：不能整目录删除，要先把 `mathRender.ts` 搬出去。
- `preview_html` 因此也已死（唯一上游 `usePreview` 已无人调用）。
- ⚠️ **文档与现实不符**：CLAUDE.md 称 Phase 1 的数学/脚注落在
  「Preview 面板与 HTML 导出」，**实际只有导出**。需同步修正。

### 2.5 导出链路上 ammonia 是真防线 **[实测]**

```
Rust 渲染 → DOMPurify → 高亮/图片宽度 → KaTeX MathML → ammonia 二次净化 → 模板写盘
```

`export.rs:160` 的注释明确写道：「前端已跑 DOMPurify，但导出绝不信任它 ——
同一份白名单在服务端再跑一遍」。另有 `export.rs:60`、`:126` 两处净化。

**补充 [实测]（2026-09-13）**：IPC 命令 `commands/export.rs:19 render_markdown`
**不做服务端净化**，其 doc 注释明示 "without server-side sanitization"。
因此在活路径上，**进程内只有 DOMPurify 这一道净化**，ammonia 要到 `export.rs:158`
才首次运行。注意与之同名的**服务**函数 `services::markdown::render_markdown` 不是一回事，
后者被 `export.rs:60` 的 `export_html` 与语料的 `rust` face 搭配 `sanitize_html` 使用。

⇒ **ammonia 不是冗余，是纵深防御。** 支持 Codex「不要随解析器一起删」的判断。
⇒ 这也是「导出链路整个去掉 DOMPurify」（下文选项 E1）不成立的直接原因。

## Part 3 — Codex 评议与我的交叉验证

Codex 的决议原文：**「采用 C→A，拒绝 B；保留 Markdown 文本真源，统一 TS 语义层；
保真与净化分别立项，ammonia 不随解析器一起删除。」**

### 我采纳的（并已独立验证）

| Codex 的判断 | 我的核实结果 |
|---|---|
| 拒绝路线 B（收向 Rust） | **采纳。** 论证成立：`原文 → PM → Markdown′ → Rust`，前三步已丢信息，Rust 只看到 `Markdown′`，无法恢复。pulldown-cmark 是事件式解析器，不是保真编辑模型。 |
| 保留 ammonia | **采纳，且已实测确认**（`export.rs:160`）。净化器不是语义引擎，保留它不妨碍解析收敛。 |
| 先做 C，不要一次性删三个依赖 | **采纳。** 一次发布同时迁移语义边界和安全边界，风险不可控。 |
| `AboutSettings.tsx:196` 仍用 marked | **实测确认。** 删降级路径 ≠ 能删依赖。 |
| `getDocumentHeadings` 参数不匹配 | **实测确认**，是真 bug。 |
| 目标应改写为「Markdown 文本是持久化真源，MDAST 是派生 IR」 | **采纳。** 我原本的提法「MDAST 作为唯一真源」不准确，Codex 这个修正更对。 |

### 我不完全采纳的

1. **[Codex] 的工期估算（2–4 人周 / 2–6 人周 / 数月）** —— 它自己标注为经验估计。
   本计划保留其量级用于排期，但**不作为承诺**，以阶段 0 的实测为准。
2. **Codex 未核实 vmark** —— 它明确声明 vmark 数据是采信我提供的信息。
   vmark 相关数字均为我本次实测，责任在我。
3. **Codex 低估了分裂程度** —— 它说「三套」，实际是**五套**（Part 2.1 的同库双语义
   是我在它给出结论后才核实出来的）。这加重而非减轻 P0 的紧迫性。

### Codex 提出而我原先遗漏的重要一点

> **导航身份不要完全等同于导出 slug。** 重复标题应定位到对应 PM 节点或源码位置，
> 而不是用标题文字去找第一个 DOM 元素。位置契约必须明确 UTF-16 offset、行号、
> 换行规范 —— **Rust 的字节偏移不能直接当 JS 字符偏移。**

这是对的。但本文原先那句「当前 `tocService.ts` 的 `offset` 正是按**字节**长度累加的」
**措辞不准，予以更正**：`offset += line.length + 1` 累加的是 **UTF-16 code unit**，不是字节。
真正的缺陷不在单位，而在换行：按 `/\r?\n/` 切分后 `\r` 已从 `line` 中剥离，
却仍固定 `+1`，于是每个 CRLF 行少算 1（实测见 4.1）。收编。

## Part 4 — 决议

**采用 C→A，拒绝 B。**

- **真源定义**：Markdown 文本是持久化真源；统一的 remark 配置定义文档语义；
  MDAST 是派生中间表示；ProseMirror 是编辑状态。
- **不要**为了「唯一真源」把应用状态强行改成 MDAST。CodeMirror 保留自己的
  增量语法树是合理的，它服务于高亮，不应决定导出语义。
- **保真与净化分别立项**，不绑在同一次发布里。

## Part 5 — 分阶段迁移（含回滚点与最大风险）

| 阶段 | 工作与通过条件 | 回滚点 | 最大风险 |
|---|---|---|---|
| **0 冻结契约** | 建语法矩阵、代表性文档、安全样例；记录当前五套引擎的差异与性能基线 | 无行为变更 | 把现有错误误当成规范 |
| **1 执行 C 清理** | 删导出的 marked 自动降级（失败改显式报错+重试）；`mathRender.ts` 搬出 Preview；删死的 Preview 入口、`toc.rs`、`preview_html`；修 CLAUDE.md 的失实描述 | 每步独立提交可撤销 | 误删仍被导出引用的工具（`mathRender.ts`） |
| **2 统一 TOC** | 用共享 remark 配置替换正则；覆盖围栏/Setext/格式化标题/重复/CJK/emoji/**CRLF/slug 唯一性**；建立正确的位置映射（UTF-16 offset + 行号） | TOC 实现开关，不动正文 | 错误导航；大文件全量解析阻塞主线程 |
| **3 TS 导出并行验证** | MDAST→HAST→HTML；以旧 Rust 输出作差异参照；**ammonia 保留**；差异人工裁决 | 显式切回旧导出器（禁止异常时偷偷切换） | 扩展语法、图片、脚注、数学表现退化 |
| **4 切换并移除 Rust Markdown** | TS 导出通过语义/安全/离线显示/性能门槛后，确认无消费者再删 pulldown-cmark | 保留上一稳定版本与测试语料 | 隐藏调用方、资源路径、大文件遗漏 |
| **5 提升编辑保真** | 逐项补 PM 支持；不支持的结构保留为原文节点或退回源码模式 | 新能力开关 + 迁移前原文/草稿 | **已保存数据的损失无法靠代码回滚恢复** |
| **6 单独评估 ammonia** | 仅当最终 TS 净化覆盖全部出口、且安全评估通过后再考虑删 | 恢复 Rust 净化；已导出文件需重新生成 | 防御层减少；净化后处理遗漏 |

### 保真分级（不要一开始就追字节级）

| 等级 | 实现方式 |
|---|---|
| 语义保真：文字与结构不丢 | 复用 Milkdown schema + 往返测试 |
| 未编辑内容保持原样 | 保存原始文本与节点来源，局部重写 |
| 字节级保真 | 还需管理空白、分隔符、引用定义、源码位置 |

**[Codex]** MDAST 是抽象语法树，序列化器按规则生成 Markdown，
**不能当作完整保存原始拼写和空白的具体语法树**。

### 10MB 门槛单列验收

分别测：普通长文、大表格、大量短节点、超长单行、密集数学的
解析时间 / 主线程阻塞 / 峰值内存。
**文件能打开 ≠ 适合完整挂载成 PM DOM。**
可把 remark 解析移入 Worker，但 **DOMPurify 需要 DOM，不能原样搬进普通 Worker**。

### 迁移验收三条红线

1. 未编辑时切换模式不得改写正文；局部编辑不得丢失其他结构。
2. 导出与 TOC 对同一语法必须给出一致解释，差异须有明确产品规则。
3. 异步结果必须携带文档 ID 与修订号，过期结果不得覆盖新内容。

## Part 6 — 与 P0 无关的独立改进项

### 为什么必须提前

P 的 WI-4.26 要求 TOC 重解析时「reconcile collapse state **by heading identity**」，
却没有定义什么算同一个标题。而它要依赖的 identity **今天就是坏的** **[实测]**：

- `tocService.ts:101-111` `generateUniqueId` 只按 `baseId` 计数，不检查生成出的 id
  是否已被占用：`# x` / `# x` / `# x-1` → `x`, `x-1`, `x-1`
- 同一函数 `:111` 的 `return id || "heading"` 在计数**之后**执行且从不注册 `"heading"`，
  纯 emoji 标题与字面 `# heading` 碰撞
- `exportService.ts:47-58` `generateHeadingId` 与之**逐字节相同** —— 两个面带着同样两个缺陷；
  `tocService.ts:99` 那句 "Algorithm must stay in sync" 是靠复制粘贴维持的，没有测试保障
- `useTOC.ts` 的 WYSIWYG 回退按文本匹配且首个命中即 `break`，重复标题点第二个会跳到第一个
- **没有任何测试把「id 两两互异」当作性质来断言**（只有逐例的等值断言）。
  **原记「`:53-59` 把缺陷钉死了」——该说法不实，已撤回**：该用例只喂**单个**标题
  `# 🎉🎊` 并断言 `"heading"`，而这正是期望行为；回退缺陷是 `# 🎉` 与 `# Heading`
  **共存时**才出现的碰撞，需要两个标题才能触发。把 `"heading"` 在计数前注册（Rust 现在的做法）
  之后，单个 emoji 标题仍然得到 `"heading"`，**该用例保持绿色**。
  ⇒ 3.2 需要**新增**碰撞用例，而不是改写这一条。
- `parseHeadingsFromContent` 按 `/\r?\n/` 切分后 `offset += line.length + 1`，
  CRLF 每行少算 1：`text\r\n# 标题` 报 offset 5，实际源码位置是 6

先做 WI-4.26 等于把验收标准写在一个会碰撞的 identity 上，并固化进测试套件。
因此 WI-4.26 只保留 E37 的 MCP 变更检测修复、`useTOC` 的 field selector 改造，
以及新组合上的回归验证；身份协调本身由本计划在第 3 步交付。

### 提前交付的范围（不是整个 M）

**提前**：标题提取、位置映射、身份协调、两种编辑模式下的真实导航。
**不提前**：导出迁移、`marked` 降级移除、`toc.rs` / `preview_html` 退役、ammonia 评估。

**slug 修复的面范围（本计划的验收条款，排期文档只作索引）**：五份实现中
**只改三个活面** —— `tocService.ts:101`、`exportService.ts:47`、`markdown.rs:23`，
三者同提交改齐并配跨语言 parity 测试。两个死面**明确不动**：

- `toc.rs:36` —— 其命令 `get_document_headings` 零调用方，且 TS 传 `document_id`、
  Rust 收 `content`，参数不匹配（见 2.2）。**明知其 slug 与三活面分歧而保留**，
  因为本计划已把 `toc.rs` 退役排在第 5 步、不提前；在一段待退役的死代码上改 slug
  并为它写 parity 测试是净损失。第 5 步退役时连同此分歧一并消失。
- `tocStore.ts:120` `generateAnchorId` —— 零引用。它的 `while` 占用检查是五份里
  唯一正确的去重逻辑，**作为参照实现被引用，但不作为落地实现**（它剥除 CJK）。

⇒ parity 测试的覆盖面是**三个活面**，不是五份。测试标题须写明这一点，
避免读者误以为 parity 已覆盖全仓库的 slug 实现。

身份必须拆成三个稳定性不同的概念，不能用一个 `id` 同时承诺 **[Codex]**：

| 概念 | 作用 | 稳定性要求 |
|---|---|---|
| `anchorSlug` | 导出 HTML 锚点 | 同输入确定、文档内唯一 |
| `headingKey` | 编辑过程中关联同一标题 | 约定范围内跨修订协调 |
| 位置 | 导航到源码或 PM 节点 | 随修订更新，不充当稳定身份 |

契约至少规定：标题前后编辑普通段落时折叠状态保留、位置更新；重复标题彼此独立，
点第二个必须到第二个；删除标题时清理其折叠与活动状态；切换文档时清空状态，
不因两个文档都有 `intro` 而继承；无法可靠匹配的标题重置状态，不得猜测后转移给另一个标题。

**补充（原缺，由排期文档回收）**：`headingKey` 的「约定范围内跨修订协调」必须把范围写死，
不得默认承诺任意编辑后无损识别 —— **重命名、插入、移动三种编辑的保留规则逐条明确**：
哪些保留折叠态、哪些重置、哪些视为新标题。此前这三条只出现在排期文档，
而排期文档按其自身章程只承载顺序与状态、不得新增验收标准，故在此收编为本计划的契约条款。

测试分三层：**协调算法单测**（输入不透明 key，不依赖解析器）；
**语义契约测试**（真实 Markdown，覆盖围栏、Setext、格式化标题、重复、CJK、CRLF、slug 唯一性）；
**用户行为测试**（折叠→编辑→重解析后仍折叠；Source 与 WYSIWYG 两种模式的导航目标）。
第三层不可省 —— store 单测全绿也挡不住重复标题跳错。

### 阶段 3 入口门禁一：代表性语料（已交付）

**[实测]** 2026-09-12 落地于 `c17c003`（分支 `frontend-backend-redesign`），三个文件：

| 文件 | 角色 |
|---|---|
| `tests/render-fixtures/heading-identity.json` | 语料本体，24 个用例 |
| `src-tauri/tests/heading_identity_parity.rs` | Rust runner，独占 `rust` 面 |
| `tests/heading-identity-parity.test.ts` | JS runner，独占其余四面 |

**机制。** Rust 渲染器无法从 jsdom 调用，所以 parity 不是一个测试，而是**一份语料 + 两个独立 runner**
（沿用 `render-fixtures/phase1.json` 已有的做法）。每个用例带 `expectedSlugs`（**正确答案**，不是今天的行为）
与 `currentlyFailsOn`（尚未产出正确答案的面）。两个 runner 同时断言：**不在** `currentlyFailsOn` 里的面
必须等于 `expectedSlugs`，**在**里面的面必须**不**等于。于是每个缺陷都以数据形式钉死，分支保持绿色；
WI-3.2 修好一个就删掉对应条目，断言自动翻转为要求正确。缺陷若被「顺手修好」而无人更新语料，
反向断言当场报红 —— 这是本机制相对「注释里写个 TODO」的唯一实质区别。
四条断言分支均已用两次负控制证明可失败（清空一条 pin、给一条全绿用例加 pin），非"从未见其红过"的摆设。

**面（face）分解。** 每个缺陷归属到拥有它的层，避免同一缺陷在多个面上重复计数：

| 面 | 实现 | 拥有什么 |
|---|---|---|
| `rust` | `markdown.rs` `render_markdown` → `sanitize_html` | 规范路径上的 slug **生成** |
| `toc` | `tocService.ts` `parseHeadingsFromContent` | TOC 侧栏自己的解析器与 slug 生成 |
| `tocOffsets` | 同一次解析的 `offset` 字段 | 位置映射 |
| `exportCanonical` | `exportService.ts` `renderMarkdown`，IPC **成功** | 锚点**保留**（不是生成） |
| `exportFallback` | 同一函数，IPC **失败** 的 `marked` 降级 | 决策 A1 的降级路径，非用户实际路径 |

`exportCanonical` 被喂入由 `expectedSlugs` 合成的 Rust 形状 HTML，因此**看不见 slug 生成缺陷** ——
那些一律归给 `rust`。这解释了为什么 `suffix-collision` 不列 `exportCanonical`，尽管真实导出该文档确实会输出重复 id。
合成而非快照真实 Rust HTML，是为了让语料不因无害的渲染改动而腐烂，也避免落入规则 10 禁止的快照测试。

**实测缺陷全表。** 全部于 2026-09-12 对活代码测得，非推断：

| 缺陷 | 面 | 用例 |
|---|---|---|
| 后缀碰撞：`# x` / `# x` / `# x-1` → `x`, `x-1`, `x-1` | `rust` + `toc` + `exportFallback`（**三个生成器全中**） | `suffix-collision` |
| 空 slug 回退在计数**之后**执行，`# 🎉` 与 `# heading` 产生真重复 id | `toc` + `exportFallback` | `emoji-then-literal` |
| 同一根因的第二形态：第二个空 slug 成为**裸后缀 `-1`**，一个没有基名的 id | `toc` + `exportFallback` | `two-emoji-only` |
| 无围栏状态，代码块里的 `# 注释` 被当成标题 | `toc` | `fenced-hash` |
| Setext 标题完全漏掉 | `toc` | `setext-noncolliding` |
| 行内格式泄漏进 slug（`strong-bold-strong-title`） | `exportFallback` **仅此一面** | `formatted-bold` / `inline-code` |
| DOMPurify 剥离与 document 属性同名的锚点 | `exportCanonical` + `exportFallback` | 五个 `clobber-*`、`trailing-hashes` 等 |
| CRLF 每行少算 1，且**逐行累积** | `tocOffsets` | `crlf-doc` / `crlf-two-lines`（`lf-two-lines` 为对照） |

**两处对本文前述内容的修正：**

1. 2.3 记 Rust 的空标题回退正确，此处确认其机制：Rust 在计数**之前**注册 `"heading"`，TS 在**之后**，
   这正是 `emoji-then-literal` 只在 TS 两面失败的原因。
2. 后缀碰撞此前只在 `tocService` 名下记录；实测 **`markdown.rs` 同样中招**，
   所以它是三个活面**共有**的缺陷，不是 TS 独有。修复必须三面同改（与「三活面同提交」条款一致）。

**语料未覆盖、留给后续的**：`headingKey` 跨修订协调（第一层，输入不透明 key）与
用户行为测试（第三层：折叠→编辑→重解析、两种模式的导航目标）。本语料只覆盖第二层「语义契约测试」，
即真实 Markdown 进、slug 与位置出。**不得据此宣称三层测试已就位。**

1. **字节数几乎不要钱，行数与标题数才要。** 同为 9.96MB：超长单行（**3 行**）3.0ms，

   计划把它列为五形态之一是对的，但压力点不在 `toc` 面。
2. **峰值内存跟着行数走，不跟字节走。** 同为 9.96MB：3 行的 82MB vs 海量短行的 295MB（堆内 198MB），

   「文件能打开 ≠ 适合完整挂载成 PM DOM」的前半句在解析器上的具体形态。
3. **CRLF 没有可测的解析开销**：受控 A/B（同一文档逐字节派生，仅换行符不同，两侧各 143 标题）
   0.49ms vs 0.48ms。`crlf-doc` 钉住的是 **offset 正确性**缺陷，不是性能问题，两者不要混为一谈。

### 导出锚点被 DOMPurify 剥离（已决 B′，见 ADR-0003；WI-3.2 实施）

> **状态：已决。** 2026-09-15 产品确认采纳 **B′**，记入
> [ADR-0003](../adr/0003-export-fragment-sanitizer-scope.md)。
> 本节保留当时的判定过程作为证据；**决议与本节冲突时以 ADR-0003 为准**。
> 小节标题在同一提交内由「待决：…」改名为现名 —— 标题里挂着「待决」而问题已决，
> 比失效指针更坏（看不出坏）。按标题引用本节的三处（knip 提案 §5.6 两处、
> 门禁二手册一处）已在同一提交同步更新。

**[实测]** 语料测出的最严重一条，且**是活缺陷，不是潜在风险**：

- `markdown.rs` 正确产出 `id="title"`；
- `exportService.ts:89` 在 **Rust 成功路径**上也跑 DOMPurify（`sanitize(result.html)`）；
- DOMPurify 默认开启 `SANITIZE_DOM`，删除与内建 `document` / `form` 属性同名的 `id`
  （`title`、`name`、`body`、`location`、`forms` 等），留下 `<h1 data-heading-id="title">` 而**没有锚点**；
- `export.rs:161` 的 ammonia 二次净化拿到的已经是丢了锚点的 body，**补不回来**；
- `App.tsx:587` 是**唯一**导出入口，走 `exportRenderedHtml` → `renderMarkdown`。

⇒ 今天用户导出一篇含 `# Title` 的文档，该标题在导出的 HTML 里**没有可跳转锚点**。
ammonia 不做此剥离，所以这是一处 **TS 与 Rust 的净化语义分歧**，而非双方一致的安全姿态。
`sanitizerPolicy.ts` 既未设 `SANITIZE_DOM: false` 也未设 `SANITIZE_NAMED_PROPS`，
其文件头详述了与 Rust 的 parity 却**从未提及 clobbering** ⇒ 这是**未登记的行为**，不是已权衡的选择。

**各选项判定如下，WI-3.2 动 slug 生成之前必须定。**
判定依据 2026-09-13 的同类实现横向调研（github-slugger / rehype-slug / GitHub、vmark、MiaoYan）
与一次 Codex 评议（`codex exec -s read-only`，high reasoning），分歧处均已实测：

| 选项 | 做法 | 判定 |
|---|---|---|
| A | `SANITIZE_NAMED_PROPS: true` | **驳回**。**[实测]** 该分支无碰撞判断，**无条件**给每个 `id`/`name` 加 `user-content-` 前缀，且**从不改写 `href`**。导出件零 JS，无法像 GitHub 那样配 `hashchange` 脚本回跳裸 fragment ⇒ 脚注回链 `href="#fn1"` 与用户手写 `[x](#slug)` 全部指向不存在的目标。把「少数碰撞锚点失效」升级成「文档内导航全废」 |
| A′ | A + 重写全部内部引用 | 保住 clobbering 防护，但需连 SVG `url(#…)`（`fill`/`stroke`/marker）一并改写，且改变公开 fragment ABI。工作量大于 B′，锚点兼容性反而更差 |
| B′ | `SANITIZE_DOM: false`，**并**把 `sanitizeRenderedHtml` 更名为 `sanitizeExportFragment` | **已采纳（ADR-0003，2026-09-15）**，理由见下 |
| C | 导出改走 Rust 独有的 `export_html` | **不是平替**：丢掉 JS 后处理链（语法高亮、图片宽度标记、KaTeX 预渲染）；且与 knip 提案 §5.6 相互牵制 |
| D | slug 生成加固定前缀 | **驳回**。破坏全部既有外链；偏离 github-slugger 的通行 slug（用户粘到别处就对不上）；且这正是 Gitea 做过、又在用户投诉「分享链接很丑」后退回的方案 |
| E1 | 导出链路整个去掉 DOMPurify，只靠 ammonia | **驳回**。**[实测]** IPC 命令 `commands/export.rs:19 render_markdown` **不做服务端净化**，ammonia 要到 `export.rs:158` 才首次运行。去掉 DOMPurify 等于让**未净化**的渲染输出先被浏览器解析器接触 |
| E2 | sanitize 之后由 `data-heading-id` 回填 `id` | 可行但次于 B′：`data-heading-id` 在 `ALLOWED_ATTR` 内，对**原始 HTML 标题**属**攻击者可控** ⇒ 等于用不可信旁路撤销 DOMPurify 的决定；且只修标题，修不了其它 fragment 目标 |

**推荐 B′，理由：**

- **`SANITIZE_DOM` 在本仓当前架构里没有防住任何东西。** 导出件零 JS
  （`html_template.rs` 不输出 `<script>`）；进程内 `renderMarkdown()` 只有
  `exportService.ts:129` 一个生产调用方，这份 HTML **从不进入 app 的活动 DOM**。
  DOM clobbering 要求元素**在 document 树内**才会成为具名属性，
  `mathRender.ts:134` 的游离 div 不满足该条件。
- **真正的控制项是改名，不是那个开关。** B 的风险在于 `sanitizeRenderedHtml`
  这个泛化名字会被后来的调用方当通用净化器复用。改名为 `sanitizeExportFragment`，
  并在类型、文档与测试里写明**「输出仅供导出，禁止进入 app DOM」**，
  才是把威胁模型显式化 —— 这一条是 B′ 区别于 B 的全部价值。
- **其余 DOMPurify 限制全部保留**（`ALLOWED_TAGS` / `ALLOWED_ATTR` /
  `ALLOWED_URI_REGEXP` / `FORBID_TAGS`），`export.rs:158` 的 ammonia 仍是权威边界。

**两条必须同时登记的限制（否则 B′ 的安全论证不成立）：**

1. **游离 ≠ 无副作用。** 游离子树与 `DOMParser` 文档**都仍会发起 `<img>` / `<iframe>`
   资源加载**；拦这类加载的是 URL 与标签白名单，不是 `SANITIZE_DOM`。
   此前把两个 `DOMParser` 后处理器称作「inert」是过强的说法，已撤回。
2. **游离 `<form>` 可凭 form 所有权（而非入树）触发具名属性 clobbering。**
   当前 `sanitizerPolicy.ts:70` 把 `<form>` 排除在白名单外，故不可达 ——
   但这是 B′ 安全性的**前提条件**，一旦 `<form>` 进入白名单必须重新评估本决议。

**与 slug 去重是两个独立缺陷**：A–E2 无论选哪个都修不了 `suffix-collision`
（`# x` / `# x` / `# x-1` → `x`, `x-1`, `x-1`，重复 id）。该缺陷的修法见下。

**slug 去重的修法（已定，并入 WI-3.2）：** 三个生成器
（`markdown.rs:23`、`exportService.ts:47`、`tocService.ts:101`）统一改为占位检查循环 ——
`归一化 → 空则回退 "heading" → while 候选被占用则递增后缀 → 登记候选`。
**空值回退必须发生在占用登记之前**，否则 emoji 与字面 `# heading` 的碰撞依旧。
该形状在 github-slugger、vmark、MiaoYan 三个互不相关的实现中独立收敛，不是风格偏好。
回归门禁除 `x/x/x-1`、emoji+字面、双 emoji 三条具体用例外，
还应断言不变量 `new Set(ids).size === ids.length` ——
横向调研未发现任何知名项目断言过该不变量，这是本仓可以做得更严的地方。

### 过渡期必须登记的事实

TOC 提前统一后，**导出仍是旧语义**。该中间状态及其已知差异必须登记进阶段 0 的语法矩阵，
