## Problem Statement

The settings dialog has 8 nav items but only 3 real pages (General, Integrations, Keyboard
Shortcuts). The other 5 show placeholder cards with fake labels. The General page surfaces
developer-only logging controls (Enable Logging, Log Level) to every user. The "Reset to
Defaults" button in the global footer only resets keyboard shortcuts — a silent lie. The
sidebar has a redundant "Settings" title heading and no icons.

The target user is a daily Markdown writer who compares mdpro to Typora. Right now, the
settings panel is the one place where that comparison hurts most.

## What Makes This Cool

The first open-source macOS Markdown editor where every settings nav item leads to real,
usable settings. No placeholder cards. Visual settings (font size, line height, content
width) apply instantly — no Save button required for those. Feels native.

## Constraints

- Tauri 2.0 + React 19 + TypeScript strict mode
- Settings persisted via existing `get_preferences` / `save_preferences` Tauri commands
- Existing `UserPreferences` struct in `src-tauri/src/models/preferences.rs`
- CodeMirror 6 source mode (`src/components/Editor/extensions/`)
- Milkdown 7.18 WYSIWYG mode (`useMilkdown.ts`)
- Zustand stores in `src/stores/`
- File size rule: every file under 300 lines

## Premises

1. **Editor, Markdown, Appearance are the priority pages.** Image and Export get minimal
   but real settings (2-3 each) by surfacing existing fields. No placeholder cards anywhere.

2. **Logging controls are developer-only.** Move to a new "Advanced" page. General becomes
   clean: Default View Mode + Autosave. Users who need logging find it in Advanced.

3. **"Reset Shortcuts" button moves to the Keyboard Shortcuts page header only.**
   Global footer "Reset to Defaults" is removed. No ambiguity about what resets what.

## Architecture

### State: use `preferencesService` directly, not a new store

No new Zustand store needed. The existing pattern — call `preferencesService.getPreferences()`
on open, hold local state in the component, call `preferencesService.setPreferences()` on
change — is sufficient. **Use `setPreferences`, not `savePreferences` — the latter does not
exist.** The key change is that for non-shortcut settings, save fires immediately on each
change (not only on explicit Save click).

For the shell component, `SettingsDialogProps` simplifies to:
```typescript
interface SettingsDialogProps {
  open: boolean;
  onClose: () => void;
}
```
All preference data is loaded from the IPC layer on open. The current prop-drilling
(`shortcuts`, `defaultViewMode`, `mcpConfig`, `onSave`, `onDefaultViewModeChange`,
`onMcpConfigChange`) is removed — each page component loads and saves its own slice.

### Instant-apply pattern (write-through, no rollback)

For all non-shortcut settings:
1. User changes a value in the UI
2. Local component state updates immediately (live preview)
3. `save_preferences` fires synchronously on the same tick (not debounced)
4. CSS variables are updated on `:root` for visual settings

**No Cancel/rollback.** Write-through means changes are permanent on interaction.
The `[Close]` button in the footer does not undo anything. The "Reset Shortcuts" button
on the Keyboard Shortcuts page is the only explicit undo mechanism in the panel.

This avoids the stale-write race that debouncing creates: since each page component holds
and saves only its own slice of preferences (not the full struct), there is no overwrite
risk between concurrent saves from different pages.

**Implementation pattern per page:**
```typescript
// Example: EditorSettings page component
// Module-level ref holds the last-known full prefs — avoids IPC read-modify-write race
const cachedFullPrefs = { current: null as UserPreferences | null };

const [prefs, setPrefs] = useState<EditorPrefsSlice | null>(null);

useEffect(() => {
  preferencesService.getPreferences().then(p => {
    cachedFullPrefs.current = p;
    setPrefs(extractEditorSlice(p));
  });
}, []);

const handleChange = (key: keyof EditorPrefsSlice, value: unknown) => {
  const next = { ...prefs, [key]: value };
  setPrefs(next);
  applyEditorPref(key, value);   // update CSS var or CM Compartment immediately
  // Merge into cached full prefs — no IPC round-trip, no stale-write race
  if (cachedFullPrefs.current) {
    cachedFullPrefs.current = { ...cachedFullPrefs.current, editor: next };
    void preferencesService.setPreferences(cachedFullPrefs.current);
  }
};
```

`cachedFullPrefs` is populated once on open and updated in-place on each change.
No IPC read-modify-write cycle — no race condition even with rapid sequential changes.

**`applyEditorPref` — defined in `src/components/common/settings/editorPrefApply.ts`:**
```typescript
// Applies a preference value either as a CSS variable or a CodeMirror Compartment dispatch
export function applyEditorPref(key: keyof EditorPrefsSlice, value: unknown): void {
  const root = document.documentElement;
  switch (key) {
    case 'fontSize':
      root.style.setProperty('--editor-font-size', `${value}px`); break;
    case 'lineHeightX10':
      root.style.setProperty('--editor-line-height', String((value as number) / 10)); break;
    case 'contentWidth':
      root.style.setProperty('--editor-content-width', contentWidthToCss(value as ContentWidth)); break;
    case 'fontFamily':
      root.style.setProperty('--editor-font-family', fontFamilyToCss(value as string)); break;
    case 'tabSize':
      getEditorView()?.dispatch({ effects: tabSizeCompartment.reconfigure(indentUnit.of(' '.repeat(value as number))) }); break;
    case 'wordWrap':
      getEditorView()?.dispatch({ effects: wordWrapCompartment.reconfigure(value ? lineWrapping() : []) }); break;
  }
}
```

`getEditorView()` reads the current `EditorView` from `editorStore.getState().view`.
CSS-only changes (font, line height, content width, font family) need no CM access.

### CSS variables (NEW — must be created in step 0)

These variables do not yet exist in `globals.css`. They need to be added AND all existing
hardcoded values in the editor layout rules need to reference them:

```css
:root {
  --editor-font-family: -apple-system, BlinkMacSystemFont, "Segoe UI", sans-serif;
  --editor-font-size: 16px;
  --editor-line-height: 1.6;

```

container CSS rules. This audit is required before instant-apply wiring can work.

### CodeMirror dynamic reconfiguration (Compartment pattern)

For settings that change CodeMirror behavior (word wrap, tab size, auto-pair, code theme),
use a `Compartment` to hot-swap extensions without destroying/recreating the editor:

```typescript
// src/components/Editor/extensions/dynamicExtensions.ts
import { Compartment } from "@codemirror/state";

export const wordWrapCompartment = new Compartment();
export const tabSizeCompartment = new Compartment();
export const closeBracketsCompartment = new Compartment();
export const codeThemeCompartment = new Compartment();
```

On preference change, dispatch a `wordWrapCompartment.reconfigure(lineWrapping())` to
the EditorView. This is the established CodeMirror pattern for live settings changes.

**Code theme:** Add `@codemirror/theme-one-dark` as a new dependency (it's the only
external theme needed for v1). `CodeTheme.Default` uses `defaultHighlightStyle` (already
in `syntax.ts`). `CodeTheme.OneDark` uses `oneDark` from `@codemirror/theme-one-dark`.
`CodeTheme.Solarized` is deferred — it requires a new package and is lower priority.

While `getPreferences()` is in-flight, render controls with `disabled` attribute and
`opacity: 0.5`. Remove disabled state when prefs resolve. No spinner needed — local
IPC is ~50ms. Add `aria-busy="true"` to the `.settings-main` container during load.

### Decision D6 — Dialog opens on General page always
`SettingsDialog` initializes `activePage` to `"general"`. No persistence of last active
page. Simple, predictable. The `initialPage` prop is not added.

### Decision D7 — Font size stepper: [−] display [+] buttons
Font size on the Editor page uses a custom stepper component (not `<input type="number">`):
```tsx
<div className="settings-stepper" role="group" aria-label="Font size">
  <button onClick={() => decrement()} disabled={value <= 12} aria-label="Decrease">−</button>
  <span>{value}px</span>
  <button onClick={() => increment()} disabled={value >= 24} aria-label="Increase">+</button>
</div>
```
Keyboard: `ArrowLeft`/`ArrowDown` decrements, `ArrowRight`/`ArrowUp` increments when
the group is focused. Range: 12–24px. The 150ms debounce from Decision 5A applies to
**all** font size changes — both button clicks and keyboard events. This prevents an IPC
call storm when the user holds an arrow key (macOS fires ~15 keydown repeats/sec). Use a
single shared `useMemo(debounce(..., 150))` that is called by both the click handlers and
the `onKeyDown` handler.

### Decision D8 — Dirty shortcuts guard: inline amber banner
When `KeyboardShortcutsSettings` detects `localShortcuts !== savedShortcuts`, show an
amber banner at the top of the page content (above the shortcuts table).
**Implementation note:** The `!==` reference comparison works correctly because both
`localShortcuts` and `savedShortcuts` are initialized from the same `prefs.shortcuts`
object reference on mount. They remain `===` until the user edits a shortcut, at which
point `setLocalShortcuts({...localShortcuts, [key]: newValue})` creates a new object.
Add a code comment in the component: `// isDirty uses reference equality — both refs must
be initialized from the same object on mount. Do not spread on load.`
```tsx
{isDirty && (
  <div className="settings-dirty-banner" role="alert">
    <span>⚠️ Unsaved shortcut changes</span>
    <button onClick={handleDiscard}>Discard</button>
    <button onClick={handleStay}>Stay</button>
  </div>
)}
```
Clicking any sidebar nav item while `isDirty` is true is blocked — the click handler
checks `isDirty` and returns early without navigating, letting the banner prompt the user.
`aria-hidden="true"` on the ⚠️ emoji; add `role="alert"` so screen readers announce it.

### Decision D9 — Dialog accessibility baseline
The settings dialog `<dialog>` (or equivalent overlay) must include:
- `role="dialog"` + `aria-labelledby="settings-dialog-title"` where `settings-dialog-title`
  is the `<h2>Settings</h2>` in the dialog header
- Focus trap: when dialog opens, focus moves to the first nav item. Tab cycles within
  the dialog only. Esc closes the dialog — **unless shortcuts are dirty**: when
  `activePage === "keyboard-shortcuts"` and `isDirty` is true, Esc is intercepted and
  triggers the amber dirty banner instead of closing. Any other page: Esc closes normally.
  Implement via `onKeyDown` on the dialog container that checks both conditions.
- When user clicks a sidebar nav item, focus moves to the page's first interactive control.
  Use `useEffect` + `ref.current?.focus()` on `activePage` change.
