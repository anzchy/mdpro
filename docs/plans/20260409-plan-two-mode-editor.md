## Problem Statement

mdpro currently has 4 view modes: split, editor-only, preview-only, wysiwyg. The mode
taxonomy is too many choices. Users pay cognitive overhead deciding which mode to be in,
and the split/preview-only modes are redundant once WYSIWYG does the same job. The goal
is to collapse to 2 modes (WYSIWYG + Source) and add Typora-style inline source reveal
for specific constructs inside WYSIWYG — so users rarely need to switch modes at all.

## What Makes This Different

The key insight: mode switching should be the exception, not the flow. When cursor enters
a link or inline code element in WYSIWYG, the source syntax reveals inline. Move cursor
away, it renders again. Source mode exists as a persistent escape hatch for structural
edits, not a parallel reading surface.

## Constraints

- Tauri 2.0, Milkdown 7 (ProseMirror), CodeMirror 6
- Keep backward compat on `lastViewMode` preference (migrate split → wysiwyg, preview-only → wysiwyg, editor-only → source)
- Keyboard shortcuts must stay in sync across 3 files (menu.rs, preferences.ts, keyboard-shortcuts.md) per rule 41
- File watcher opens from Finder/drag-drop → default to wysiwyg (currently preview-only, changes behavior)

## Key Discovery

`src/plugins/milkdown/inlineEditPlugin.ts` exists and implements cursor-triggered inline
reveal via ProseMirror decorations for links (`[text](url)`) and inline code (backticks).
The CSS uses design tokens. `pluginRegistry.getMilkdownPlugins()` exists in
`src/plugins/core/pluginRegistry.ts` (line 287) to serve Milkdown plugins from the
registry.

**Critical bug: the plugin is never wired into the editor.**
`MilkdownEditor.tsx` (lines 148-160) builds the editor manually with explicit `.use()`
calls. `inlineEditMilkdownPlugin` is registered in `src/plugins/index.ts` via
`pluginRegistry.register(inlineEditPlugin)` but `getMilkdownPlugins()` is never called
in `MilkdownEditor.tsx`, and `inlineEditMilkdownPlugin` is not in the `.use()` chain.
The decoration plugin is dead code from the perspective of the running editor.

Fix (XS — one import + one `.use()` call):
```typescript
// MilkdownEditor.tsx — add import
import { inlineEditMilkdownPlugin } from "../../plugins/milkdown/inlineEditPlugin";
// add to Editor.make() chain
.use(inlineEditMilkdownPlugin)
```

**Gap 1:** Link URL is shown via CSS `::after { content: "](" attr(data-href) ")" }`.
Visible but NOT editable. Text portion of link IS editable (lives in ProseMirror doc).
To make the URL editable inline, need a widget decoration — a real `<input>` element.
This is separate from the wiring fix above.

**Gap 2:** No keyboard shortcut to force-reveal current element. Plugin is cursor-only.
User confirmed: want both cursor-triggered AND shortcut-triggered.

**Gap 3:** `ViewMode = "split" | "editor-only" | "preview-only" | "wysiwyg"` — the type
and all its routing still has 4 variants. These need to be cut from type, routing, menu,
preferences, docs, and stores.

## Premises (all agreed)

1. Split view is redundant when inline source reveal handles the specific-element case.
2. Preview-only is redundant when WYSIWYG is already the reading experience.
3. Source mode stays as a persistent mode (not a popup/overlay) — structural edits need it.
4. Inline source reveal triggers on cursor position + keyboard shortcut (both).

## Approaches Considered

### Approach A: Ship now — cut modes only (S effort)
Cut Split and Preview-Only. Two modes, both existing. No new inline work. Ships in hours.
Cons: Editing a link URL in WYSIWYG still requires switching to Source mode. Incomplete.

### Approach B: Full Typora-parity (chosen — S/M effort)
Cut modes + add link URL editability + keyboard shortcut for reveal. The complete vision.
Since inlineEditPlugin already exists, the remaining work is well-scoped.

### Approach C: WYSIWYG-first, Source hidden (M effort)
Same as B technically, but Source mode is demoted to shortcut-only (no visible toggle).
Discarded: accessibility concern — users who need Source must know the shortcut exists.

## Recommended Approach: B — Full Typora-parity

**WI-2: Update menu + keyboard shortcuts (S, rule 41 sync required)**

- `src-tauri/src/menu.rs`: remove ⌃1 (Split) and ⌃3 (Preview Only) menu items.
  Keep ⌃2 → Source, ⌃4 → WYSIWYG. Or renumber: ⌃1 → WYSIWYG, ⌃2 → Source.
- `src/types/preferences.ts` DEFAULT_KEYBOARD_SHORTCUTS: update to match
- `docs/guide/keyboard-shortcuts.md`: update registered shortcuts table
- `docs/guide/view-modes.md`: rewrite for 2-mode model

**WI-3: Wire inlineEditPlugin into the editor + URL editability (S+M)**

Step 3a (XS): Wire the plugin. Add to `MilkdownEditor.tsx`:
```typescript
import { inlineEditMilkdownPlugin } from "../../plugins/milkdown/inlineEditPlugin";
// in Editor.make() chain:
.use(inlineEditMilkdownPlugin)
```
After this, link reveal and inline code reveal should work. Verify by placing cursor
in a link in WYSIWYG mode — `[text](url)` should appear. If not, debug CSS specificity.

Step 3b (M): Link URL editability. Current state: URL shown via `::after` CSS — read-only.

To fix: When cursor is inside a link mark, add a ProseMirror **widget decoration**
(not inline decoration) that renders after the link text as:
```
[text](|editable input for href|)
```
The widget is a real `<input>` element. On change, dispatch a transaction that updates
`mark.attrs.href`. On blur, destroy the widget.

Implementation path:
- Extend `createDecorations()` in `inlineEditPlugin.ts`
- Add `Decoration.widget(to, dom => { ... })` where `dom` is an `<input>` pre-filled
  with `mark.attrs.href`
- Wire `input.oninput` → `view.dispatch(tr.removeMark(...).addMark(..., {href: input.value}))`
- CSS: style the widget to look like the `::after` pseudo-element (muted color, monospace)

Alternative if widget proves flaky: use a floating tooltip (absolutely positioned)
anchored to the link range. Simpler DOM, same UX.

**WI-4: Keyboard shortcut for force-reveal (S)**

Add a ProseMirror keymap to `inlineEditPlugin.ts`:
- Shortcut: `⌘E` (matches Typora; check for conflicts in menu.rs first)
  or `⌃\`` as an alternative
- Action: if cursor is inside a link/code mark AND decoration not yet showing → force
  show it (the current plugin already shows it automatically, so this shortcut mainly
  serves mouse users who clicked without typing)
- Actually: the cursor-triggered reveal already fires on any cursor movement. The
  shortcut use case is "I clicked on a link and want to edit the URL without moving
  the cursor." Wire the shortcut to dispatch a no-op transaction that forces a
  selection update → triggers the decoration re-evaluation.

Note: Check `menu.rs` for `⌘E` — currently used for Export HTML. Use `⌃\`` instead.

**WI-5: Finder/drag-drop open behavior (XS)**

Currently `setViewMode("preview-only")` when opening from Finder. Change to
`setViewMode("wysiwyg")`. One-line change in the file open handler.

## Open Questions

1. **Shortcut renaming**: ⌃1 and ⌃3 will be freed up. Assign to something, or
   just remove? (Freeing shortcuts mid-product is fine — just update the 3 files.)
2. **Inline reveal for images**: `![alt](url)` is a block node, not a mark. The
   existing inlineEditPlugin won't handle it. Out of scope for this design — noted
   for future.
3. **Fenced code block fence markers**: The CodeMirror NodeView hides the ` ```lang ```
   ` markers. Should they be revealed when cursor enters? Currently: no. They're implied
   by the code block UI. Probably fine to leave as-is.
4. **ViewMode naming in preferences file**: `"editor-only"` → `"source"` is a stored
   preference key change. Needs a one-time migration on preferences load — any stored
   `"editor-only"` value must be read as `"source"`.

## Success Criteria

- `ViewMode` type has exactly 2 values: `"wysiwyg"` | `"source"`
- Navigating to a link in WYSIWYG reveals `[text](url)` with URL editable in-place
- Moving cursor away from link restores rendered link styling
- Inline code in WYSIWYG shows backtick decorations on cursor enter
- Keyboard shortcut (⌃\` or similar) force-reveals current element
- `pnpm check:all` and `cargo test` pass
- `menu.rs`, `preferences.ts`, and `keyboard-shortcuts.md` are in sync
