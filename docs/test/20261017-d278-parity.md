# D278 parity, layer 2: one browser run (evidence, not a gate)

**Date:** 2026-10-17. **Master:** `467326c3` (the branch's parent). **Head:**
`0eb8b3de` (WI-3, the last code commit; `src/styles` is the same tree in
every later commit on the branch). **Browser:** HeadlessChrome
145.0.7632.6 through gstack `/browse`.

Layer 1, `tests/d278-parity-values.test.ts`, is the parity gate (user ruling
through the delegator, 2026-10-17: 「Demote browser check (Recommended)」).
No test, lane or gate reads this record or its JSON. A difference found here
goes to the delegator, and layer 1 gets a row for it.

## Result

Normalised to 8-bit `rgba()`, master and head differ in **exactly the two
rows the plan expected** in each of the three frames (`root` = first paint,
no theme class; `light`; `dark`):

- `.settings-placeholder-card` background → `rgba(0, 0, 0, 0)`: the rule is
  deleted; the class renders nowhere in the app.
- `.tab--active` box-shadow → `--shadow-soft`: TabBar is imported nowhere,
  so this is not rendered in the app.

Every other row (the running badge, toggle off and on, its knob, the unsaved
banner fill and border, the group and input fills on all six of their
selectors, `.shortcut-value.is-editing`, the placeholders, the danger-soft
error fill, the progress value, and the `:hover` / `:focus-visible` states)
is equal in all three frames.

## How it was run

- **Page:** `scripts/design/d278-parity.html`, which loads
  `src/styles/index.css` only. One element per row, with the states set in
  markup (`:checked`, `.is-editing`) or by the driver: `:hover` by pointer;
  `:focus-visible` by focusing the anchor just before the element and
  pressing Tab. Each read checks `el.matches(state)` first and would record
  `NOT_REACHED` if the state was not reached. None was.
- **Trees:** each side's `src/styles` was taken by `git archive <sha>
  src/styles` into a scratch directory, with the page copied in, and served
  by `python3 -m http.server` (master on 8762, head on 8761). This departs
  from the plan in two ways. It uses neither `pnpm dev` (Vite's port 1420
  is strict and shared between sessions) nor a `verify-<sha7>` worktree
  (only the stylesheets are needed). The app has no PostCSS step, and
  `index.css` is plain `@import`s, so the browser applies the same cascade
  as under Vite.
- **Progress bar:** `::-webkit-progress-value` cannot be read with
  `getComputedStyle` (recorded `NOT_SUPPORTED`). It is read instead from the
  centre pixel of an element screenshot of a full bar (`value="1"`):
  `scripts/design/d278-parity-compare.mjs pixel`.
- **Reduced motion:** `/browse` cannot emulate `prefers-reduced-motion`.
  So the run reads the `@media (prefers-reduced-motion: reduce)` block's
  `--motion-duration-fast` through the CSSOM: `0ms` on `:root`, on both
  sides. The knob's computed `transition-duration` (`0.15s`, the
  no-preference value) is equal on both sides.
- **Raw output:** `20261017-d278-parity/master.json` and `head.json`.
  `node scripts/design/d278-parity-compare.mjs diff <master.json>
  <head.json>` prints the table below. Its exit code is always 0.

## What it does not prove

- **Sheet set.** Only `index.css` is loaded. The seven module-loaded sheets
  are absent: BottomTabs.css, MilkdownEditor.css, ImageContextMenu.css,
  wysiwygDecorationsPlugin.css, imagePastePlugin.css, inlineEditPlugin.css
  and linkDefinitions.css. Their cascade order is not reproduced either.
  They are not expected to touch Settings controls, but this run does not
  show it.
- **Alpha on the progress bar.** That row is a composited pixel, which
  cannot show alpha.
- **Engine.** Chromium only. The app runs in WebKit (WKWebView), which was
  not run. `:hover` and `:focus-visible` are as Chromium's driver reached
  them.
- **Layout and the app's DOM.** The elements are bare and outside their
  real parents. Selectors that need an ancestor would not match here. None
  of the rows above does.
- **Reduced motion, rendered.** It was read from the CSSOM, not emulated.
