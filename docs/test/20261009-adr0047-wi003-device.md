**结论**：WI-R3 的修复在真机上成立。`--via open` 把文件送进了活着的运行（开了新窗口），没有留下第二个进程，没动 `instance.json`；文件没送到时结论是 `fail`，不是假的 `pass`。

**偏离与说明**：

- **D2 没走到 app**：日志一行没长，连 `not_markdown` 的过滤行都没有。看来 Launch Services 根本没把 `c.txt` 交给 `mdpro-verify`，也没交给别的 app。D2 测的仍是本意的路径：启动器等满了时限，然后报没送到。
- **pnpm 在失败的结论之后多打一行** ` ELIFECYCLE  Command failed with exit code 1.`。启动器自己输出的最后一行仍是结论，这一行是 pnpm 包装器加的，不是启动器的缺陷。读结论的脚本要取启动器的最后一行，不能直接取整段输出的最后一行。
- **C 的第二个进程**在交出参数之前，会往运行自己的日志里写一行 `app.launch` start。这是预期行为，不影响结果。
- **`doctor` 的提示行**：`outside run dir: /tmp/com_mdpro_app_verify_si.sock`，以及 WebKit 和 Caches 的落点「measured on macOS 26.3.1」，这台机器是 26.4。两行都只是信息。

## 4. 没测到的（仍开着）

- **评审 M2**：`--into --via open` 不带 `-n`，Launch Services 会把文件交给同一 bundle id 的任一进程。只有另一份验证包能抢（日常 mdpro 的 id 不同）。抢走时运行自己的日志里不会出现送达行，所以结论是 `fail`，不会假通过。这一点没在真机上测，因为测它要同时开两份验证包；复测时 `pgrep` 只看到一个验证进程。
- **日常 mdpro 开着时的 D**：复测时日常 app 没开，所以 `b.md` 不可能被它收走，但「开着时也不收」这一点这次没观察。
- 评审的其他跟进项（`.claude/tdd-guardian/review-20261009-wi-r3.md`）都是测试或代码层面的，真机测不到，仍开着：M1 慢测桩只走「原样路径」分支，真实路径分支没有真进程覆盖；L4 未规范化的路径（`/a//b.md`、经符号链接的 `..`）可能误判失败；L6 日志里的 `source` 未过滤就打印；L9 测试注释重复七次；L10 放宽后的快照不再检查应用日志只追加；缺的测试是「退出与送达都贴着共同时限」和「`--via open` 带相对路径」。更早的 Low（锁与建目录之间的窗口、`clean` 最后一步失败要手动 `rmdir` 等）见计划 § WI-003 原状态。
