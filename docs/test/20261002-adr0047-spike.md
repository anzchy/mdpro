## How a cell is filled

Each cell holds three things: a result, an evidence class, and where the
evidence is.

| Result | Meaning |
|---|---|
| `pass` | The criterion was met, and the evidence is cited |
| `fail` | The criterion was not met. The candidate stops at this screen |
| `not run` | The candidate stopped earlier, or the time box ended |
| `n/a` | The criterion does not apply to this transport. The reason is stated |

| Evidence class | What it is |
|---|---|
| `physical` | A person pressed the key or clicked. Only this class settles keyboard behaviour in a dialog (`progress.md`, 2026-09-30) |
| `driver input` | Input sent by the candidate. It never counts as `physical` |
| `remote key` | A person's keypress made on another computer and relayed by remote-desktop software (UU Remote), which injects it as a native event. The page sees `trusted:true`, and the event takes the native route from the window server to the key window. It is not `physical`: no key on the device was pressed (`progress.md`, 2026-09-30). Accepted for the S2 control (adr047-verify ruling, 2026-10-16); the upgrade to `physical` with a local keyboard was deferred by the user (「defer」) |
| `log` | A byte-offset slice of the run's `mdpro.log` |
| `disk` | A file in the run directory, compared with the expected content |
| `source` | A `path:line` in the pinned crate or in this repo |
| `artefact` | A build manifest, a dependency graph, a listener inventory |

A screen passes only when every row in it passes. There is no "mostly works".

- **Why it failed.** This is the risk ADR-0100 names. `ConfirmDialog` puts
  initial focus on Keep editing by script, inside the card, so on the reverted
  build the card's own `onKeyDown` takes the Esc too. Initial focus inside the
  card is not new: before `c39dfb1` the confirm button had `autoFocus`
  (`git show c39dfb12^:src/components/common/ConfirmDialog.tsx`). D34 was an
  Esc with focus **outside** the card, as the reproducers CD-1 and CD-2 put it
  (`<body>`, an outside textbox). This protocol never reaches that state.
- **The paths still differ.** The reverted build logs one line, the head build
  both. That tells which listener ran; it does not make the control hold,
  because the outcome is what S2 compares.
- **D34 holds on the baseline head**: one Esc from the user (`remote key`) closes the dialog
  through `useDialogEscape`.
- **How the window came back.** It lost focus while the user read the chat.
  Before each Esc the user brought it forward by clicking its **Dock icon**
  (「两次都是点 Dock 图标」), the same on both builds and on the production
  sample. A Dock click activates the app and sends no event into the page; DOM
  focus stayed where the script put it. It is recorded as an app activation,
  not as "clicked or focused first".
- **The Esc presses came through UU Remote.** The mini has no keyboard
  connected. The user pressed Esc on their own computer, and UURemoteServer
  injected it on the mini. Asked whether that was so for P1 and P3, the user
  answered 「是的」 (relayed by mdpro-delegator). So these rows, and comparison
  two's J5 step 3, are `remote key`, not `physical`.
- The baseline head was run after the stop on the user's word, as a D34
  record. Under ADR-0113 it is not the control (its focus was inside the
  card). S2.1–S2.3 were not run.
