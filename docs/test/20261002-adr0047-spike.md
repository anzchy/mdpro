## How a cell is filled

Each cell holds three things: a result, an evidence class, and where the
evidence is.

| Result | Meaning |
|---|---|
| `pass` | The criterion was met, and the evidence is cited |
| `fail` | The criterion was not met. The candidate stops at this screen |
| `not run` | The candidate stopped earlier, or the time box ended |
| `n/a` | The criterion does not apply to this transport. The reason is stated |

| Evidence class | What it is |
|---|---|
| `physical` | A person pressed the key or clicked. Only this class settles keyboard behaviour in a dialog (`progress.md`, 2026-09-30) |
| `driver input` | Input sent by the candidate. It never counts as `physical` |
| `remote key` | A person's keypress made on another computer and relayed by remote-desktop software (UU Remote), which injects it as a native event. The page sees `trusted:true`; the record does not show how the relay injects the key, and `trusted` does not mean it came from hardware. It is not `physical`: no key on the device was pressed (`progress.md`, 2026-09-30). Accepted for the S2 control (adr047-verify ruling, 2026-10-16); the upgrade to `physical` with a local keyboard was deferred by the user (「defer」). Admitted in place of `physical` for the S2 control under ADR-0113 and both candidates' S2.1 only, by [ADR-0117](../adr/0117-a-relayed-remote-key-stands-for-the-physical-esc-in-the-spikes-s2-runs.md) (Proposed) |
| `log` | A byte-offset slice of the run's `mdpro.log` |
| `disk` | A file in the run directory, compared with the expected content |
| `source` | A `path:line` in the pinned crate or in this repo |
| `artefact` | A build manifest, a dependency graph, a listener inventory |

A screen passes only when every row in it passes. There is no "mostly works".

reverted build and closes it on the head build. If it closes on both, S2 is
void and the spike stops until the control is redesigned. For the control

runs keep the class `remote key`. Every later S2 run needs a physical Esc.

Evidence: mini `~/.mdpro-redesign/dtrack/reports/20261016-wi005-baseline.md`

- **Why it failed.** This is the risk ADR-0100 names. `ConfirmDialog` puts
  initial focus on Keep editing by script, inside the card, so on the reverted
  build the card's own `onKeyDown` takes the Esc too. Initial focus inside the
  card is not new: before `c39dfb1` the confirm button had `autoFocus`
  (`git show c39dfb12^:src/components/common/ConfirmDialog.tsx`). D34 was an
  Esc with focus **outside** the card, as the reproducers CD-1 and CD-2 put it
  (`<body>`, an outside textbox). This protocol never reaches that state.
- **The paths still differ.** The reverted build logs one line, the head build
  both. That tells which listener ran; it does not make the control hold,
  because the outcome is what S2 compares.
- **D34 holds on the baseline head**: one Esc from the user (`remote key`) closes the dialog
  through `useDialogEscape`.
- **How the window came back.** It lost focus while the user read the chat.
  Before each Esc the user brought it forward by clicking its **Dock icon**
  (「两次都是点 Dock 图标」), the same on both builds and on the production
  sample. A Dock click activates the app and sends no event into the page; DOM
  focus stayed where the script put it. It is recorded as an app activation,
  not as "clicked or focused first".
- **The Esc presses came through UU Remote.** The mini has no keyboard
  connected. The user pressed Esc on their own computer, and UURemoteServer
  injected it on the mini. Asked whether that was so for P1 and P3, the user
  answered 「是的」 (relayed by mdpro-delegator). So these rows, and comparison
  two's J5 step 3, are `remote key`, not `physical`.
- The baseline head was run after the stop on the user's word, as a D34
  record. Under ADR-0113 it is not the control (its focus was inside the
  card). S2.1–S2.3 were not run.

**Two contracts neither spike met.** The recorded S1 passes stand, but they are not full compliance, and the
implementation built next (WI-009) has to meet both before its re-verification counts:

- **No runtime opt-in (ADR-0047 decision 6).** B's plugin setup calls `open()`, which binds the socket with no check
  (`control_channel/mod.rs:106-120` in `79bde78a`). So a feature-enabled verify run opens the channel whenever it
  starts. `MDPRO_CONTROL_EVAL` gates `eval` only. S1's feature-off case did not test "feature on, opt-in absent".
  Candidate A's adapter has the same gap.
- **At-most-once is bounded.** B remembers the last 1,024 mutating ids (`proto.rs:18-19`; A's cache holds 4,096).
  After that many later mutations, an old id runs again. S1.4 tested immediate duplicates only, not eviction.

**What choosing B costs** (the record of what the selection gives up):

- **864 is every changed line, not the interop alone, and not a ceiling.** `control_channel/` 843, `main.rs` +9 −1,
  `services/mod.rs` +4, `Cargo.toml` +7; the one deleted line is counted. The 498 lines of spike scripts are not.

- **274 lines of Objective-C interop are owned here** (`input_macos.rs`): `NSEvent` construction, a keyCode table
  for the ANSI layout, and `-[NSWindow sendEvent:]` on the main thread. Nobody upstream maintains it, and an
  AppKit or WebKit change that alters how a synthesised event is handled breaks it here first.
- **A `control-channel` build is macOS-only as written**, not a portable channel that just lacks input elsewhere:
  the module imports Unix sockets and the AppKit input module unconditionally, and the AppKit crates exist only for
  the macOS target. The keyCode table is the ANSI (ABC) layout's; the briefs check the input source, the code does
  not.
- **`type` takes printable ASCII only.** CJK and other Unicode text cannot be injected; IME stays manual.
- **B gives up A's Windows and Linux paths.** A's crate has platform implementations for both and a wider WebDriver
  interface. Neither was verified in this spike.
- **`objc2-app-kit`'s three added features (`NSEvent`, `NSGraphicsContext`, `NSWindow`) sit in the unconditional
  macOS dependency list**, not behind `control-channel`. The channel's code is gated; the features are not.
- **Release separation is designed, not verified.** The module and its registration are feature-gated, and
  `control-channel` implies `verify-run`. The four-layer clean-release check and the runtime-activation attempt on
  a release bundle (ADR-0047 decision 6) are WI-009 acceptance; the spike ran neither. A release-profile *verify*
  bundle carries the channel on purpose; a shipped release must not.
- **The driver's key is `trusted:true` in the page**, like a physical key, so the recorder's `trusted` field no longer
  tells the two apart. The evidence class comes from who sent the key, and the record has to say so on every run
  (decision 8 is unchanged: driver input never discharges the physical-key rule).
- **`activate` is part of every input step**: the app is activated and the window made key before the input, with no
  event into the page (the user's 「Allow activate, record it (Recommended)」, relayed by mdpro-delegator on
  2026-10-17). A driver step can move focus away from whatever the person was doing on that machine. It rests on
  `activateIgnoringOtherApps`, deprecated since macOS 14; its replacement `activate()` is cooperative and may not take
  focus from a terminal (the code's own comment).
- **A page command sent while the page still loads fails as `script_error`**, not `timeout`. The client waits for
  `app.ready` first.
- **The spike's scripts needed three fixes** (`48914c50`, `3b4ec320`), each in the scripts, none in the channel: an
  empty id swapped for a generated one, an eval sent before the page loaded, and a selector naming the Settings
  footer that D260 removed. Selectors written against today's markup age with it.
- **Compared with A**, B gives up an upstream crate others maintain (and its WebDriver API) for input that reaches
  the page as native events. The counts measure different things: A's 232 lines are its upstream patch against a
  400-line budget, and A also needed about 113 lines on mdpro's side (`control_channel.rs` +96 −10, `main.rs` +4 −1,
  `Cargo.toml` +1 −1), which its S1 row left to S6. B's 864 lines are every line it changed here.

Selection is not verification. The implementation that is built afterwards
passes S1 to S5 again, and that run has its own record.
