# ADR-0047 WI-002 真机验收记录（2026-10-07）

计划：[`docs/plans/20261002-plan-agent-control-channel.md`](../plans/20261002-plan-agent-control-channel.md) § WI-002。
执行方：主会话用 `/gui-acceptance`（computer use）驱动，Finder 双击和 5c 的 HTTP 探针由人执行（本机权限不允许会话发 localhost 请求）。

## 0. 测量条件

| 项 | 值 |
|---|---|
| 机器 | Apple Silicon，macOS 26.3.1 (a)，build 25D771280a |
| 被测构建 | `pnpm control:build --profile verify`，`src-tauri/target/verify/release/bundle/macos/mdpro-verify.app`，由 `e36c63a` 构建，工作区干净；清单 `buildId` `25de09dd…`，`features: []` |
| 日常 app | `/Applications/mdpro.app` v0.3.0（`com.mdpro.app`） |
| 运行目录 | 由临时脚本按启动器（WI-003）的约定建：父目录与运行目录 0700，`launch.json` 带随机数，四个变量都取 realpath，`HOME` = `CFFIXED_USER_HOME` = 运行目录 |
| 旁证清单 | 对真实 `~/.mdpro`、`~/Library/Application Support/mdpro` 和四个 MCP 客户端配置取 `stat` 元数据（路径、大小、mtime），不读内容 |

**测试脚手架的教训**：第一次运行预置了只含 `{"mcp":{"serverEnabled":true}}` 的 `config.json`。`UserPreferences` 有不带 `serde(default)` 的必填字段，整份解析失败，设置页全部显示 “Failed to load …”。这是脚手架错误，不是 WI-002 的缺陷；之后的运行不预置偏好，app 首启自己写全量默认值。WI-003 的启动器写偏好夹具时必须写**完整**的一份。附带观察：偏好文件损坏时 app 不回落到默认值，只在每个设置页报错（既有行为，与本 WI 无关）。

## 2. 覆写实验

| 项 | 结果 |
|---|---|
| 做法 | 同一运行里起第二个进程（旅程 J7a），运行目录和四个变量与主实例相同 |
| 观察 | 第二个进程重跑启动前守卫，把 `<RUN>/instance.json` 的 pid 从 36009 改成 36146；随后经 `/tmp/com_mdpro_app_verify_si.sock` 把参数转给主实例（主实例日志 `file.open.external`，路由 `broadcast`），自己 exit 0 |
| 结论 | **缺陷**。`instance.json` 指向一个已退出的 pid，WI-003 的 `quit` 和 `--via open` 握手会认错进程 |
| 修复 | 校验留在 `main()`，`instance.json` 改在 Tauri setup 钩子里排他发布，已存在就以 78 退出、不覆写（计划 § WI-002 偏离 13，[ADR-0058](../adr/0058-a-verify-run-publishes-its-handshake-once-and-never-replaces-it.md)）。复测时未提交，2026-10-08 已提交 |

## 3. 修复后复测（2026-10-08）

被测构建：`pnpm control:build --profile verify`，由 `4834dc8` 加**未提交**的修复构建（工作区不干净），清单 `buildId` `f562a007…`。直接执行包内二进制，四个变量由 `mkrun.sh` 给出；日常 app 没开。

| # | 情形 | 结果 |
|---|---|---|
| R1 | 首次启动 | **通过**。`instance.json` 的 pid 71622 = 子进程 pid，随机数与 `launch.json` 一致，0600；日志恰一条 `app.verify_run` success `{runDir, pid, buildId}`；stderr 0 字节 |
| R2 | 同一运行里第二个进程（J7a） | **通过**。第二个进程 exit 0；`instance.json` 的 inode、mtime、大小、权限、sha256 前后都一样；主实例存活；日志 `app.single_instance` 1 条、`file.open.external` 2 条，`app.verify_run` 仍只有 1 条，没有 fail 行；运行目录里没有临时文件 |
| R3 | 新运行目录预置垃圾 `instance.json`（0644） | **通过**。exit 78，stderr 恰为 `mdpro verify-run guard: refusing to start: instance.json already exists`；垃圾文件逐项不变；无 `.instance.json.*.tmp`，无 `server.port`；日志 `app.launch` 之后一条 `app.verify_run` fail `{pid, reason:"instance_exists", runDir}`。运行目录里出现了 `Library/`（草稿迁移已跑，计划里记的代价）。窗口是否闪现：没截图，**未观察** |
| R4 | 真实状态清单 | **通过**。R1–R3 前后逐行一致 |

**脚手架的教训**：第一次跑 R3 时，脚本在同一个 shell 里 `eval` 了 R1 的变量，`HOME` 已经是 R1 的运行目录，于是 R3 的运行目录建在了 R1 里面，守卫以 "not a direct child of the runs parent" 拒绝，测的不是发布路径；清单也读错了 `HOME`。改成每个运行在子 shell 里取变量后重跑，上表是重跑的结果。WI-003 的启动器和以后的脚本不要在父 shell 里导出 `HOME`。
