# ADR-0047 journeys, comparison rule and S2 baseline protocol (2026-10-02)

This is the WI-000 definition document for
[ADR-0047](../adr/0047-agents-verify-in-the-real-app-through-a-feature-gated-control-channel.md)
and its [plan](../plans/20261002-plan-agent-control-channel.md). It fixes three
things before any code is written:

1. the ten journeys the driver spike runs (J1a to J7b);
2. the **semantic projection**, which is the only definition of "two runs agree";
3. the protocol for S2's physical baseline.

Results go in the [spike record](./20261002-adr0047-spike.md), not here.

**Almost nothing in this document has been run.** Every control, key and log line was
read from the code at `1f2de1a` and is cited. The citations were then checked a
second time, one by one, against the tree. An expected event is a
prediction. The one exception is J1a and J5, which were run once on the
upgrade-trial bundle on 2026-10-02 (see "Observed on the trial run"). That run
corrected two predictions and is not the reference. The hand run of WI-005 (comparison one) is the reference; where it
disagrees with a prediction, this document is corrected and the hand run stands.
Lines marked *inferred* were reasoned from code and are the likeliest to be
wrong.

## What a run looks like

A journey runs inside a verification run: a fresh process of a `verify` bundle,
started by the launcher with `HOME` pointing at a new run directory. `<RUN>`
below is that directory. `<BIN>` is the bundle's `Contents/MacOS/tauri-app`.

### Step classes

Every step has one class, from plan §4.1.

| Class | Who acts |
|---|---|
| `cli` | Driver input or a probe, through the control channel |
| `launcher` | The launcher starts an external process |
| `native` | `gui-acceptance` (computer-use) or a person: native menus, panels, alerts |
| `human` | A person only: a physical key, IME, whether something painted correctly |

In a hand run (driver feature off) a person performs the `cli` steps with the
mouse and keyboard, and reads what a probe would read from the window.

A native menu step means **clicking the menu item**. Its accelerator is not
pressed. Several accelerators are also bound in the webview
(`src/hooks/useKeyboardShortcuts.ts:161-231`), and which path a physical key
takes is not known from code.

### Files

| File | Source | Used by |
|---|---|---|
| `<RUN>/adr0047-journeys.md` | A copy of [`tests/manual-fixtures/adr0047-journeys.md`](../../tests/manual-fixtures/adr0047-journeys.md) | All journeys |
| `<RUN>/adr0047-second.md` | A second copy of the same fixture, under another name | J7b |
| `<RUN>/.mdpro/config.json` | The preset below | All journeys |

The committed fixture is never opened. A run edits its copy.

### Preset preferences

```json
{
  "themeMode": "light",
  "autoSaveInterval": 5,
  "defaultViewMode": "source",
  "lastViewMode": "source",
  "showSidebar": true,
  "enableScrollSync": true,
  "recentFiles": [],
  "windowState": { "width": 1200, "height": 800, "x": 100, "y": 100, "isMaximized": false },
  "logging": { "enabled": true, "level": "debug" },
  "markdown": { "autoPair": true }
}
```

- Seven keys have no serde default: `themeMode`, `autoSaveInterval`,
  `defaultViewMode`, `showSidebar`, `enableScrollSync`, `recentFiles` and
  `windowState`. Leaving one out is a parse error, and a parse error turns
  logging off without a message
  (`src-tauri/src/models/preferences.rs:6-69`, `src-tauri/src/services/logger.rs:43-46,88-93`).
  So the launcher checks, after start, that `mdpro.log` has an `app.launch` line.
- `autoSaveInterval: 5` is the shortest the app honours (`src/hooks/useAutoSave.ts:15`).
- `logging.level: "debug"` adds `app.launch_paths_check`
  (`src/App.tsx:915`), which names the window that took the launch path.
- `mcp` is left out, so the MCP server starts as it does for a user (plan R3).
- `defaultViewMode` selects the editor. A launch-file open calls
  `setViewMode(defaultViewMode)` (`src/App.tsx:901-948`), so the mode is set
  with no key press. `⌃2` and `⌃4` exist only as native menu accelerators
  (`src-tauri/src/menu.rs:158-173`), which a driver cannot reach.

| Run | Preset `defaultViewMode` and `lastViewMode` | Journeys, in order |
|---|---|---|
| 1 | `source` | J1a, J2, J5, J4a, J4b, J6, J7a, J7b |

### Evidence per step

- **Log slice.** The launcher records the byte length of `<RUN>/.mdpro/mdpro.log`
  before and after each step. A step's slice is the bytes between the two.
  Expected events are stated per slice.
- **State.** A probe reading (driver runs) or what the person sees (hand runs).
- **Disk.** Files under `<RUN>`, read after the journey.

The draft of a document is
`<RUN>/Library/Application Support/mdpro/drafts/<documentId>.draft.json`, field
`content` (`src-tauri/src/services/draft/paths.rs:8-13,33-36`,
`src-tauri/src/services/draft/mod.rs:62-73`). It is **not** under `.mdpro`.

**How expected events are written.** `a → b` means the code guarantees `a` is
written before `b`. `a, b` means both are in the slice, in either order. The
webview sends each log line as its own asynchronous call
(`src/services/loggingService.ts`), so two webview lines carry no guaranteed
order, even when the code issues them one after the other. Order is guaranteed
only inside a synchronous Rust chain, from a start to its own success, and
from a Rust command's lines to a webview line issued after that command was
awaited.

**When the draft is read.** The autosave tick writes the active document every
five seconds while it is dirty, and logs `draft.write` start and success
(`src/hooks/useAutoSave.ts:15-33`, `src-tauri/src/commands/draft.rs:107,139`).
Until D56 (2026-10-08) this event was named `file.write`, so a log from an
earlier build has `file.write` where this document says `draft.write`.
WYSIWYG marks the document dirty at once but copies the text into the store
200 ms later (`src/plugins/milkdown/editSync/controller.ts:55,142-186`), so the
first tick after the last key can hold older text. The draft is read after the
**second** `draft.write` success for that document that follows the last input
step. This is an ordering rule. No duration is measured or compared.

### J1b — cold start through `open`

Screens: S4, S5. Run 3.

| # | Class | Action | Expected events | State after |
|---|---|---|---|---|
| 1 | `launcher` | `open --env … -a <bundle> <RUN>/adr0047-journeys.md`, one `--env` per variable of the run environment. No instance is running | `app.launch` start, then `file.open.external` start `{filePaths, source:"finder", appReady:false}` → `file.open.external.pending {pendingPaths, reason:"app_not_ready"}` (`src-tauri/src/main.rs:438-492`). In setup: `file.open.args_filtered {source:"cli", accepted:0}` → `app.pending_paths_transfer` → `app.launch_state.set {count:1, paths}` → `window.open {windowLabel:"main"}` → `app.ready` (`main.rs:184-252`). Then the window lines of J1a. There is no `file.open.cli` line | As J1a |

- `file.open.external` success is also written, once per path, even though the
  open was only queued (`main.rs:498-508`). It does not prove the file opened;
  `tab.open` does.
- **Known risk.** Whether the open event arrives before setup cannot be told
  from code. If it arrives after `app.ready`, the line says `appReady:true` and
  the file is routed instead. A route miss from Finder always makes a new
  window (`src-tauri/src/services/open_route/plan.rs:113-119`), so the end
  state would be an empty `main` and the document in `W2`. Which happens is
  decided by the reference run. If hand runs disagree with each other here,
  J1b has no reference and is recorded as not comparable.
- Setup takes the queued paths (`main.rs:201`) some lines before it marks the
  app ready (`main.rs:254`). An open event landing between the two would be
  queued and never opened. Whether an event can be delivered in the middle of
  setup was not checked. If a run shows `file.open.external.pending` and no
  `tab.open`, this is the place to look, and it is an app defect, not a driver
  result.

### J2 — Source editor: typing, selection, undo, a modifier shortcut

Screens: S3, S5. Run 1, after J1a. Mode is Source: `.cm-editor` is mounted
(`src/App.tsx:1010-1019`).

| # | Class | Action | Expected events | State after |
|---|---|---|---|---|
| 1 | `cli` | Put the caret at the end of the document. By hand: click the line `Last paragraph.`, press `⌘↓`. A driver may reach the same caret position by any input it has; this step is setup and is not what S3 judges | none | Caret on the empty last line, after the final newline |
| 2 | `cli` | Type `alpha beta` | none | Tab shows the dirty marker `.bottom-tab__modified` (`src/components/BottomTabs/BottomTabs.tsx:65`; `src/stores/documentStore.ts:79-84`) |
| 3 | `cli` | `←` five times, then `Shift+←` five times | none | `alpha` is selected |
| 4 | `cli` | `Backspace` | none | Last line reads ` beta` |
| 5 | `cli` | `⌘Z` | none. Undo writes no log line on any path | Last line reads `alpha beta` |
| 6 | `cli` | `⌘1` | `ui.shortcut.trigger {shortcut:"Cmd+1", action:"paragraph.heading1"}` (`src/hooks/useKeyboardShortcuts.ts:141-152`) | Last line reads `# alpha beta` |
| 7 | `cli` | Wait for the draft (rule above) | `draft.write` start → success `{documentId:D1}`, at least twice | — |

Disk: the draft's `content` equals the fixture followed by `# alpha beta`, with
no newline after it. The fixture copy on disk is unchanged; nothing saved it.

Why these keys:

- The selection in step 3 moves the caret away from where typing ended.
  CodeMirror joins an edit to the previous history event only when no selection
  change came between them (`@codemirror/commands` 6.10.1,
  `dist/index.js:482-488`). So step 4 is its own undo event however fast the
  keys arrive, and step 5 restores exactly `alpha`. Without this, a fast driver
  and a slow person could undo different amounts.
- `⌘1` is bound only in the webview: by the CodeMirror keymap
  (`src/plugins/codemirror/headingPlugin.ts:101-112`) and by the window listener,
  which also logs. Both run: the keymap binding does not stop propagation and
  the window listener does not look at `defaultPrevented`. The heading command
  replaces the line's prefix and does not toggle, so running it twice gives the
  same text.
- `⌘Z` is also the native Edit → Undo item (`src-tauri/src/menu.rs:139`).
  Whether a physical `⌘Z` reaches CodeMirror's keymap
  (`src/components/Editor/Editor.tsx:71-80`) or the native `undo:` selector is
  not known from code. The journey judges the text, which must be the same
  either way.

### J3 — WYSIWYG editor: the same, plus bold

Screens: S3, S5. Run 2, after its J1a. Mode is WYSIWYG: `#milkdown-container`
holds the editor.

| # | Class | Action | Expected events | State after |
|---|---|---|---|---|
| 1 | `cli` | Put the caret at the end of the paragraph `Last paragraph.`. By hand: click to the right of its last character. Setup, not judged | none | Caret after `paragraph.` |
| 2 | `cli` | `Enter`, then type `alpha beta` | none | A new last paragraph `alpha beta`. Tab is dirty |
| 3 | `cli` | `Shift+←` four times | none | `beta` is selected |
| 4 | `cli` | `⌘B` | none. Milkdown's shortcuts are not logged (`src/plugins/milkdown/typoraKeymapPlugin.ts:158-166`) | `beta` is bold |
| 5 | `cli` | `←` twice, then `Shift+←` five times | none | `alpha` is selected |
| 6 | `cli` | `Backspace` | none | Paragraph reads ` beta`, `beta` bold |
| 7 | `cli` | `⌘Z` | none | Paragraph reads `alpha beta`, `beta` bold |
| 8 | `cli` | `⌘1` | none, apart from the known warning below | The paragraph is a level-1 heading |
| 9 | `cli` | Wait for the draft | `draft.write` start → success `{documentId:D1}`, at least twice | — |

Disk: the draft's last block is `# alpha **beta**`. Milkdown re-serialises the
whole document, so the text above it may differ from the fixture in spacing
(the table's separator row, blank lines). The expected `content` is therefore
the one the reference run produced, kept with the reference. It is compared
byte for byte.

**Known warning (D88).** On the `0b54bde` baseline (2026-10-10), step 8 wrote
one `ui.toc.resolve.mismatch {level:"warn", status:"fail", domCount:5,
entryCount:4}` (`src/utils/tocResolveMismatch.ts`). The new heading makes five
heading elements while the outline still has four entries. The projection keeps
the line, because it is a `warn`. It is a known baseline warning, tracked as
D88. A post run passes J3 if it shows the same line or no line.

Why these keys:

- ProseMirror starts a new history group when an edit is not adjacent to the
  previous transaction's ranges, or after 500 ms
  (`prosemirror-history` 1.5.0, `dist/index.js:277-281,292-304`). The bold in
  step 4 is a mark step with an empty position map, so the edit after it is
  never adjacent. Step 6 is therefore its own group at any speed, and step 7
  restores exactly `alpha` (*inferred from source*).
- The heading in step 8 applies to the block, so it does not depend on what
  the selection is after the undo. It uses `setBlockType`, which does not
  toggle. The window listener of J2 acts only when `.cm-editor` is present, so
  here it neither logs nor runs.

### J5 — Esc on the unsaved-changes dialog

Screens: S2. Run 1 after J2, or alone on any build with a dirty document.

| # | Class | Action | Expected events | State after |
|---|---|---|---|---|
| 1 | `cli` | Make the document dirty, if it is not: type one character in the editor | none | Dirty marker on the tab |
| 2 | `cli` | Click the tab's `×`, `.bottom-tab__close` (`BottomTabs.tsx:67-74`) | none. The click and the dialog opening are not logged | `ConfirmDialog` is shown: `.dialog-card[role=dialog][aria-modal=true][aria-label="Unsaved changes"]`, buttons `Keep editing` and `Discard` (`BottomTabs.tsx:79-87`, `src/components/common/ConfirmDialog.tsx:86-103`) |

- On the build with the `src/` part of `c39dfb1` reverted, the expected result
  is no line and the dialog still open. That is the negative control, and it is
  an expectation to be tested, not a fact (see "S2 baseline protocol").
- Initial focus is on `Keep editing`. The Discard dialog passes `destructive`
  (`BottomTabs.tsx:84`), which sends initial focus to Cancel (D48). The focus is
  one `focus({focusVisible:true})` call through `useVisibleInitialFocus`, not
  `autoFocus` (D53, D63; header of `ConfirmDialog.tsx:10-23`). The 2026-10-10
  baseline showed the focus ring on `Keep editing`.
- Esc does not depend on focus. It goes through the document-level capture
  stack in `useDialogEscape` (ADR-0045), so step 3 needs no focus first.
- **`Enter` and `Space` are never pressed in this journey.** They are not the
  input under test, and they would act on whichever button has focus. A build
  without D48 opens with focus on `Discard`, where they would close the
  document and delete its draft.
- If the dialog is still open after step 3, it is closed by clicking
  `Keep editing`. That click writes `ui.dialog.cancel` without
  `ui.dialog.escape`, and it belongs to the next slice.
- **When Esc is not pressed** (MANUAL/SKIP), `J5.set.txt` is expected to be
  empty with `drafts=drop`. Steps 1 and 2 write no line, and the slice holds
  only `draft.write` lines, which `drafts=drop` removes. An empty file is not a
  failed projection. J5 is judged on its own, by the outcome of step 3, and is
  not diffed against another run.

### J7b — `open` while running

Screens: S4. Run 1, after J7a. The path is **not** open in any window.

| # | Class | Action | Expected events | State after |
|---|---|---|---|---|
| 1 | `launcher` | `open --env … -a <bundle> <RUN>/adr0047-second.md` while the instance runs | Rust, in order: `file.open.external` start `{filePaths, source:"finder", appReady:true}` → `window.open {windowLabel:W3, filePath}` → `file.open.route {source:"finder", outcome:"new-window", windowLabel:null, matchCount:0}` → `file.open.external` success (`main.rs:438-510`, `execute.rs:60-66`, `tauri_glue.rs:106-131`). The window is created first and the route line is written after it. From `W3`, in any order: `app.url_param_check {windowLabel:W3, hasOpenParam:true}`, `file.open.url_param` start `{windowLabel:W3, fileBasename}` and success `{windowLabel:W3, fileBasename, documentId:D3, hasContent:true}`, `tab.open {documentId:D3, tabIndex:0}`, no `tab.switch` (as in J1a), one `view.mode.change {fromMode:"wysiwyg", toMode:"source"}`, `preferences.set` start → success (`src/hooks/useOpenUrlParam.ts:65-107`). `file.open` start → success, and that success → `tab.open`. With `--via open`, the launcher also prints
`into: run <R> second process exited 0`. That line is the `open` helper
exiting, not an app process. The app side still starts no second app process:
on 2026-10-10 `pgrep` showed one app pid after J7b, and the slice had no
`app.single_instance` line. In J7a the same launcher line is the second app
process exiting, as the table says.

`RunEvent::Opened` being reached is the point of this journey: with its own
bundle identifier, the verification build depends on Launch Services finding
the running instance (plan WI-002, risks).

## Semantic projection

Two runs of a journey agree when their projections are equal. The projection
is built per step from the step's log slice, the state reading and the disk.

### 1. Which lines count

A line is in the projection if its `event` is in this list:

| Group | Events |
|---|---|
| Start-up | `app.launch`, `app.ready`, `app.pending_paths_transfer`, `app.launch_state.set`, `app.launch_state.take`, `app.launch_paths_check`, `app.single_instance`, `app.url_param_check` |
| Opening | `file.open`, `file.open.cli`, `file.open.args_filtered`, `file.open.external`, `file.open.external.pending`, `file.open.route`, `file.open.url_param` |
| Windows | `window.open`, `window.create`, `window.close` |
| Documents | `tab.open`, `tab.switch`, `tab.close`, `file.close`, `view.mode.change` |
| Input as the app saw it | `ui.menu.select`, `ui.shortcut.trigger`, `ui.button.click`, `ui.dialog.confirm`, `ui.dialog.cancel`, `ui.dialog.escape` |
| Persistence | `preferences.set`, `draft.write`, `file.save` |

**Any line with `status: "fail"`, or `level` `warn` or `error`, is in the
projection whatever its event.** A failure cannot hide behind the list.

Everything else is left out. The ones a reader will see most, and why:

| Left out | Reason |
|---|---|
| `window.focus`, `window.blur`, `window.move` | They follow the person's pointer and other applications |
| `mcp.*` | `mcp.sync` is debounced, so its count follows timing |
| `plugin.*`, `editor.milkdown.*`, `editor.scroll_anchor.*`, `ui.toc.*`, `toc.extract`, `file.watch.*` | Driven by rendering and mounting; counts vary |
| `preferences.last_view_mode`, `preferences.window_state.save`, `preferences.recent_files.buffer` | Bookkeeping around `preferences.set`, which is kept |
| `ui.menu.listen`, `file.open.route.listen`, `app.quit`, `app.quit.*`, `legacy.log`, `app.draft_migration` | Listener set-up, run end, and free text |
| `file.draft.cleanup`, `file.draft.list`, `ui.sidebar.preference` | Start-up housekeeping. Added after the 2026-10-02 trial run showed them |
| `app.verify_run` | The verify build's own start line. It carries `runDir`, `pid` and `buildId`, which the launcher checks against the handshake file. Seen once per run start (J1a, J1a in run 2, J1b). Added after the 2026-10-10 baseline showed it |
| `preferences.read` | A read changes nothing; the write it may precede, `preferences.set`, is kept. Each window reads as it mounts (J1a, J1b, J6, J7b), and the Settings dialog reads when it opens (J4b). Added after the 2026-10-10 baseline showed it |
| `menu.recent_files.sync` | Bookkeeping around `preferences.set`: the native Open Recent menu is rebuilt from the recent-files list (`src-tauri/src/menu_recent.rs`). Seen as windows mount (J1a, J1b, J6, J7b). Added after the 2026-10-10 baseline showed it |
| `window.apply_state` | Window geometry at hydration (`src/services/windowStateApplier.ts`), the same ground on which `geometry` is removed. Seen as windows mount (J1a, J1b, J6, J7b). Added after the 2026-10-10 baseline showed it |
| Anything the driver itself writes | It is not the app's behaviour. Candidate A writes nothing to `mdpro.log`; a candidate that does gets its event names listed in the spike record first |

A new event name that appears in a slice and is in neither table is reported.
It is not silently dropped.

### 2. Normalisation

| Field | Rule |
|---|---|
| `ts`, `durationMs`, `startupTimeMs` | Removed. No time is compared (E39) |
| `actionId` | Used to pair a start with its success or fail, then removed |
| `pid`, `buildId`, ports | Removed. The launcher checks them against the handshake file |
| Window label | `main` is kept. Each `mdpro-<uuid>` becomes `W2`, `W3`, … in order of first appearance. `windowId` is treated the same way |
| Document id | `D1`, `D2`, … in order of first appearance. A file's id is a hash of its path (`src-tauri/src/models/document.rs:63-69`), so it changes with the run directory |
| Paths | The run directory prefix becomes `<RUN>`, in both its `/tmp` and `/private/tmp` spellings |
| `geometry`, `geometryReason`, `geometryClamped`, `toPosition` | Removed. They depend on the display |
| `bytes` in `draft.write` | Removed. A tick can catch text mid-journey; the final text is checked on disk |
| `app.launch_state.take` and `app.launch_paths_check` with a count of 0 | The line is removed. Every window polls for launch paths as it mounts and once more 300 ms later (`src/App.tsx:901-948`); a poll that found nothing says nothing about the journey |

### 3. Fields that must be equal

After normalisation, these fields of each line must match. Other context
fields are ignored.

| Event | Fields |
|---|---|
| every line | `event`, `status` |
| `file.open.args_filtered` | `source`, `accepted`, `dropped` |
| `file.open.cli`, `app.single_instance` | `filePaths` |
| `file.open.external` | `source`, `appReady` (start), `filePaths` or `filePath` |
| `file.open.external.pending` | `pendingPaths`, `reason` |
| `file.open.route` | `source`, `outcome`, `windowLabel`, `matchCount`, `documentId` when present |
| `file.open`, `file.open.url_param` | `filePath` or `fileBasename`, `windowLabel` when present, `fileSizeBytes`, `encoding`, `documentId` and `hasContent` when present |
| `app.launch_state.set`, `app.launch_state.take`, `app.launch_paths_check` | `count` or `pathCount`, `paths`, `windowLabel` when present |
| `app.url_param_check` | `windowLabel`, `hasOpenParam` |
| `window.open`, `window.create` | `windowLabel` or `windowId`, `filePath` |
| `tab.open`, `tab.close`, `file.close` | `documentId`, `filePath`, `tabIndex`, `wasModified` |
| `tab.switch` | `fromDocumentId`, `toDocumentId` |
| `view.mode.change` | `fromMode`, `toMode`, `source` |
| `ui.menu.select`, `ui.button.click`, `ui.dialog.*` | `controlId`, `windowLabel`, `mode`, `dialog`, `outcome`, `title` |
| `ui.shortcut.trigger` | `action`, `shortcut` |
| `draft.write`, `file.save` | `documentId` |

### 4. Order and count

- **Order is compared only where the code guarantees it.** That is the arrow
  sequences in the journey tables, plus every start before its own success or
  fail. Everything else in a slice is compared as a set with counts. Rust and
  the webview write to the log independently, and each webview line is its own
  asynchronous call, so two lines the code issues one after the other can land
  either way round.
- **Counts are exact**, with one exception: `draft.write`. The autosave tick
  repeats every five seconds while the active document is dirty, so the number
  of pairs follows how long the step took. Where a journey table asks for
  `draft.write`, the projection holds only "at least one success for this
  document in this slice". In every other slice, `draft.write` lines for a dirty
  document are not a difference, and neither is their absence. The tick keeps
  writing the active document while it is dirty, whether or not the text
  changed (seen on the 2026-10-02 trial run). It does not write a dirty
  document that is not active (J4a, 2026-10-10 baseline).
- A line that is in the list and in the slice but not in the journey table is a
  difference. So is a missing one.

### 5. State and disk

| Check | Journeys |
|---|---|
| Windows by label; per window: tab titles in order, the active tab, each tab's dirty flag | all |
| An open `ConfirmDialog`, by its `aria-label`, or none | J5 |
| Draft `content` for a document, read by the rule in "Evidence per step" | J2, J3 |
| `config.json`: `markdown.autoPair`, `recentFiles` with `<RUN>` normalised | J4b, J1a, J1b |
| The fixture copies are byte-identical to the committed fixture | all. No journey saves |
| No draft file for a document that was never dirty | J1a, J1b, J4a, J7b |

### 6. What the comparison is against

- **The reference is the hand run** on the baseline head build with the driver
  feature off (WI-005, comparison one). Predictions in this document that the
  hand run contradicts are corrected here, with the date.
- A driver run that differs from the reference is first checked against a
  second hand run of that journey. If the two hand runs differ from each other
  in the same place, the projection is wrong for that journey: it is corrected,
  or the journey is recorded as not comparable. It is not a driver failure.
- **A hand run and a driver run use the same step classes.** A `native` step is
  native in both. So `ui.menu.select` and `ui.shortcut.trigger` are expected to
  match, and a mismatch means the input reached the app by a different path.
- Undo is the one input with two possible paths and no log line (J2, J3). Only
  its effect on the text is compared.

## S2 baseline protocol

S2 asks whether a driver's Esc behaves like a physical one. The baseline is
taken by a person, before any driver is installed (WI-005), on two bundles:
**baseline reverted** (the `src/` part of `c39dfb1` reverted) and **baseline
head**.

### What is recorded

Four items, each time Esc is pressed in J5 step 3:

| Item | How it is observed |
|---|---|
| Native key window | Looked at, not clicked: the menu bar shows the verification build's name, and window `main` has coloured traffic lights. Recorded as the window label, or "another application" |
| DOM focus | From the key recorder below: the active element at the moment of the key, whether it is inside `.dialog-card`, and `document.hasFocus()` |
| Window that got the key | From the key recorder: an entry exists in window `main`'s page, or none exists. No entry means the key never reached the page |
| Log line | The slice of `mdpro.log` for step 3, quoted |

Plus the outcome: dialog closed or still open, and the tab still present and
dirty.

### The key recorder

A release-profile bundle has no Web Inspector: `src-tauri/Cargo.toml` does not
enable Tauri's `devtools` feature. Without it a person cannot read DOM focus,
and a focus ring is not a substitute (a button focused by script after a mouse
click may show none). So **every bundle built for the spike enables
`devtools`**, and the "Builds" table of the spike record says so. The bundles
built after selection (WI-009 on) do not; there the fixed probe reads the same
facts.

The recorder is passive. It is armed, the inspector is closed, and only then
does the journey start:

1. Start the run (J1a). Right-click in the window → Inspect Element.
2. In the console, paste:

   ```js
   window.__s2 = [];
   window.addEventListener("keydown", (e) => {
     const a = document.activeElement;
     window.__s2.push({
       key: e.key,
       trusted: e.isTrusted,
       repeat: e.repeat,
       hasFocus: document.hasFocus(),
       active: a ? `${a.tagName}.${a.className}` : null,
       activeText: a ? (a.getAttribute("aria-label") || a.textContent || "").slice(0, 24) : null,
       inDialog: Boolean(a && a.closest(".dialog-card")),
       dialogOpen: Boolean(document.querySelector(".dialog-card")),
     });
   }, true);
   ```

   It listens on `window` in the capture phase, so it runs before the app's own
   listener on `document` (`src/hooks/useDialogEscape.ts:139`). It prevents
   nothing and stops nothing.
3. **Close the inspector.** Its window would otherwise be the key window.
4. Do J5 steps 1 and 2 with the mouse and keyboard.
5. Look at the menu bar and the traffic lights, and note the key window.
6. Press Esc once, physically. Do not hold it.
7. Note whether the dialog closed.
8. Open the inspector again and read `window.__s2`. The last entry with
   `key: "Escape"` is the record. Copy it into the spike record as text.
9. If the dialog is still open, click `Keep editing`. Never `Discard`.

`trusted` is `true` for a physical key. In S2.2 and S2.3 the same recorder
shows `false` for the driver's key, which keeps the two classes of evidence
apart in the record.

If the recorder itself turns out to change the result (the dialog behaves
differently with and without it armed, on the same build), it is dropped, DOM
focus is recorded as "not observed", and the spike record says so.

### The control must hold

| Baseline reverted | Baseline head | Meaning |
|---|---|---|
| Dialog stays open | Dialog closes | The control holds. The spike goes on |
| Dialog closes | Dialog closes | **S2 is void.** The spike stops until the control is redesigned (ADR-0047 decision 4) |
| any | Dialog stays open | D34 is not fixed on this build. The spike stops; this is a defect, not a spike result |

On the head build Esc goes through the document-level capture stack
(`useDialogEscape`, ADR-0045) and does not depend on focus. On the reverted
build it depends on focus: the old listener sits on the card and fires only
while DOM focus is inside it. The dialog sends initial focus to `Keep editing`
by script (D48, D53/D63), and that button is inside the card. So focus may well
be inside the card on the reverted build, and the old listener would then fire.
The reverted result is not assumed.

### Evidence class

A physical Esc is class `physical`. A driver's Esc is class `driver input` and
never stands in for a physical one (`progress.md`, 2026-09-30). S2 passes for a
candidate when its Esc gives, on both bundles, the outcome the physical Esc
gave there, failure included, with nothing focused first.

## Known limits of these journeys

- No journey saves a file, uses a native panel, or quits through the quit
  guard. Those are `native` or `human` and belong to `gui-acceptance`.
- No journey uses `⌘K` in Source mode. It calls `window.prompt`
  (`src/plugins/codemirror/linkPlugin.ts:9`), which a build with candidate A
  answers by freezing the window for 30 s (spike record, "Source reading").
- IME input is not covered.
- WebKit's own data sits outside `<RUN>` (plan Q11). The app uses no web
  storage, so no journey's result should depend on it (*inferred*).
- Ten journeys are a screen for choosing a driver. They are not coverage of
  the app.
