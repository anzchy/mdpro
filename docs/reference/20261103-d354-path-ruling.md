**What “closes D354” means.** There must be one admitted fixed-version application process per intended identity, with no duplicate initial window, migration or MCP owner. A healthy second launch sends one request carrying its cwd and argv, including CJK/spaces; the owner routes it once. mdpro already intentionally opens additional document windows (`main.rs:288–290`; `services/open_route/tauri_glue.rs:134–145`), so “one live window” must not become a ban on normal document windows. A no-file second launch creates none (`main.rs:260–290`; `launch_args.rs:195–196` skips argv[0]).

“Once” is not a durable exactly-once transaction across an owner crash. The legacy wire has neither a receipt nor deduplication. A sender that writes and loses the connection cannot know whether routing happened. Retry connection establishment within a deadline; do not replay after delivery may have begun. Test healthy delivery at the receiving/routing effect, not just successful `write_all`. Owner death, stalled IPC and uncertain delivery must fail/refuse without a second setup; they must not be reported as a confirmed file-open success. Adding durable delivery or a new acknowledgement protocol is outside this ruling.

**Why option 2 also needs an explicit AC boundary.** The handoff is right that an unchanged plugin cannot meet unrestricted AC-3. I disagree with any implied conclusion that simply owning the listener, or checking `(device,inode)` before unlink, automatically proves the unrestricted promise. Against a process that can replace the pathname between that check and unlink, it is still a check/use race. An advisory lock excludes only participants. No replacement or crate patch can retroactively stop an old binary executing its own `remove_file` or “launch normally” branch.

Accordingly, fixed code must **not** treat failed connect, elapsed time, a PID file, or possession of its new flock as permission to delete an unowned legacy pathname. It must leave a live/unknown foreign endpoint alone and forward to a compatible owner or refuse. This is stronger than option 1: the fixed implementation no longer contains the known destructive legacy-path sequence. The residual boundary is external old code and ambiguous compatibility, not that mdpro knowingly keeps executing that sequence.

A concrete design direction is a validated private per-user/identity directory containing the stable lock and authoritative fixed-version socket. Cleanup of that socket remains serialized by the same lock and ownership generation. The legacy `/tmp/<normalized-identifier>_si.sock` address is compatibility, not ownership authority. One candidate is an exclusively created, stable compatibility symlink to the private socket, retained across fixed-owner exits, so fixed code never needs a check-then-unlink on the public legacy name. An existing unknown socket/link is never overwritten; a healthy legacy socket is forwarded to, an ambiguous stale one causes a diagnostic refusal. This preserves the old request bytes and potentially the old address while fencing fixed-version cleanup.

That compatibility-alias mechanism is a **proposal requiring a macOS probe**, not a runtime fact established by WI-0. Before RED, prove old-plugin-equivalent connect/EOF framing through it, safe crash recovery, path-length limits, exclusive creation, refusal on a racing foreign bind, and behavior when legacy cleanup removes the alias. Do not substitute an unproved alias design for the current unproved wrapper. If a different mechanism is selected, it must prove the same no-unowned-unlink property. Never silently fall back to connect-failed → remove.

The private directory prevents cross-user interference when correctly validated; it does not defend against arbitrary code running as the same UID modifying its contents. Treat that as an explicit trust boundary, not a claim of universal protection. Do not forward file names/cwd to another UID's listener. Validate ownership/type/symlinks and bound incoming bytes, read duration, pending requests and concurrency. The old listener reads an unbounded string and processes connections serially (`macos.rs:102–111`); copying that loop verbatim would allow one stalled sender to block all forwarding.

**ADR-0047 and planning disposition.** ADR-0047 does not require the shipping singleton implementation to remain forever in the upstream crate. Its decision 3 requires isolation and fresh-process proof (`:169–187`); decision 4/S4 says the driver must not reorder or bypass the single-instance plugin or `RunEvent::Opened` (`:226–229`). Do not rewrite the accepted body's history. Its control-channel authentication rules (`:251–268`) do not turn the ordinary file-forwarding socket into a control channel.

Keep `verify_run::enforce()` before admission filesystem access or logging: its validation-only, no-log behavior is deliberate (`services/verify_run.rs:7–17,26–34,185–203`). “Top of main” means after this existing validation on feature builds, before draft migration/Builder. Release and verify identities stay separate. A second verification run must not forward into a different run; same-run duplicate handling and cross-run refusal need distinct tests. The admission key must not accidentally split one release identity by version, build SHA, executable path or arbitrary HOME spelling. Existing exclusive `instance.json` publication remains a separate guard (`verify_run_instance.rs:13–19,64–79`).

RULING 2 · ADR yes · AC-3 narrowed: fixed-version ownership/recovery; preserve foreign endpoints and refuse ambiguous legacy reclamation; no guarantee against uncooperative binaries or arbitrary same-UID namespace mutation

**Exact revised AC-3:**

> **AC-3 [unit].** For fixed-version processes sharing the same validated user/application identity, when the owner exits or is SIGKILLed, a later start acquires ownership and establishes its endpoint, provided no foreign endpoint obstructs the compatibility address. The lock inode is never deleted or replaced. Cleanup is authorized only for the owning generation while it retains the admission lock; a delayed cleanup from an earlier generation cannot remove or disable the successor's endpoint. A live or unknown legacy/unrelated endpoint, including one bound after a failed notification, is never unlinked or overwritten by the fixed implementation: it forwards once to a compatible owner or refuses before migration, Builder and normal setup. A failed connection alone is not proof of stale ownership. Recovery guarantees cover mdpro-owned resources inside its validated namespace; they do not promise that an unfixed process obeys the new lock or cannot remove a public compatibility address, nor protection against arbitrary same-UID mutation of the private namespace. Proof: real subprocess tests for SIGKILL and normal exit, successor reachability after delayed cleanup, foreign-bind interleaving, ambiguous stale legacy refusal and stable lock identity.
