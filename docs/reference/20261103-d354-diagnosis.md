## Ranked causes

### 1. Confirmed defect: simultaneous starts bypass macOS single-instance admission

`tauri-plugin-single-instance-2.5.2/src/platform_impl/macos.rs:20–46,74–76,95–131`:

- Each process first tries to connect (`26`, `78–79`). NotFound/ConnectionRefused means remove socket (`34`), schedule listener task (`35`), then return setup success (`46`).
- Binding happens later in an async task (`100–101`). Bind failure logs “launching normally” and does not stop startup (`124–128`). Other notification errors also allow normal startup (`37–41`).
- A valid interleaving: A and B both connect before a listener exists; both return failure; A removes stale path and binds; B removes A's live path and binds another socket. Both continue. Another valid interleaving has both remove before bind, then one bind fails and **still continues**. Both can reach ready under either schedule.
- Socket is `/tmp/com_mdpro_app_si.sock` (`61–71`, config identifier `com.mdpro.app`). No semver feature is requested in mdpro's dependency. The plugin is already the first application plugin (v0.3.5 main.rs:250); moving it earlier among plugins does not fix its internal asynchronous admission.

This directly explains persistence of both PIDs, the same-millisecond-start opportunity for the race, and concurrent migration/MCP effects. It does **not** generate a second start and does not explain the 3.3 s. It existed in the successful 0.3.4 canary too. That run can avoid the race because only one process was spawned, or a second reached singleton after its listener was ready; the record does not distinguish those possibilities. **Not a proved v0.3.5 regression.**

### 2. Open origin candidate: duplicate old-client restart execution

A duplicate backend command or two entries to Tauri's restart routine could create two children. One UI start weakens a duplicate-click explanation but cannot count Rust restart entries. The runtime uses a restart-on-exit flag read with `load`, not an explicit consume; that observation alone is not evidence that Exit was delivered twice. Repeated Exit callbacks would ordinarily also repeat mdpro's `app.quit` line, whereas this interval contains one. No causal hook change or dependency bump supports blaming the quit guard.

The static ordinary path above spawns once. No trace in the granted evidence shows a second restart entry, reentrant exit, or request-send failure. Rank this as an investigation target because restart is the known launcher, **not** an established cause. The timing is compatible with two requested children delayed before main, but cannot explain why 0.3.4 passed without an additional scheduling/input difference.

### 3. Open origin alternative: a separate launcher or OS launch request

One Tauri child plus another launch from outside the old process could produce the same logs. There is no parent/executable-launch trace to distinguish this from candidate 2. Same-millisecond `main` logs do not prove two Tauri spawn calls. No positive evidence identifies LaunchServices, tester input, restoration, or another process as that launcher. Do not attribute it to any of them. This alternative also remains compatible with a one-process 0.3.4 run; no version-specific change is demonstrated.

### 4. Low: changed plist parsing directly double-spawns

The differential exists and reaches relaunch, but source control flow refutes the simple “macOS spawn falls through to generic spawn” mechanism. A parser failure yields generic spawn only. No demonstrated parser side effect creates another process. Do not roll back a security-related dependency on this evidence.

## Ownership and proposed change

**Which side:** the relaunch instruction runs in old **0.3.5**; changes to that path help only updates initiated **from a fixed client**. The new client cannot retroactively change old Rust execution. But the confirmed failure to exclude a second live process belongs to **startup in the receiving client** (also pre-existing in earlier clients). An atomic receiving-side guard protects updates from 0.3.5/0.3.6 into a fixed version as well. Root ownership of the extra spawn remains unresolved.

**Should macOS refuse a second instance? Yes.** The tree already expresses that policy with `tauri-plugin-single-instance = "2"`; this is hardening a failed existing policy, not deciding to add a second-instance feature. Its callback forwards cwd/args/file opens to the existing instance. Existing instances must continue receiving file-open requests, with no second setup, config migration, MCP server, or window.

**Proposed seam, not implemented:** repair the macOS singleton admission in the existing plugin through a reviewed pinned patch, or an mdpro-owned startup service if a dependency patch is unsuitable. Atomic ownership must precede cleanup/bind and normal app setup, with a synchronously established IPC endpoint. A per-user, identifier-scoped OS advisory lock held through the owning process's lifetime is one approach; never delete/recreate the lock inode while peers can retain it. Only the owner may remove a stale socket, bind, or clean up its endpoint. Losers forward to the owner and exit; if its listener is not ready, use bounded readiness handling, **not** launch-normally fallback. An admission failure must stop setup with a clear diagnostic. Account for crash recovery, old-owner shutdown/restart overlap, and cleanup identity so an outgoing owner cannot remove its successor's socket. Preserve the old plugin's IPC wire behavior for older live versions. `verify-run` publication is a separate opt-in guard, not shipping protection.

Also move any startup writes that currently precede singleton admission behind it: `main.rs:107–108` runs legacy draft migration before builder/plugin setup. Validate that Tauri initial-window construction cannot precede the chosen admission point. This may require an earlier main-entry guard rather than just changing a plugin callback. Preserve intentional development/verification isolation; the exact key and lock scope need the implementation brief.

Do not replace this with only a React debounce or only a restart-once flag: neither guards an old client's two arrivals into a newly installed bundle. Once provenance identifies a duplicate restart execution, fix that specific old-client seam as a separate change and test it; no speculative relaunch replacement is warranted now.
