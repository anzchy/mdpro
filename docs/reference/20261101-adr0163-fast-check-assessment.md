# ADR-0163 assessment by gpt-auditor (2026-11-01)

## Recommendation

Choose **A**, scoped to TypeScript tests of rich *data shapes*, while leaving D323's race harness and Rust exactly as planned. The ADR should say that `fast-check` is an additional test-only tool, not a replacement for bounded enumeration, pinned regression cases, or device tests. It should narrow D323 §4's rejection to its race models and amend the “repo does not use fast-check by design” comment in `tests/support/seededRandom.ts:2-5` when the dependency actually lands. D323's WI-0 and Q7 must still explicitly reject fast-check **for D323** (`docs/plans/20261027-plan-d323-model-property-tests.md:845-851,1358`); option A does not silently overrule that reviewed plan.

### What it buys

- The best candidates have combinatorial structured inputs: `tests/table-mcp-overflow.test.ts:176-203,246-265` samples 200 overflow table shapes from `tests/support/tableCorpus.ts`, then tests actions and payloads; `tests/tooling/release-latest-json.test.ts:162-165` tests a build/validate round trip over 100 seeded values and one-field mutations; `tests/tooling/device-drag-plan.test.ts:268-290` samples 300 valid argument lists. Arbitraries for table geometry/content, metadata variants, and valid/invalid argument lists could explore shape combinations absent from those fixed seeded samples and shrink a failure to the smallest useful input. This is a **prospective** benefit; I found no documented past defect proven discoverable only by fast-check. D194's real-editor round trips (`tests/d194-link-definitions-roundtrip.test.tsx:1-21,75-92`) show the kind of serializer data-loss boundary where a carefully constrained arbitrary could find an unlisted combination, but its 14 named regressions must remain.
- D343's PowerShell step-list shapes, as described in this request, are another plausible data generator. The D343 row is **not present in this checkout** (`rg -n D343 docs/plans/20260912-frontend-backend-sequencing-order.md` returned no match), so I cannot cite its implementation as evidence. Its implementor can enumerate now; ADR-0163 should not hold it up.
- D323 differs: its defect traces have at most four disturbances (`docs/plans/20261027-plan-d323-model-property-tests.md:580-600`), and §4.1 requires *every* enabled release order within that bound (`:602-610`). Random sampling or `fc.scheduler` would weaken that exhaustive claim unless the whole oracle and plan were reworked. Shortest-first enumeration supplies a minimal trace without generic shrinking. This is why **B** is worse despite fast-check's real scheduler/model-run support. [fast-check's race-condition documentation](https://fast-check.dev/docs/advanced/race-conditions/) confirms that capability, not equivalence to D323's exhaustive contract.

### Integration and cost

- `package.json:90` pins Vitest `~3.2.7` (D323 §4's 3.2.4 statement at `:573` is stale). Use `fc.assert(fc.property(...))` or `fc.assert(fc.asyncProperty(...))` inside ordinary Vitest `it` blocks. Record the reported seed/path in failures, replay it, and turn consequential counterexamples into named regressions. No adapter is needed. If an adapter is desired later, `@fast-check/vitest@0.2.4` has peer `vitest: ^1 || ^2 || ^3 || ^4` and depends on fast-check `^3 || ^4`; current 0.4/0.5 lines require Vitest 4.1+ ([package compatibility table](https://www.npmjs.com/package/%40fast-check/vitest?activeTab=readme)). Pinning the old adapter adds a second maintenance surface for little value.
- Keep fast properties in `tests/**/*.test.{ts,tsx}`. Measure under coverage; if a property takes at least 2,000 ms, move the broad sweep to `*.slow.test.ts` and keep a fixture-scale check in the unit file. ADR-0050 (`docs/adr/0050-exhaustive-tests-run-in-a-separate-slow-lane.md:27-45,59-75`) makes the slow lane push/manual, with no coverage threshold; `vitest.slow.config.ts:22-36` gives it a 180 s timeout. Set an explicit run budget and avoid default arbitrary sizes that overrun CI. No measured fast-check test runtime exists yet, so any CI time claim beyond this lane policy would be speculative.
- Registry metadata checked read-only with `pnpm view` on 2026-11-01: `fast-check@4.10.2` is 1,523,883 bytes unpacked and has one runtime dependency, `pure-rand:^8.0.0`; `pure-rand@8.4.2` is 64,122 bytes unpacked. Thus the minimum package footprint is about 1.59 MB unpacked, plus lockfile entries; there is no dependency or patch currently for either (`package.json:64-90`, `patches/`, `rg fast-check|pure-rand pnpm-lock.yaml` returned none). [npm's fast-check metadata](https://www.npmjs.com/package/fast-check?activeTab=dependencies) corroborates the single dependency. A devDependency does not add a runtime bundle dependency: plan P's A7 forbids runtime additions and explicitly records earlier test-only devDependencies (`docs/plans/20260911-plan-ui-redesign.md:119`). It still adds registry trust, version/lockfile updates, audits and install bytes. D181's `postinstall`/`build` guard (`package.json:9-10`, `scripts/deps/check-patched.mjs:4-18`) protects the existing patched `prosemirror-tables`, not these new packages; run it after the install and confirm the patch remains active. Do not add a fast-check patch.
- ADR-0160 freezes **new user-facing product features** until 0.3.6 (`docs/adr/0160-development-continues-on-master-under-a-feature-freeze-until-0-3-6.md:53-67`), so a test-tool ADR does not itself breach that freeze. ADR-0162 decision 5 freezes changes to audit rounds, auditor set, receipt contract and landing gates (`docs/adr/0162-rework-countermeasures-before-0-3-6-and-a-process-freeze.md:76-84`); the ADR must leave those unchanged. The user still decides when the dependency work is granted.

### Routing rule for the ADR

There will be two TS property-test styles, so state a concrete choice rule: **finite, small event alphabets and bounded lifecycle/interleaving claims use exhaustive enumeration** (D323); **rich value/shape spaces where exhaustive coverage is infeasible and a valid independent oracle exists may use fast-check**; **known bug examples remain named regression tests**. Existing seeded helpers (`tests/support/seededRandom.ts:10-38`, `seededSequences.ts:17-30`) can remain for stable fixture generation and pre-existing tests, but new open-ended random property loops should prefer fast-check when shrinking or compositional generators justify it. Document seed/path replay and the ADR-0050 lane threshold. This prevents “property” from meaning an automatic license to replace complete enumeration.

**Option C** has no new supply-chain or style cost, but keeps the same ad hoc generators for expanding data-shape work. Reconsider A if the first two proposed uses cannot produce a meaningful independent oracle or a counterexample simpler than the existing seeded cases; conversely reconsider B only if D323's bounded exhaustive harness proves infeasible under its measured lane budget or a real race requires a longer, richer trace than §4's >8-event trigger (`docs/plans/20261027-plan-d323-model-property-tests.md:599-600`).

RECOMMEND A
