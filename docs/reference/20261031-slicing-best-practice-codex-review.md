### Claim-by-claim judgment

1. **Vertical ticket as the default — QUALIFY.** A small, self-contained, independently verified change is a sound default for mdpro, and a user-facing path is often the clearest unit of value. Google explicitly presents *vertical, horizontal, file-based, stacked, and mixed* splits in G1; it does not prescribe vertical as the universal default. A CL may be one part of a feature, and Google cautions that an introduced API should have a usage in the same CL. “Every layer” is too literal: a slice should touch only layers needed for the behavior. O1/O2 favor independently verifiable scope and checkpoints, not a one-context-window ceiling. Given newer agent capabilities, a context-window limit is a useful mdpro budgeting heuristic, not a source-backed rule. G1, O1, O2, O3.

2. **Explicit blocking edges and prefactoring first — QUALIFY.** Planning dependencies helps preserve small, working changes. Google recommends planning a multi-CL split and sometimes a preceding refactoring-only CL; it does not say prefactoring must always come first. A preparatory refactor is warranted when it creates a clean seam or testability, and should have its own proof. G1. Meta's stacked diffs provide a way to review dependent increments while the next is being built (M1). mdpro's fast-forward-only policy can land such increments sequentially; no integration branch is implied merely by a dependency.

3. **Horizontal only for wide refactors — DISAGREE.** G1 explicitly recommends horizontal splits for shared contracts/stubs that isolate client, API, service, and model work, and even combines horizontal and vertical cells. Separate test coverage, infrastructure, contract, compatibility, and preparatory refactor changes can also be legitimate small horizontal units. They must stay useful, reviewable, and green when landed. A wide mechanical migration is *one* strong case, not the exclusive case. G1, G3, G4.

4. **Expand–migrate–contract and green batches — AGREE with scope qualification.** P1 supports this for incompatible interface/schema changes and warns that the old form must eventually be removed. G1 says dependent CLs must keep the build working. Google and Meta show that large migrations can consist of many reviewable changes aided by tooling (G3/G4/M1). This pattern is unnecessary for every mechanical rename. A batch that cannot independently preserve tests or behavior needs a new compatibility seam, staged flag, or smaller batch before landing; an integration branch is a local policy question, not an industry best-practice consequence. Meta's gates separate code landing from user exposure (M2/M4), although mdpro would need to justify a flag's maintenance cost.

5. **Vertical implementation equals one RED→minimal GREEN→next; bulk REDs are an anti-pattern — QUALIFY / DISAGREE with the universal label.** G2 and P2 describe the classic one-case cycle and justify it for uncertain behavior because each green step informs the next test. O1 calls for the smallest meaningful red check. Yet A1 explicitly recommends writing tests from expected input/output pairs, confirming they fail, committing them, then asking Claude to implement without modifying them. That is a viable agent workflow when the behavior and independent oracle are already stable. Its risks are test overfitting and brittle imagined interfaces; Anthropic suggests independent verification against overfitting. Thus bulk REDs need a narrower exception and stronger review, not an “anti-pattern” label. Separating tests and code into two *landed* commits may conflict with G1's green-trunk and related-test guidance; A1's commits can remain local until the feature is green. G1, G2, A1, O1, P2.

6. **Design the matrix up front; independently attack it; implement in cycles; amend it — AGREE as a mdpro-specific process, QUALIFY as external evidence.** G2/P2 support planning candidate tests, then selecting one case per cycle. A2 and O2 support observable evidence and stop-and-repair checkpoints. No reviewed source requires an adversarial matrix review or RED receipts; these are mdpro controls whose value should be assessed against defects caught and cycle time. A full matrix should map observable behavior, failure/lifecycle cases, and callers; revise it when a cycle reveals a missing case or false assumption. Keep the attacker independent enough to challenge assertions, not merely check test names. O3 cautions against excessive process context for agents.

7. **Refactor only when green, in the review stage — DISAGREE with “in the review stage.”** G2/P2 put refactoring *inside every red–green–refactor cycle*, after the test passes. Google also recommends a separate CL for substantial refactoring that would obscure a feature change (G1). For mdpro, keep the tree green before refactoring, run affected checks afterward, and split a broad preparatory refactor into its own ticket. Do not defer all cleanup until final review.

### Differences and omissions across the four companies

- **Test timing:** Google's explicit TDD tutorial teaches a single failing test followed immediately by minimal code and refactoring (G2). Anthropic's 2025 agent workflow describes a test-first *batch* followed by implementation (A1); its current docs emphasize evidence and independent review, without prescribing that batch. OpenAI's illustrative Codex workflow asks for the smallest meaningful failing check per phase (O1). Meta's cited guidance requires regression testing at trunk entry but does not prescribe test-first order (M3). These are genuine differences in published workflow, not proof that all engineers at each company follow one method.
- **Change shape:** Google explicitly allows vertical, horizontal, mixed, and stacked CLs (G1). Meta uses stacks of diffs and small incremental trunk changes (M1/M2); neither source mandates full-stack tickets. OpenAI emphasizes milestone scope, verification and externalized state rather than a fixed slice geometry (O1/O2). Anthropic's agent guidance emphasizes an observable target and separate verification (A1/A2).
- **Landing versus release:** Meta's Gatekeeper/MobileConfig lets code land before broad user exposure (M2/M4). This can make a partly implemented feature safe if the dormant path is tested and the flag is later retired. Google insists each submitted CL leave the system working and related test code travel with the behavior (G1). mdpro should not equate “demoable to users now” with “landable”; a preparatory, dormant, or migration slice may be landable without a user-visible demo.
- **AI changes the feedback loop, not the need for small review units.** Anthropic and OpenAI allow agents to execute more work and use independent verification or long-running milestones (A1/A2/O2); neither says a task must fit one context window. OpenAI warns that excessive instructions consume context (O3). Google reports AI-assisted migrations (G3), while Meta uses automation to help keep numerous changes reviewable (M1). The sources support checking actual outputs, tests, and diffs at each checkpoint rather than treating agent completion as proof.

### Revised best practice for mdpro

Plan an outcome and its observable acceptance evidence first; choose the smallest independently green, reviewable, fast-forward-landable ticket, usually a narrow behavior slice but sometimes a contract, coverage, prefactor, flag, or migration slice. Mark dependencies so the delegator lands them in order, use compatibility seams and expand–migrate–contract for incompatible wide changes, and never leave an unverified or broken intermediate commit as a landing candidate. For each ticket, draft an amendable behavior matrix and obtain the independent attack required by mdpro; then prefer one meaningful RED receipt → minimal GREEN → refactor while green → verify before the next case. Permit a test-first batch only when outputs and interfaces are stable and an independent reviewer can show the tests assert observable effects; keep the batch and implementation together as one green landing unit. Have the agent report actual test, build, and audit evidence, and let its milestone size be governed by risk and reviewability rather than a fixed context-window size.
