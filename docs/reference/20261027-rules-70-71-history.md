## 70 - Multi-Session Coordination

**The Claude sessions listed below work on this repo at once. Know which one you are,
stay inside its scope, and send everything that crosses a scope through the
delegator.** Two sessions editing the same file without knowing it, or taking
the same ADR number, cost a rebase or a renumbering every time.

**Under herdr-delegator, [rule 71](../../.claude/rules/71-herdr-mixed-roster.md) replaces only the clauses it
lists: the roster (device roles included), how Codex agents get work and report, their guard, who runs each audit
half and `/security-review`, and who posts round-one reports**
([ADR-0124](../../docs/adr/0124-two-implementation-slots-and-a-herdr-mixed-model-roster-overlays-rule-70.md)).
Everything else here still binds, including landing, the verdict merge, receipts, the Mac mini and device-check batches.

Session names are the `ListAgents` names. Socket addresses change between
runs, so look them up; don't copy them from an old message. If the delegator is
not in the listing, stop and wait; do not ask the user directly or act on an old
message.

### How work is assigned

- **The delegator assigns.** A D item or WI belongs to one session at a
  time. The delegator's assignment message is the record of who owns what;
  the sequencing doc has no owner column.
- **The user may hand a task straight to a session** (an auditor's
  audit is the precedent). That session tells the delegator its scope and the
  files it will touch and **waits for the delegator's reply before it edits
  them**, so the delegator can warn the owners of those files first.
- **Areas are exclusive while claimed.** Don't edit a file in another
  session's claimed area. Example: CSS while an implementor runs a Plan P
  stage, or `file_watcher.rs` / `commands/file.rs` while another is on a
  watcher defect. If you must,
  ask the delegator first.
- **New findings get a D number from the delegator**, not by taking the next
  free row yourself. Report the finding and the delegator registers it.

#### When a session is idle: pull from its queue

**An idle session pulls the next item from its queue instead of waiting**
([ADR-0097](../../docs/adr/0097-idle-sessions-pull-prep-from-a-queue-and-implement-only-under-a-grant.md);
user decision, 2026-10-15: 「Adopt revised (Recommended)」). The delegator
keeps a short queue per session in its assignment messages and in its own
handoff. Each item is tagged `prep` or `impl`.

- **Prep is the default and needs no grant**: reading, read-only
  investigation, scratch documents outside the repo. Tracked edits, heavy
  commands, numbered artifacts and device runs keep their usual controls.
- **`impl` needs a grant**: the queue entry reserves its file scope. Send the
  delegator one line when you start. A path outside the grant needs a
  revised grant first.
- **Deferred items stay `prep`** until the user's priority order makes them
  current.
- **Cap**: one unlanded implementation item per session and **three** machine-wide since
  2026-10-30 ([ADR-0156](../../docs/adr/0156-three-implementation-slots-and-opus-imple-2-joins-the-roster.md); user:
  「Raise cap to 3, all start」). Before that, two machine-wide
  ([ADR-0124](../../docs/adr/0124-two-implementation-slots-and-a-herdr-mixed-model-roster-overlays-rule-70.md),
  superseding ADR-0119's four, with or without herdr; user decision, 2026-10-18: 「decrease slot
  (parallel implementor to 2)」, accepted 2026-10-20). Items already over the cap finish first.
  Dirty, committed, waiting and fix work all count; the auditor's audits do not.
  Under herdr-delegator, one more slot holds a Low-tier item for gpt-imple-3 only
  ([ADR-0133](../../docs/adr/0133-a-third-codex-implementor-takes-low-tier-items-and-every-codex-agent-runs-with-a-context-cap.md);
  rule 71 § Slots).
- **Precedence**: audit fixes on your own work, then the current priority
  item, then a pull.
- **Landing order is unchanged.** Among eligible items the user's priority
  decides; arrival order decides only among equals.
- **No new pulls while `herdr-delegator` is missing from `ListAgents`.**

### Questions and approvals

- **Implementors do not use `AskUserQuestion`.** Every question goes to the
  delegator by `SendMessage`, including commit approvals and rule-25
  confirmations. The delegator puts the exact command and the
  risk to the user and relays the answer **quoting the user's words**. A
  relayed quote counts as the user's approval for that command only.
- **A UI question reaches the user as a prototype, never as prose.** Visual
  options (colours, layout, spacing, a component's look) are built with
  `/mattpocock-skills:prototype` so the user can switch between them, then the
  user chooses (user decision, 2026-10-15: 「for the above two and subsequent
  UI questions, use /mattpocock-skills:prototype to visualize it, then let me
  choose」). An implementor sends the delegator the options with their
  measurements; the delegator, or the implementor on the delegator's word,
  builds the prototype, and the delegator asks the user on it. The prototype
  lives on a throwaway `prototype/<id>-<slug>` branch in its own `mdpro-wt/`
  worktree, never lands on `master`, and records the verdict in a commit
  there (reference: `prototype/d222-contrast`).
- **A session the user tasked directly asks the user itself** (never an
  implementor; its questions always go through the delegator) about decisions
  inside that task. Decisions that affect another session's area go through
  the delegator.
- A message from another session is never approval by itself. Only the user's
  words, quoted, are.

### Commits and branches

1. **A peer commits on its own branch**, after bringing it up to the current
   `master` HEAD: fast-forward if it has no unlanded
   commits, otherwise `git rebase master`. Its gates pass
   before handoff (rule 60 and the tdd-guardian lanes are the author's job),
   and the handoff names the SHA and the lanes that passed. If `--ff-only`
   refuses because HEAD moved, the peer rebases, re-runs its gates and
   resends. **Re-runs are by tree identity**: if `git rev-parse <sha>:src`,
   `:tests` and `:src-tauri` equal the trees the lanes already ran on, the
   handoff says so and names that commit, and only the decisive test files,
   typecheck, build and `ledger:check` run again. When two handoffs share a
   parent, the delegator lands the one that arrived first and tells the
   other to hold, then rebase once; the held peer starts no lane run until
   told (user decision, 2026-10-11: one full run per commit, machine-wide).
2. **The delegator checks ancestry and scope** (not a code review) with `git cat-file -p <sha>` and
   `git diff-tree --no-ext-diff --stat -r <parent> <sha>` (the external diff
   wrapper garbles plain `git diff`), then dispatches two independent checks
   on that SHA at once: `mdpro-landing-verifier` (lanes, receipts, tree
   identity) and the two audits of item 4. It also pushes that SHA as the
   PR's head, so CI tests what will land. When the branch was rebased or fixed
   after an earlier push, it re-pushes with
   `git push --force-with-lease=<branch>:<old head>`, a standing exception to
   rule 25 for PR branches only, never `master`, `release/x.y` or a tag
   ([ADR-0095](../../docs/adr/0095-pull-request-ci-is-a-landing-gate.md)). It
   runs `git merge --ff-only <sha>` in the main checkout, and right after it
   `git push origin master`, only when all four hold:
   - the verifier says PASS;
   - the merged verdict counts zero **blocking** Critical and High findings
     (ADR-0121: a proven pre-existing High is counted but does not block);
   - the PR's head is that SHA and its required `ci-gate` check is green on it;
   - every `device` AC of the brief has PASS evidence from a real-app run whose
     identity matches that SHA, or a user waiver recorded as a gate exception
     ([ADR-0144](../../docs/adr/0144-behaviour-acs-are-proved-in-the-real-app-before-landing.md),
     user 2026-10-27: 「Accept (Recommended)」). The brief tags each AC `unit` or
     `device` and cites its cards in `docs/test/cards/`; the tester role runs the
     cards after round one's code report; the verifier checks the identity. NOT
     EXERCISED is not PASS. Windows `device` ACs stay in batches for now.

   A red result from a registered intermittent test (D196) may be rerun once
   with `gh run rerun <id> --failed`. A second red blocks the landing.
   A docs-only commit that item 4 leaves unaudited also needs no PR and no CI.
3. **No other session lands on `master` itself**, by cherry-pick or
   otherwise. An auditor's fixes reach `master` the way a peer's do: a
   branch rebased onto `master`, handed to the delegator with the SHAs and
   the lanes that passed, landed by `--ff-only`. After each landing the
   delegator warns the peers to fast-forward before their next commit.
4. **Every WI or finished module is audited before it lands**
   ([ADR-0085](../../docs/adr/0085-a-branch-is-audited-before-it-is-fast-forwarded-onto-master.md);
   user decision 2026-10-12: 「只有分支branch 经过Codex audit 并且修复，没有critical /
   high severity findings之后，才允许ff 到master」). When a handoff passes the
   ancestry and scope check, the delegator sends the auditor the branch SHA,
   its parent, the WI or D id and the owner. The auditor audits
   `<parent>..<sha>` under the set that § Which set of
   `docs/agents/audit-dimensions.md` names for the range, pinned at master `<M>` by blob `<B>`,
   with preflight bypassed, model `gpt-6.1-sol` and effort `high`, unless the delegator names others. Nobody
   asks the user first: the user approved this standing order on 2026-10-10
   so that no human sits in the loop. The approval covers the audit run
   only; rule 25 commands still need their own confirmation. A docs-only or
   device-record commit is not audited, except that a change to
   `docs/agents/audit-dimensions.md` goes through a PR, audited at High tier
   under the old pinned blob, with plan review of the proposed blob by both
   auditors before it lands; never a direct docs-only commit. A
   [gate-sensitive decision-log entry](../../docs/agents/decisions/README.md#gate-sensitive-entries) is the other exception:
   both auditors plan-review it before it lands. **Mediums are listed, Lows counted**;
   the verdict ends with one line counting Critical, High, Medium and
   Low, and the delegator reads the gate off that line. Nobody registers
   Medium or Low findings as D items (user decision, 2026-10-10). **A
   Critical or High the auditor downgrades carries a reproduction or a
   counter-proof**: the command and its decisive output, or a run, a
   measured value or a file:line trace showing the ordinary path never
   reaches it, posted next to the finding on the PR and in the report.
   Without one, the finding stays High and fails the gate (user decision,
   2026-10-16: 「后续每次降级都附上复现或者反证」). The
   auditor reports to the delegator, not to the implementor.

   **Every audit runs twice, on the same dimensions** (the second auditor is `opus-auditor` on Opus since
   [ADR-0137](../../docs/adr/0137-the-second-auditor-runs-on-opus-as-the-opus-auditor-pane.md), 2026-10-23; "Fable" below names that
   half as it was first set up)
   ([ADR-0115](../../docs/adr/0115-every-pre-landing-audit-runs-twice-codex-and-fable-on-the-same-dimensions.md);
   user decision, 2026-10-16: 「除了让 codex-audit 来启用 codex Audit 之外，
   还应当由 subagent 启动 fable 进行 Audit，维度参考 Codex audit 的维度，
   保持维度相同，才能互相 challenge」):
   - In the message that sends the Codex request, the delegator dispatches
     `mdpro-fable-auditor` in `audit` mode, with the same range and the same
     dimension set from the pinned file (the set its § Which set names for the range).
   - **Round one is blind** (「不能，先各自单独审」). Neither auditor sees the
     other's verdict, and the delegator forwards nothing between them until
     both are in.
   - **Fable's round-one report gets its own PR comment**, the way the
     Codex auditor posts its own. The delegator posts it as written, once
     both round-one verdicts are in, so the PR never shows it to Codex
     while Codex is still auditing (user decision, 2026-10-17:
     「第一轮fable的audit report，也单独写到对应pr作为comment，其他的不变」).
   - **The delegator merges** the Critical and High findings, one by one:
     - A finding both raise stands.
     - A finding only one raises is challenged. The other auditor gets that
       one finding (Fable in `challenge` mode, Codex by `/cc-suite:continue`
       on its thread) and returns CONFIRMED or REFUTED. A refutation needs a
       reproduction or a counter-proof. Without one, the finding stands.
     - A disagreement that survives the challenge stands too: the gate fails
       closed.
   - The delegator posts the merged verdict on the PR: both count lines, each
     challenge and its outcome, and the merged count.
   - **ADRs and plans**: a plan before its first `impl` grant, an ADR that
     meets [CLAUDE.md § ADR](../../CLAUDE.md#architecture-decision-records-adr)'s
     review trigger before the user is asked to accept it (doubt means review), and a
     [gate-sensitive decision-log entry](../../docs/agents/decisions/README.md#gate-sensitive-entries) before it lands
     ([ADR-0165](../../docs/adr/0165-adrs-record-architecture-and-product-decisions-only.md)
     decisions 2 and 4; [decision log](../../docs/agents/decisions/20261102-adr-scope-and-decision-log.md)), get Codex `/cc-suite:review-plan`
     and an **Opus** reviewer: the `mdpro-fable-auditor` definition in `plan`
     mode, dispatched with `model: "opus"`. Each runs, by request file (rule 71), the set
     the pinned file's § Which set names for that case: plan; plan + policy at Full for a
     gate-sensitive entry ([policy set](../../docs/agents/decisions/20261102-cc-suite-policy-set.md)). Blind and merged the same way.
     Fable itself reviews PRs only
     ([ADR-0118](../../docs/adr/0118-three-implementation-slots-and-opus-reviews-adrs-and-plans.md);
     user decision, 2026-10-17: 「Fable只参与审计pr，不参与adr等其他的」).

   **Zero Critical and zero High in the merged verdict is the landing
   condition.** A Critical or High goes to the owner on the same branch: the
   owner fixes it there (new SHA, rebased if `master` moved, decisive tests
   re-run). **Both** auditors then confirm the fix on the new SHA (Fable in
   `confirm` mode), each scoped to every open finding from either side, not
   a fresh full audit (「Both, scoped (Recommended)」). One auditor's OPEN or
   PARTIAL is challenged like a one-sided finding. Then the verifier
   re-checks by tree identity, and the delegator lands. **At most three
   rounds**: the first audit and two confirms
   ([ADR-0120](../../docs/adr/0120-a-pre-landing-audit-runs-at-most-three-rounds-then-the-user-rules.md);
   user decision, 2026-10-17: 「规定以后codex audit最多2个round」, settled as
   「Audit + 2 confirms」 for both auditors). A Critical or High still open after
   round three gets no fourth round. The delegator brings it to the user, who
   rules, and the ruling is quoted in the row.

   **After the cap** ([ADR-0129](../../docs/adr/0129-a-high-that-survives-the-audit-cap-is-classified-tracked-and-expires.md);
   user decision, 2026-10-21: 「采纳 (Recommended)」):
   - **The ruling request** classifies each open finding:
     - introduced or pre-existing;
     - reproduced or disputed;
     - product or tooling;
     - its impact.

     It offers five options: fix with a scoped confirm, narrow or revert, reconsider, refuted, or
     land open.
   - **Landing a finding open** needs a record:
     - a D row with an owner;
     - a fix-by version number;
     - a compensating control, or "none" with the reason;
     - for product code, a `CHANGELOG.md` Known issues line;
     - the quoted ruling.

     A Critical's fix-by is the lowest unreleased version, and it is never carried.
   - **A post-cap fix** is confirmed by each detector that raised the finding, on the fix diff
     only. It lands only if every raiser marks it CLOSED. Otherwise it goes back to the user once,
     and no second fix is offered.
   - **Every release checkpoint** runs each tracked finding's presence check on the locked SHA.
     Ancestry does not count.
   - **Every gate exception** (lane, receipt, unrunnable check) gets a row in
     `docs/audit/audit-log.md` § Gate exceptions, whenever it is granted.

   **Effort follows risk** ([ADR-0121](../../docs/adr/0121-audit-effort-follows-risk-pre-existing-findings-do-not-block-and-auditors-are-measured.md); user decision,
   2026-10-18: 「Accept with revisions (Recommended)」):
   - **Tier.** The delegator names a tier for each range in the audit request, and either auditor
     may raise it:
     - **High** (document save, close, draft or sync behaviour, MCP approval, preference writes,
       `src-tauri`, `src/services`, CI, release, gate tooling, dependencies, any unlisted path):
       both auditors, on the set the pinned file's § Which set names for the range, in the pinned
       `docs/agents/audit-dimensions.md` blob `<B>`.
     - **Medium** (other `src/`): both auditors, on the set § Which set names, as above.
     - **Low** (CSS, docs except `docs/agents/audit-dimensions.md`, presentation-only tests):
       Codex alone, on the set § Which set names, with Fable challenging each Critical or High it raises. A change to the
       excluded file is High tier.
   - **Base.** The base is the PR's fork point on `master` (`git merge-base`). It moves with each
     rebase.
   - **Pre-existing.** A *Pre-existing* High needs three things before it stops blocking:
     - proof: the code is unchanged at the base, a caller trace shows the PR does not reach or
       worsen it, and the PR claims no such property;
     - the other auditor's affirmative confirmation;
     - a linked D row with an owner.

     A pre-existing Critical still goes to the user.
   - **Confirms** review the fix diff (a `git range-diff` across a rebase) and every open finding.
     A Critical or High that any PR commit introduced blocks, whatever round finds it.
   - **Count line.** It carries raw counts plus a blocking count, and the gate reads the blocking
     count.
   - **Records.** The delegator records every audited range in `docs/audit/audit-log.md` and every
     escaped defect in `docs/audit/escapes.md`.

   A partial fix does not land; deferring a Critical or High instead of fixing
   it needs the user's word, quoted in the row. Audits requested before
   2026-10-12 on already-landed ranges finish under the old order: a
   Critical or High there gets a D number and goes to the owner, and the
   landed commit is not reopened.
5. The sequencing-doc row and the ledger row change in the same commit as
   the behaviour they describe. A peer edits **only the D and WI rows it owns**. The
   shared release-freeze paragraph belongs to the delegator.

**Only the delegator lands on `master`**, by `git merge --ff-only`, and it
pushes `origin master` right after every landing (user decision, 2026-10-12:
「落地即推」). No one else pushes, and no one else commits to `master`.
`master` never takes a merge commit, and the only direct commits on it are

### Session rotation

**A session that has been compacted many times writes a handoff and is
rotated.** Each compaction drops a layer of detail. After enough of them the
session works from summaries of summaries, which is how verified facts turn
into guesses. The model cannot count this reliably itself, so a hook counts for
it. (User decision, 2026-10-10.)

- **The PostToolUse hook `.claude/hooks/session-size-guard.sh`** reads the
  session transcript and warns once per level:
  - **soft** at 5 compactions: rotate at the next WI or D boundary;
  - **strong** at 10 compactions, or at a transcript of 25 MiB or more:
    rotate as soon as the current step is done.

  The user sees the message. The session gets the same instruction as
  context.
- **On a warning, write the handoff before anything is lost.** Put it at
  `~/.mdpro-redesign/handoff/<alias>-<YYYYMMDD-HHMM>.md`. It names:
  - the current WI or D and its stage;
  - the branch, its HEAD and whether it is landed;
  - uncommitted state (save a patch next to the handoff rather than
    committing half a step);
  - the next concrete step;
  - ADR and D numbers held;
  - open questions and pending messages from other sessions.

  Verify each fact in it with a command; don't copy it from memory.
- **An implementor or auditor then sends the delegator the handoff path.**
  The delegator writes its own handoff the same way and tells the user.
- **The user chooses one of two ways to rotate.** Both start from the same
  handoff file, e.g.
  `~/.mdpro-redesign/handoff/mdpro-85-20261010-1051.md`.

  | | **A. `/clear` in place** | **B. New session** |
  |---|---|---|
  | How | In that session, type `/clear`, then 「读 `~/.mdpro-redesign/handoff/mdpro-85-20261010-1051.md` 继续」 | Close the old one. Start a new one with the same role (`MDPRO_ROLE=implementor claude`) and the same permission mode as the other sessions, then send the same 「读 … 继续」 |
  | `ListAgents` name | Usually kept; nothing to update | New alias: the delegator updates the alias table above in its next commit |
  | Worktree and branch | Kept; work carries on in them | The successor gets a new worktree, or the old one is handed over. A retired session's worktree is removed only after its handoff is archived and the user confirms (rule 25), except a landed per-item worktree (ADR-0157) |
  | Use when | The same session carries on the same area | The role changes, the area is handed to someone else, or the session itself misbehaves |

  The transcript starts fresh either way, so the hook's counts start again
  from zero.

### Briefs and self-acceptance

**The delegator gives a Codex implementor a full brief, the implementor accepts its own work
against it, and only then does the delegator confirm.** A cross-model agent shares none of the
delegator's context. User decision, 2026-10-18: 「由于是cross model delegate tasks,
之后给implementor 布置任务，要详细交代任务背景，给出详细的验收标准，让 implementor执行完之后，自己验收合格再由你确认」.

Every grant, and every fix round, is written to
`~/.mdpro-redesign/herdr-spike/<name>/<item>-brief.md` before the prompt points at it. It has
six sections:

1. **Background.** Why the item exists: the defect or plan row, the user decisions it rests on
   (quoted), the ADRs it must not contradict, and what earlier work already landed.
2. **Scope.** The worktree, the branch and its base SHA, and the paths it may edit and create.
   Anything outside them needs a revised grant.
3. **Acceptance criteria**, numbered `AC-1…`. Each is a behaviour plus its proof:
   - the test file and case, or the command;
   - the expected decisive output;
   - for a behaviour change, the receipt id of the RED that must come first.

   The plan row's tests column is the floor, not the ceiling.
4. **Out of scope.** What this item must not do, and which later item does it.
5. **Gates.** The lanes to run before handoff, with the exact commands.
6. **Self-acceptance.** The handoff ends with an `AC | evidence | verdict` table: each AC with the
   command or test it ran, its decisive output line, and its receipt and verdict. Then come the
   lanes, the tree SHAs and the paths changed.

**A test matrix is attacked before any RED is recorded** (user decision, 2026-10-20: 「加上，
gpt-imple-1, gpt-imple-2都适用」, after the delegator found that the herdr flow skipped
`/tdd-guardian:workflow`'s design-tests and spec-adversary steps). That day all three blocking Highs
were cases nobody had tested:
- M3b H1: a submit that fails inside a table;
- D290 H1: a close while a save awaited;
- D290 H2: a deletion ignored mid-batch.

It works in four steps inside the implementor's run of
`$tdd-guardian:tdd-guardian-workflow` (current user decision, 2026-10-24). The previous
`.codex/skills/mdpro-tdd-workflow/` port is retained only for historical handoffs.
**A Claude implementor runs the same four steps without the plugin**, which is disabled for Claude Code at project scope
(user, 2026-10-30: 「Disable + narrow cleanup (Recommended)」; 2026-10-31: 「修复 PR #564 的 High」). Codex's own install is
unaffected:
1. **Design tests.** The plugin's design-tests stage writes and attacks the test matrix before implementation.
   The implementor also records the matrix under
   `~/.mdpro-redesign/herdr-spike/<name>/<item>-test-matrix.md` for the delegator. For each AC it lists:
   - success;
   - boundary (empty, max, CJK);
   - invalid input;

2. **Independent matrix attack.** The plugin's spec-adversary attacks the completed matrix.

  - it is expected to take more than one PR;
  - it needs an ADR.
- **Exempt,** as long as they add no capability or contract:
  - D-item fixes that restore stated behaviour;
  - audit fix rounds;
  - CI, receipt and test-only repairs;
  - docs-only work.

## 10 - TDD Workflow

Vitest + jsdom (frontend) and `cargo test` (Rust). Run `pnpm test:run`
or `cd src-tauri && cargo test` before commit.

### Core discipline

**Work RED → GREEN → REFACTOR** — a test you never saw fail proves nothing.
Bug fixes MUST include a regression test that fails without the fix and
passes with it.

### When tests are required

| Category | Required? | Notes |
|----------|-----------|-------|
| Stores (`src/stores/`) | **Yes** | State transitions, selectors |
| Hooks (`src/hooks/`) | **Yes** | Side effects, lifecycle |
| Utils / parsers / formatters | **Yes** | Pure functions |
| Rust commands (`src-tauri/src/commands/`) | **Yes** | Input validation, error paths |
| Business logic (close, save, merge) | **Yes** | |
| Bug fixes | **Yes** | Regression test |
| Edge cases (empty, null, max, concurrent) | **Yes** | Bugs live at boundaries |
| Components | Case-by-case | Test behavior (clicks, ARIA), not rendering |
| Plugins (Milkdown / CodeMirror) | Case-by-case | Test extracted logic, not editor DOM |
| CSS-only | No | Visual QA in both themes |
| Docs / config / type-only | No | |

### Anti-patterns

- **Mock only at boundaries** (Tauri, network, fs) — mocking the logic under test makes the test assert its own mock.
- **No snapshot tests for logic** — snapshots get auto-updated without review; use explicit assertions.

### mdpro-specific patterns

- **Stores**: reset with `useXStore.setState(...)` in `beforeEach`. Call actions via `useXStore.getState()` — no React rendering needed.
- **Hooks**: use `renderHook` from `@testing-library/react`. Mock `@tauri-apps/api/event` and `@tauri-apps/api/core` at boundaries.
- **Components**: query by ARIA role/name, not CSS class. Use `userEvent`, not `fireEvent`.
- **Plugins**: extract testable logic from plugin wiring; test transforms and state changes, not editor DOM.
- **Rust commands**: every `#[tauri::command]` returns a `Result` (error type is `String` or a serializable enum such as `FileError`); test the error path explicitly.

### File placement

**Put frontend tests under `tests/`** — `vitest.config.ts` includes `tests/**/*.test.{ts,tsx}`, so both `.test.ts` and `.test.tsx` are discovered, but only inside `tests/`. A test anywhere else — co-located under `src/`, or in a feature-local folder — never runs.

**Its folder is chosen by the system it tests, never by its filename** ([ADR-0098](../../docs/adr/0098-launcher-tooling-and-perf-tests-move-into-their-own-folders-under-tests.md)):

| Folder | A test goes here when |
|---|---|
| `tests/control/` | its system under test is `scripts/control/**` or the launcher (`control-*`, or any file whose imports or read paths reach `scripts/control`) |
| `tests/tooling/` | it imports nothing from `src/`, and it tests repo tooling: `.github/` workflows and scripts, `.claude/hooks`, `scripts/{ci,ledger,lint,release,device}`, `heavy-lock`, the vitest configs |
| `tests/perf/` | it is a `*.perf.ts` run by `vitest.perf.config.ts` (`pnpm perf:d12`), or that harness's helper |
| `tests/` (root) | everything else: app behaviour |

Control wins over tooling, and both apply only when the file imports nothing from `../src/`; a test that reaches app source and tooling stays at the root, as does anything in doubt. `tests/support/`, `tests/helpers/`, `tests/setup.ts` and the fixture folders stay where they are. Old paths in receipts, ADRs and closed rows resolve through `docs/reference/adr-0098-test-move-map.json`.

### Environment and the slow tier

- **jsdom is the default; a DOM-free file opts into node** with `// @vitest-environment node` as its first line. `tests/setup.ts` then makes any first-party read of `window`, `document`, `navigator` and the rest fail the file — if it trips, remove the marker rather than stubbing around it ([ADR-0049](../../docs/adr/0049-dom-free-test-files-opt-into-the-node-environment.md)).
- **An exhaustive, property or cost-enumeration test that takes ≥ 2 s under coverage goes in a `*.slow.test.ts` sibling.** The default run and the per-commit `unit` lane exclude it; `pnpm test:slow` and the tdd-guardian `slow` lane (push / manual) run it. Share the domain through `tests/support/`, never by copying it ([ADR-0050](../../docs/adr/0050-exhaustive-tests-run-in-a-separate-slow-lane.md)).

**Format before you record.** A Rust red goes through the same entry, on
`rustfmt`-clean test files: `cargo fmt` first, then
`node scripts/tdd/red-receipt.mjs record --id <ID> --lane rust --test src-tauri/<file>.rs`.
`cargo fmt` is never run between record and verify: the receipt fingerprints
the file's bytes, and a later reformat breaks it for good (D187). The entry
checks this itself and refuses the record, naming each Rust file that is not
`rustfmt`-clean at the crate's edition (ADR-0145 d8). The PreToolUse hook
`.claude/hooks/receipt-rustfmt-guard.sh` still refuses a direct `receipt.js record`
that would hash one.

For frontend RED receipts, run `scripts/heavy-lock.sh --guard-only node scripts/tdd/red-receipt.mjs record --id <ID> --test tests/<file>.test.ts`;
after GREEN, run the same guarded command with `verify --id <ID>`. The focused
`unit-red` lane is unlocked and uses at most 2 workers with a 1024 MiB worker
heap inherited from the outer guard; the full unit coverage
lane still runs before commit. Using direct receipt.js bypasses the entry script's
selection guard and is a residual risk, so it is not a supported frontend path.

**The entry keeps evidence for both lanes** (ADR-0145 as amended by ADR-0149):
- the failing ids, each with its kind, location and message;
- the RED-time test tree, pinned under `refs/receipts/`;
- a sidecar, `.claude/tdd-guardian/evidence.json`.

`verify` routes any byte change of a spec file since RED to evidence, even when the plugin holds,
and `check-pending` judges every lane. `node scripts/tdd/red-receipt.mjs replay --id <ID>` prints
the diffs and replays the RED against the PR base. See
[`docs/guide/receipt-evidence.md`](../../docs/guide/receipt-evidence.md).

**The receipt engine is vendored at `scripts/tdd/vendor/tdd-guardian-0.10.2/`** (#566). The entry runs it from
there and never reads a plugin cache under `~/.claude` or `~/.codex`; a missing or unloadable engine file stops it
with the path named. Upgrading the engine is a reviewed diff of that directory (its README pins each file's SHA-256),
never a side effect of a plugin update.

### How much to run, and when

Several sessions share one machine, so **run the full suite once per commit,
not once per step**. The full unit lane (413 files, with coverage) and two
`cargo test` builds are the heaviest jobs here, and repeating them is most of
the CPU load.

| When | Run | Coverage |
|------|-----|----------|
| RED → GREEN while writing a WI | Only the affected files through `VITEST_MAX_WORKERS=2 scripts/heavy-lock.sh --guard-only pnpm exec vitest run tests/<files>` | Off |
| Once, just before each commit | The full `unit` lane, plus typecheck and build **under the lock**: `scripts/heavy-lock.sh sh -c 'pnpm -s typecheck:tests && pnpm -s build'` | On (the gate reads it) |
| Only when `src-tauri/` changed | The `rust` and `rust-verify-run` lanes | — |
| After a rebase or fast-forward that only brought docs or `.claude` changes | Nothing new: `src/` and `tests/` are tree-identical, so the earlier gate still holds. Re-run only the tests touching any conflicted file | — |
| After a rebase or fast-forward that brought a `patches/` or lockfile change | `pnpm install --force --frozen-lockfile --offline` first, in every worktree you build in: the D181 guard refuses a build whose `node_modules` predates the patch set (2026-10-13, D192's patch landing broke adr047's and the main checkout's builds) | — |

- **Every heavy command goes through `scripts/heavy-lock.sh`**: vitest
  with coverage, `tsc`, `pnpm build`, `cargo test`, `tauri build`. A command
  outside the lock runs in parallel with another session's locked job, so the
  lock only stops half of the overload.
- **A full run happens once per commit.** When a subagent has already run the
  full lane on the exact tree being committed, the session reviewing its work
  reads that log and re-runs only the decisive test files. Run it again only
  if the tree changed after that run.
- **An unlocked partial run takes at most 2 workers and the guard-only monitor.** The RED → GREEN
  runs in the first row are outside the lock, so three sessions doing them at
  once stack their workers on the same cores; on 2026-10-11 the machine sat at
  load 45 on 10 cores with one locked lane running. Since D147 (`bce24d3`)
  `vitest.workers.ts` makes 2 the default; a locked run also defaults to 2
  after ADR-0151's measurement, and an explicit override is clamped to its
  measured cap. Guard-only workers get a 1024 MiB V8 heap. A worker heap
  failure is reported as a test failure, never retried. Exit 76 is a load-guard
  infrastructure stop; callers follow [the retry rule](../../docs/guide/load-guard.md).
- **Two handoffs on the same parent cost one full run, not two.** The one
  that arrived first is verified and landed; the other waits for that landing,
  rebases once, and is verified by tree identity (rule 70 § Commits). A peer
  does not start a lane run on a handoff it has been told to hold.
- Need the machine for something else? Keep the 2-worker default or use one
  worker. The cost is a longer run.

- **Topic** is one of a closed set, listed in the file's header. A new topic is added to the header
  first.
- **Where to read more points at the durable home.** A reusable how-to answer that has no home yet
  gets one under `docs/guide/` or `docs/knowledge/`, in the same commit.
- **The delegator maintains it** and commits it to `master` as a docs-only
  commit. It batches these commits while a code handoff is in flight, so
  `master` does not move under the handoff.
- **Every other session reports its own.** When the user asks a session a
  question directly, that session answers, then sends the delegator one
  message: the question verbatim, the answer condensed to one to four
  sentences, and a pointer to anything longer. The delegator applies the
  criteria above and records it or not.
- **One entry per question, newest first.** Each entry has the date, the session it was asked in,
  Kind, Topic, the question quoted exactly, the condensed answer, and where to read more.
  A corrected answer is a new `Correction` entry naming the one it corrects.
  Rows are not edited after commit. The one-off 2026-10-20 cleanup moved status rows,
  verbatim, to `docs/reference/user-question-and-answer-archive.md`.

### Feature Ledger

[`docs/feature-ledger.md`](../../docs/feature-ledger.md) is the inventory of **what
mdpro has right now**: every capability, its state, where the code is, and how to
confirm it in the running app. `docs/feature-ledger.html` is the rendered view —

  `pnpm ledger:build` when the markdown changes. The gate gives three answers:
  every path claim resolves, every state cell is in the enum, and every declared

  third is the one that catches a surface nobody wrote a row for.

  items (ADR-0148). Why → `docs/adr/`.

### Architecture Decision Records (ADR)

**A repository-wide ADR records a decision about the product or its architecture**
([ADR-0165](../../docs/adr/0165-adrs-record-architecture-and-product-decisions-only.md)
decision 1; [decision log](../../docs/agents/decisions/20261102-adr-scope-and-decision-log.md)):

- **Scope.** An IPC or MCP contract; a persisted format or preference key; a
  dependency added or refused; a rendering surface or editor engine; platform and
  release scope, including what a release workflow ships; accepting a known
  product defect; deciding **not** to build something.
- **The test.** Would a user of the released app, or a contributor reading product
  code, see the difference? If yes, it is a product decision.
- **Not an ADR:** how the work is done (the roster, slots, audit shape and rounds,
  receipts, locks on machine load, model and effort routing, brief and handoff
  formats, CI lane layout). Each goes to one file in the
  [decision log](../../docs/agents/decisions/README.md). A decision that reaches for
  `AskUserQuestion` is not, by that fact alone, ADR-worthy.
- **Mixed cases** (both product and process) get an ADR, and their process half is
  a log entry pointing at it.
- **Who classifies.** The delegator, before reserving a number; the planner
  proposes for a feature. Doubt goes to the ADR route and to the user.
- **Below the bar.** A product decision too small for an ADR is recorded where it
  is made: the D row, the spec snapshot or the ledger row.
- **One feature's decisions** stay in its spec snapshot under local ids
  `<prefix>-r<N>-D<n>` (rule 12), unless they are on the scope list above.
- **Location**: `docs/adr/NNNN-kebab-title.md`, numbered sequentially from
  `0001`, never renumbered and never deleted.
- **Structure** (Nygard): `# NNNN. Title` → **Status** → **Enforced by** →
  **Context** → **Options considered** → **Decision** → **Consequences**. Every
  new ADR's "Enforced by" line names the lint, test, gate or config that holds the
  decision, or says plainly that nothing does. Context states the
  forces *as they were understood at the time*, not as they look in hindsight.
  Options considered names every option that was on the table, with the reason
  each losing one lost; a record without them cannot stop the re-litigation it
  exists to prevent. Keep it to a page where you can; evidence (log lines, device
  runs, probe output) goes in a linked record under `docs/test/` or
  `docs/reference/`, not in the ADR.
- **Status** is one of `Proposed` / `Accepted` / `Rejected` /
  `Superseded by ADR-NNNN` / `Deprecated` / `Drifted` / `False in practice`. Date
  every status change, and on
  `Accepted` or `Rejected` say **who decided**, quoting the user's words when the
  user did. `Rejected` keeps a proposal that was turned down, with the reason, so
  it is not proposed again from scratch. `Drifted` and `False in practice` are
  dated lines with a link to the evidence, added without a superseding ADR.
- **An accepted ADR's body is immutable.** Only its Status line and a forward
  link (`Superseded by ADR-NNNN`, `partially superseded: <clause> by ADR-NNNN`,
  `Current text: <rule>#<anchor>; folded by ADR-0165` for a clause moved unchanged,
  or `Current text: <rule>#<anchor>; folded and changed by docs/agents/decisions/<file>`
  for a changed one) may change after acceptance. Changing your mind on a repository-wide ADR writes a
  **new** ADR that supersedes the old one, in whole or for a named clause, and links
  back; both stay in the tree. (A process ADR's unfolded clause is folded in
  instead: see Existing records below.) Editing an accepted record destroys the evidence of why the
  earlier decision looked right at the time — which is the only thing that stops
  it being remade by accident. (Rules amended 2026-10-11 after the vendor
  comparison in `docs/reference/20261011-adr-criteria-best-practices.md`;
  ADRs accepted before then keep their shape.)
- **Review.** Plan review by both auditors is required when the ADR touches
  `src-tauri/`, `src/services/`, a persisted format or preference key, an IPC or
  MCP contract, or a dependency; when it spans more than one PR; or when the user
  asks. Otherwise it lands with the user's quoted acceptance. The delegator records
  the classification in the Status line, and doubt means review (ADR-0165
  decision 4).
- **Existing records** are not rewritten or renumbered (ADR-0165 decision 5). A
  process ADR up to 0164 governs each clause until that clause is folded into a
  rule while ADR-0147 is carried out; the folded ADR stays `Accepted` and gains the
  dated "Current text: `<rule>#<anchor>`; folded by ADR-0165" line. ADR-0159 finishes under the old flow. Changing a
  clause that is not yet folded in takes no new ADR: the change folds the clause
  into its rule with a decision-log entry recording the new decision (plan review
  by both auditors when it is
  [gate-sensitive](../../docs/agents/decisions/README.md#gate-sensitive-entries)), and
  the old ADR gains "Current text: `<rule>#<anchor>`; folded and changed by
  `docs/agents/decisions/<file>`", naming that entry ([entry](../../docs/agents/decisions/20261102-changing-an-unfolded-process-adr-clause.md)).
- **Record the costs, not just the benefits.** An ADR whose Consequences section
  lists only upsides is advocacy, not a record. Name what the decision gives up
  and what it forecloses.
- Plans and rules **link** to ADRs rather than restating the reasoning. When a
  plan and an ADR disagree, the ADR is the decision and the plan is corrected.

Decisions already taken for the in-flight redesign still live inline in
`docs/plans/` (E26, E29 Stryker-not-adopted, E39 no-benchmarking-harness, the

conversion produces records nobody wrote and nobody trusts. Promote one when it

### Zustand Patterns (MANDATORY)
- NEVER destructure store values at component top-level — use selectors.
  BAD:  `const { mode } = useEditorStore()`
  GOOD: `const mode = useEditorStore(s => s.mode)`
- Inside callbacks/event handlers, use `useXStore.getState()` — never read stale closure state.
- All stores use `create<State>()` with explicit TypeScript generic — never untyped.

### Tauri IPC Rules
- Every `#[tauri::command]` must return a `Result` — never `unwrap()`/`expect()` on user input. The error type is `String` **or** a `Serialize` enum such as `FileError` (`src-tauri/src/commands/file.rs` uses the latter); both are valid.
- Log every command with Start + Success/Fail pairs using `logger::log_event()`.
- A new command must be registered in `src-tauri/src/commands/mod.rs` → `handlers()`, and needs a typed `invoke()` wrapper in `src/services/`. It does **not** need an entry in `src-tauri/capabilities/default.json` — that file carries only `core:*` and plugin permissions (`opener`, `updater`, `process`), not application commands.

### Logging (MANDATORY for all new features)
- TypeScript: use `loggingService.logEventSync()` — never `console.log()` in committed code.
- Rust: use `logger::log_event()` — never `println!()` / `eprintln!()` in committed code.
- Every significant user action needs: `[ActionName] Start` → `[ActionName] Success/Fail`.
- Include `actionId` in every log call.

### Styling Rules
- Default to CSS variables (`--color-text`, `--color-bg`, etc.); do not hardcode hex/rgb/rgba colors. Sanctioned exceptions exist and are not review findings: `.claude/rules/31-design-tokens.md` "Acceptable hardcoded values" (e.g. `rgba()` fallback lines preceding `color-mix()`, defensive `var(--xyz, #fallback)`) and `.claude/rules/34-dark-theme.md` "When overrides are needed" (per-theme raw `rgba()` for translucency where the source color must flip). Prefer `color-mix(in srgb, var(--color-text) N%, transparent)` over raw rgba; if no token exists, add it to both theme files first.
- Plugin styles live ONLY in their colocated `<name>.css` file, not in `src/styles/globals.css`.
- Theming uses `.theme-light` / `.theme-dark` class selectors on the root (not `[data-theme]`); see `.claude/rules/34-dark-theme.md`.

### Code Review Guidelines (for `@codex review`)
Source of truth is `.claude/rules/60-review-checklist.md`; use its four labels, not P0–P3:

| Label | Meaning | Action |
|---|---|---|
| **BLOCK** | Data loss, security, or silent failure | Must fix before merge |
| **MUST** | Rule violation or correctness issue | Fix in this PR |
| **SHOULD** | Code quality or test gap | Fix now if cheap; otherwise file an issue |
| **NOTE** | Observation | No action; mention in the PR description |

Report BLOCK and MUST always. Report SHOULD only when the fix is concrete and cheap.
NOTE is optional. The six universal discipline rules in `.claude/rules/30-ui-consistency.md`
are review-blocking: a violation is at least **MUST**.

Treat these as BLOCK (must fix before merge):
- Tauri `#[tauri::command]` that trusts frontend input (paths, IDs, strings) without
  validation, or uses `unwrap()`/`expect()` on user-supplied data. Commands must return
  a `Result` (error type `String` or a `Serialize` enum such as `FileError`).
- MCP tool handlers that touch the shadow store or emit events without validating args.
- Save/draft paths that can silently discard dirty content, or overwrite a newer draft
  with an older one. Document close with unsaved changes must prompt, never silent-discard.
- Async commands touching shared state (file watcher, shadow store, draft timer) without
  `Mutex`/`Arc<RwLock>` guarding.
- Frontend `listen()` handlers closing over Zustand state instead of `useXStore.getState()`
  (stale-closure bug).
- Auto-save firing after document close; un-debounced file-watcher reloads.
- Rust `match` with `_ => {}` that silently drops cases; non-exhaustive TS discriminated
  unions; a new `menu:action` value with no handler in `useMenuEvents.ts`.
- Events emitted to the frontend that leak secrets or non-serializable data.

Treat these as SHOULD (comment, do not block; omit if the fix isn't obvious):
- `console.log`/`println!` in committed code (use the logging service), magic numbers,
  dead code, files over ~300 lines, missing tests, a behaviour change that didn't rewrite
  its `docs/feature-ledger.md` row.

Do not flag style nits below NOTE. Keep reviews focused on correctness, data loss,
and trust-boundary risks.
