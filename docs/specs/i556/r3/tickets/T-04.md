## What to build

**Where rows are read.** The command reads the audit log's Gate exceptions section from the fetched `origin/master`,
never the working tree. Every row is read in the new grammar only:
- its Closed cell is empty or `open`;
- its Gate waived cell starts with a check token from `verifier | auditor:gpt | auditor:opus | security | ci-gate |
  device:<AC>`, then `:`;
- its Ruling cell quotes the user in 「…」 or “…”.

Old rows stay as written and match nothing.

**Two ways a row counts.**
- **`--exception <id>`**, repeatable. It is accepted only for a `this landing only (PR #<n>, <sha40>)` row that names
  this PR and the landing SHA, or for a post-cap row. Its token must name a failing check, and it waives that one check.
  A `device:<AC>` row is how a DEVICE entry `<AC>=waived:<id>` is accepted, and its id must be among the
  `--exception` ids.
- **Carried by the verifier.** A row with PR `any` and an open `until <condition>` scope counts only when the verifier
  record says `VERDICT PASS` and lists the row's id on its `CARRIED` line, and only while the row is open. Through
  `--exception` it is refused. A carried `ci-gate` row is refused.

**Post-cap rows.** These have the check token `auditor:<name>`, name this PR, quote the user's ruling, and take one of
four scopes:
- **`post-cap raiser-confirm <pre sha40> → <landing sha40>`** (ADR-0129 decisions 6 and 7). The named auditor is the
  non-raiser. Three things must hold:
  - (a) its last report ends at the pre-ruling head, and is clear;
  - (b) the landing SHA descends from the pre-ruling head, or is an accepted rebase of a commit that does;
  - (c) the raiser's clear confirm ends at the landing SHA, and its range starts at or before the pre-ruling head.
- **`post-cap no-round <pre sha40> → <landing sha40>`** (ADR-0143 decision 3, a fix with no further round). It takes
  one row per auditor. Each named auditor's last report ends at the pre-ruling head, and its blocking count is not
  read. (b) must hold. The verifier and `ci-gate` still gate.
- **`post-cap land-open <sha40> D<n>[, …]`** (ADR-0143 decision 3 with ADR-0129). The named auditor's blocking
  Critical plus High may be at most the number of D rows listed.
- **`single-auditor <sha40>`** (ADR-0143 decision 4). The named auditor's report is not required. The other's must be
  clear at the SHA.

A post-cap landing needs `--item`.

**Docs.** The ticket edits two documents to match:
- the audit-log § Gate exceptions header, which today describes only `this landing only` and `until`. It gains the
  check tokens, the `post-cap` forms and the carried rule;
- the delegator's `merged-verdict-template.md`, which gains the post-cap row form for a recorded ruling.

There is no other bypass flag.

## Acceptance criteria

- [ ] A failing check with a valid matching `this landing only` exception lands, and the output names each exception
      used. Two exceptions covering two failing checks land.
- [ ] Each of these is refused:
      - an exception id with no row;
      - a row for another PR;
      - a row for another SHA;
      - a closed row;
      - a row without quoted user words;
      - a row whose check token differs from the failing check;
      - a row present in the working tree but not on `origin/master`.
- [ ] An open `until` row with PR `any`, passed by `--exception`, is refused. The same row lands when the verifier record
      says `VERDICT PASS` and lists it on `CARRIED`. A carried row that is closed is refused. A carried `ci-gate` row is
      refused.
- [ ] A `security` exception for this landing lets a High-tier landing pass a missing security line.
- [ ] A raiser-confirm row for `auditor:opus` lands when opus's clear last report is at the pre-ruling head and gpt's
      clear confirm covers `pre..landing`. These are refused, each naming `auditor:opus`:
      - the same evidence without the row;
      - opus's pre-ruling report not being clear (a);
      - a landing SHA not descended from the pre-ruling head (b);
      - gpt's confirm not covering the pre-ruling head (c).
- [ ] No-round rows for both auditors land with the verifier and `ci-gate` present, and are refused without the
      verifier.
- [ ] A land-open row with one D row lands a report counting BLOCKING H1. The same row with a BLOCKING H2 report is
      refused.
- [ ] A single-auditor row lands with only the other auditor's clear report at the SHA.
- [ ] A waived device AC lands with `<AC>=waived:<id>` and a valid `device:<AC>` row among the `--exception` ids. It is
      refused without the row, or when the id is not passed.
- [ ] An old-format row (a fixture copy of G551-1) matches nothing.
- [ ] Without an exception, every failing check still refuses (no default bypass).
- [ ] The audit-log § Gate exceptions header and `merged-verdict-template.md` describe the new grammar. A fixture row in
      each documented form parses.
- [ ] Proved at the landing-command process seam, with a fixture audit log committed on the fixture origin's `master`.
