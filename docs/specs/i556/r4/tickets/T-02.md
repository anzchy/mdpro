## What to build

The landing command now also requires the auditors' clearance for the exact SHA.

**Discovery.** For each auditor, the command finds the report:
- with `--item`: the highest-round `<item>-r<n>.md`. For records written before rollout, the `r<n>pc` and `r<n>postcap`
  forms also count. A `pc`/`postcap` file outranks the plain file of the same round;
- without `--item`: the highest-round report whose VERDICT head names the SHA.

**Parsing.** The command parses the report shape that `docs/agents/audit-dimensions.md` pins. That file does not
change.
- **VERDICT line:** `VERDICT <mode> · <item> @ <sha7+>`, with `(range a..b` or `(fix range a..b`, then `tier <T>`. The
  range must end at the `@` head. A short SHA matches when it is a sha7-or-longer prefix of the full SHA.
- **COUNT line:** the first `COUNT C<n> H<n> M<n> L<n> · BLOCKING C<n> H<n>` outside a `## Security review` section.
- **SECURITY line:** with or without the word `COUNT`, and with or without a BLOCKING pair.
- **Non-conforming reports:** a report with no conforming VERDICT or COUNT line is refused. The delegator re-asks the
  auditor in the same round.

The audit and confirm request templates name the output file `<item>-r<n>.md`.

**Clearance.** Each report must name a range that ends at the SHA, or at an audited head of which the SHA is an
accepted rebase. Its blocking counts must be zero Critical and zero High. An accepted rebase is proved by
`git range-diff`:
- every commit pair is `=`;
- no commit is added or dropped;
- the new base is on the fetched target branch.

A rebased landing without `--item` is refused, naming `--item`.

**Security.** A landing is High tier when either qualifying report's VERDICT says `tier High`, or when any changed
path is gate-sensitive. This is decided before, and independently of, which reports are present. On a High-tier
landing, both auditors' qualifying reports must
carry a clear security count line: zero Critical and zero High (user, 2026-10-30: 「两个都强制」). A missing, stale or
blocking line on either side is refused, naming `security`. The audit and confirm request templates ask opus-auditor for
the security section too.

**Policy route.** The PR body's `Policy route: routine | audited` is read, but the command decides first. It refuses
`routine`, naming the route check, when any of these holds:
- a changed path is code;
- a changed path is gate-sensitive, per T-01's path module;
- either auditor's VERDICT tier is above Low.

A routine Policy PR that passes needs:
- both auditors' Low-tier mini reports;
- `ci-gate`;
- no verifier record. The command skips T-01's verifier check for it.

`Policy route: audited`, or no marker, needs both auditors at the tier the request names, plus the verifier.

**Gate-sensitive means High.** When any changed path is gate-sensitive, both qualifying reports must say `tier High`,
whatever the route marker. A Low or Medium report is refused, naming that auditor and the tier.

## Acceptance criteria

- [ ] With T-01's evidence present, and both auditors' latest reports clear for the SHA, the landing proceeds.
- [ ] Either auditor's latest report counting a blocking Critical or High is refused, naming that auditor.
- [ ] A latest report whose range ends at an older head is refused, even if an earlier round named the SHA.
- [ ] A missing report for either auditor is refused. So are a bold COUNT line, a COUNT line without `·`, and a report
      without a VERDICT line. Each refusal names the auditor.
- [ ] A report with a COUNT line inside `## Security review` before the main one is read by the main one.
- [ ] A rebase whose range-diff is all `=`, on a new base in `origin/master`, is accepted. One that shows a `!`, an added
      commit or a dropped commit is refused, even when `src`, `tests` and `src-tauri` are tree-identical.
- [ ] Without `--item`, a report found by its VERDICT head at the SHA is accepted. A rebased landing without `--item` is
      refused, naming `--item`.
- [ ] Gate-sensitive paths refuse the routine route. A routine Policy PR touching any of these is refused, naming the
      route check, with one case per glob: `scripts/codex-rules/**`, `.claude/hooks/**`, `.claude/scripts/**`,
      `.claude/settings*.json`, `.claude/agents/**`, `.claude/tdd-guardian/**`, `.codex/rules/**`, `.codex/agents/**`,
      `.agents/skills/*/scripts/**`, `.agents/skills/mdpro-delegator/SKILL.md`,
      `.agents/skills/mdpro-delegator/references/**`, `docs/agents/audit-dimensions.md`,
      `.claude/rules/60-review-checklist.md`, `.claude/rules/70-multi-session-coordination.md`,
      `.claude/rules/71-herdr-mixed-roster.md`, `CLAUDE.md` and `AGENTS.md`.
- [ ] An `audited` or unmarked PR touching a gate-sensitive path (including `.claude/rules/70-…`) with `tier Low` or
      `tier Medium` reports is refused, naming the auditor and the tier. The same PR with `tier High` reports from both
      lands.
- [ ] A routine Policy PR on non-gate-sensitive Policy paths and Knowledge documents lands with no verifier record when
      it has clear Low reports from both auditors and a green `ci-gate`. It is refused:
      - when either auditor's report is missing;
      - when either report says `tier Medium` or `tier High`;
      - when it touches code.
- [ ] High tier is decided by either report: an opus report saying `tier High` beside a gpt report saying
      `tier Medium` makes the landing High tier, and a missing opus security line is then refused, naming `security`.
- [ ] Security, on a High-tier landing: a gpt or an opus report with no security line, with one only on an older head,
      or with one counting a Critical or High, is refused, naming `security`. Clear lines from both pass.
- [ ] The audit and confirm request templates ask both auditors, opus-auditor included, for the security section and
      its count line; a fixture test pins that wording.
- [ ] The audit and confirm request templates name the output file `<item>-r<n>.md`, and a fixture of the pinned report
      shape parses (fixture test).
- [ ] Proved at the landing-command process seam.
