# 0122. The updater drops its `zip` feature instead of ignoring `zip`'s advisories

**Status**: Accepted (2026-10-18). Decided by the user, relayed by
mdpro-delegator: 「去掉 zip 这个 crate，停止codex评估」. Drafted by mdpro-a3
for [D274](../plans/20260912-frontend-backend-sequencing-order.md#d274); the
delegator reserved the number. It applies
[ADR-0107](0107-cargo-audit-runs-in-its-own-job-outside-the-landing-gate.md)
and adds nothing to its `audit.toml` list.

## Context

- **`cargo audit` reports three advisories against `zip` 4.6.1.**
  RUSTSEC-2026-0367: extraction keeps SUID/SGID bits. RUSTSEC-2026-0368:
  `ZipArchive::extract` can create symlinks that point outside the target
  directory. RUSTSEC-2026-0369: Unix permissions are set through a symlink,
  with no limit on the target. Each needs a hostile archive passed to
  `extract`, and each is fixed only in `zip` ≥ 9.0.0. `rust-audit` is outside
  `ci-gate`'s `needs` (ADR-0107), so the check is red on every PR and on the
  daily run, but it blocks nothing.
- **Only the updater uses `zip`.** In Cargo.lock, `tauri-plugin-updater`
  2.13.1 is the only package that depends on it. The figures below come from
  that version's source, whose `.crate` SHA-256 matches the lockfile checksum
  (`3cb0b2ea…0f18`):
  - Plugin `Cargo.toml:63-67`: `default = ["rustls-tls", "system-proxy", "zip"]`.
  - `:75-79`: `zip = ["dep:zip", "dep:tar", "dep:flate2"]`.
  - `:192-195`: `zip` is a Windows-only optional dependency.
  - `lib.rs:11`: the feature "adds support for compressed updater bundles
    from Tauri v1".
- **mdpro never sends the updater a zip.** `tauri.conf.json` sets
  `createUpdaterArtifacts: true`, which is the v2 format, and `release.yml:83`
  builds Windows as `nsis`.
  - A v2 Windows update is the signed `setup.exe` itself. It takes
    `extract_exe`, never `extract_zip` (`updater.rs:1050-1074`).
  - Every download passes `verify_signature` (`:837`) before anything is
    unpacked.
  - Windows and Linux are not offered updates at all today: `latest.json`
    has only the two darwin entries
    ([ADR-0102](0102-v0-3-4-ships-with-a-failing-update-check-on-windows-and-linux.md)).
  - So the vulnerable code is compiled into the Windows build but cannot be
    reached.
- **The feature does not gate macOS.** The macOS updater unpacks
  `.app.tar.gz` with `tar` and `flate2`. They are non-optional on macOS
  (plugin `Cargo.toml:174-176`, `:181-182`). The macOS `install_inner`
  (`updater.rs:1382-1412`) is gated only on `target_os`; no feature
  condition appears anywhere in `:1380-1546`. On Linux, `tar` and `flate2`
  are optional (`:166-172`), and the feature gates only the gzip branch
  (`:1179`). A v2 Linux update is the bare signed `.AppImage`, which takes
  the direct-write branch (`:1205-1207`).
- **No updater release fixes it.** The local registry index from 2026-10-15
  lists 2.8.0–2.14.0 and 3.0.0-alpha.3, and every one requires `zip ^4`. A
  fresh index query was not possible from the drafting session.

## Options considered

- **A. Ignore the three advisories in `audit.toml`, with the reason and a
  re-check date** (the ADR-0107 precedent for rmcp). Lost: it accepts a known
  vulnerability that is still compiled into the Windows build. It needs
  re-checking with every updater release, and it hides the next `zip`
  advisory behind the same reasoning.
- **B. Override or fork.** `[patch.crates-io]` must still satisfy the
  updater's `zip = "4"`, so it cannot bring in `zip` 9. The only workable
  patches are forks: an updater fork on `zip` 9, or a `zip` 4.x fork with the
  fixes backported. Lost: mdpro would maintain a fork of security-relevant
  code for a feature it does not use.
- **C. Leave `rust-audit` red until an updater release moves to `zip` ≥ 9.**
  Lost: a check that is always red stops being read, and this one is red
  every day on the scheduled run.
- **D. Depend on the updater with `default-features = false` and the other two
  defaults, `rustls-tls` and `system-proxy`.** Chosen.

## Decision

1. `src-tauri/Cargo.toml` declares
   `tauri-plugin-updater = { version = "2", default-features = false, features = ["rustls-tls", "system-proxy"] }`.
   The TLS stack and the proxy behaviour are the same as with the defaults.
2. Cargo.lock is regenerated by cargo. It loses `zip` and the two crates only
   `zip` used, `arbitrary` and `derive_arbitrary`, and nothing else changes.
   `cargo tree -i zip` matches no package for `aarch64-apple-darwin`,
   `x86_64-pc-windows-msvc` or `x86_64-unknown-linux-gnu`.
3. `tests/tooling/d274-no-zip-dependency.test.ts` fails if `zip` appears
   anywhere in Cargo.lock (which lists every target), if the locked updater
   lists it, or if the updater's declared features change.

## Consequences

- `cargo audit` no longer reports RUSTSEC-2026-0367, -0368 or -0369, and
  `audit.toml` keeps no entry for them.
- **Cost: v1-format updates can no longer be installed.** On Windows a `.zip`
  package fails with `InvalidUpdaterFormat` (`updater.rs:1099`). On Linux a
  `.tar.gz` package is worse: it is not rejected but written over the AppImage
  as it is (`:1205-1207`), which leaves a broken app. Only a signed package
  gets that far, and mdpro publishes only v2 artifacts. Going back to v1 artifacts, by turning
  `createUpdaterArtifacts` to `"v1Compatible"`, would need this decision
  reversed first.
- **Cost: in-app updates on Windows and Linux are still untested on a
  device.** They are not offered today (ADR-0102). The first release that
  offers them must test the update on each platform, and it cannot rely on
  this change having been tested there. The macOS update path is unchanged
  in code. Its device check, an update from a build of this branch, goes into
  the update/release batch.
- **Cost: a future updater feature added to `default` is not picked up.**
  With `default-features = false`, a new default in a later 2.x release stays
  off. When the updater is bumped, its `[features]` must be read again; the
  guard test's exact feature list makes that a deliberate edit.
- This does not clear `rust-audit` by itself. `ammonia` 4.1.7's
  RUSTSEC-2026-0373, published 2026-10-16, is a separate finding
  ([D284](../plans/20260912-frontend-backend-sequencing-order.md#d284)).
