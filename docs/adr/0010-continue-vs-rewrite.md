# 0010. 不从零重写：原地绞杀热点，非热点继续排期文档

## Status

Proposed — 2026-09-18

评估依据：[`docs/plans/20260918-assessment-continue-vs-rewrite.md`](../plans/20260918-assessment-continue-vs-rewrite.md)
（HEAD `e030a2c`，脏树 51 条 porcelain，全部数字为当日实测）。

## Context

项目由 vibe coding 积累到 505 个提交、约 35,700 行生产代码、166 行 feature ledger，
排期文档（`docs/plans/20260912-frontend-backend-sequencing-order.md`）还有阶段 3→5、至少 33 个
工作项未完成。用户问：继续，还是先定义一套新规范、另起新项目重写。

评估时看到的力量（按当时的理解记录，不是事后判断）：

- **门禁全绿**：`pnpm build` / `test:run`（1578 passed）/ `coverage`（lines 33.83%，阈值 31）/
  `ledger:check` / `cargo test`（265 passed）/ `clippy`（0 warnings）全部退出码 0。
  但 CI 只在打 tag 时运行，最新 tag 后有 158 个提交从未在 CI 上跑过测试。
- **slop 是系统性的，但集中在纪律层面，不均匀分布在代码里**。先声明的七条判据里六条触阈：
  同逻辑多份并存（slug 五份三活两死、五套 Markdown 引擎全在生产路径）；账簿抽样 10 行假 2 行；
  排期文档 422 行含 32 处自我订正；49.5% 的测试文件用 `readFileSync` 读产品源码做正则断言；
  非合并 fix 提交 181 个中 116 个（64.1%）不带任何测试改动；26 个文件超过 300 行；14 条迁移开了未收。
- **热点集中**：按「提交次数 × 行数」，前四名是 `globals.css`、`App.tsx`（1195 行、15 个
  useEffect、10 簇职责）、`file.rs`、`http_server.rs`（1083 非测试行、8 个互不相干的关注点、
  17.6% 测试）。196 个现存源码文件中的绝大多数提交次数低、体量小，新模块（`tableParser/*`）覆盖率 100%。
- **重写会丢什么**：116 个无测试修复承载的知识只在代码里（含两个并发修复）；五个落盘位置零版本字段、
  两个配置根、草稿两种格式靠文件名后缀判别、格式迁移无测试；不存在 source→WYSIWYG→source 往返测试，
  也不存在 Markdown→HTML 整段 golden；唯一语料 `heading-identity.json` 18/25 个 case 用 `currentlyFailsOn`
  同时钉住了今天的错误答案。
- **同栈重写不改变 D6 的天花板**：大表格冻结的两个已知真因一个在依赖（已修，ADR-0006）、
  一个在项目代码（在修）；「整篇一次性挂 ProseMirror DOM、无虚拟化」是栈的固有形态，
  换目录重写不会改变它。是否换内核需要 D6 判据改正后的实测数据，本评估无法回答。
- **新规范尚未成文**。评估发现它需要的 12 项里 6 项是现有规则「已立但未执行」（300 行上限、
  fix 必带测试、禁测源码文本、账簿状态与调用点一致、CI 门禁、ADR 落地追踪），6 项缺失
  （ESLint 架构边界、磁盘格式版本、往返 golden、大文档降级判据、发布节奏、文档体量纪律）。
- 是否有外部用户无法静态判定（无遥测、README 无安装章节、updater 端点已配置）。

## Decision

**不从零重写。采用原地绞杀（strangler）：保留仓库、历史、ADR、账簿；先把新规范中「已立未执行」
的六项做成可执行机制；然后逐个重写热点，用先补好的行为测试与往返测试守住；非热点按排期文档继续。**

具体顺序：

1. 机制先行（不改产品代码）：CI 在 push/PR 触发；`fix` 提交必须触及测试；vitest 禁止读取 `src/` 源码文本；
   文件大小 ratchet；`ledger:check` 增加「Shipped 必须有非测试调用点」；Accepted ADR 必须挂落地 WI。
2. 修正本次证实的账簿失实（表格右键菜单 16→15 两处；按文件记忆窗口几何 Shipped→Partial/Stub）
   与排期文档 3.2 行「五面皆有」→「四面皆有」。
3. 一天 spike：绞杀 `http_server.rs`（先补纯函数测试，再拆 8 个关注点为 4 个模块）。
4. 补往返测试网，然后按 WI-4.22 的控制器形式绞杀 `App.tsx`；`main.rs` 拆 `main()`；`globals.css`
   按计划 P Stage 0 重做。
5. 接排期文档阶段 3 余项 → 4 → 5。

**可翻转条件**（任一触发即重开本决定，写新 ADR 取代本记录）：

- F1：账簿 30 行同种子复抽假率 > 30% → 先重建账簿。
- F2：spike 在 1 个工作日内不能让 `cargo test` + `pnpm test:run` 全绿，或需改动 > 3 个现有测试文件
  → 该模块改为整体替换，但不升级为整仓重写。
- F3：spike 或往返测试证明新规范在现栈内不可满足（必须换编辑器内核）→ 重开「从零重写」讨论，
  且定义改为「换内核」。
- F4：往返测试暴露数据损失 → 冻结所有 WYSIWYG 热点与计划 M 阶段 5，先修保真。
- F5：机制落地 30 天后 fix 无测试率仍 > 30% → 问题在流程不在仓库，停下审视流程。

外部用户假设：两种情形下本决定不变。有外部用户时「从零重写」被数据契约兼容成本排除；
无外部用户时反对它的主证据（116 个无测试修复、同栈重写对 D6 零收益）与用户数无关，
但可放弃整条 updater 链。

## Consequences

**得到的：**

- 116 个无测试修复的知识不丢；1578 + 265 个测试里与非热点绑定的部分继续有效。
- 磁盘契约不需要在没有格式测试的情况下被新代码「读懂」。
- 158 个未发布提交不再继续积压——CI 机制先行后，发布可以恢复。
- 每个后续 WI 在机制保护下进行，slop 的产生速度被门禁压住而不是靠人记得。

**付出的代价（本决定放弃或承担的）：**

- **放弃「一次清零」**：14 条半完成迁移要串行收口，其中 8 条（`marked` 依赖、CSP、ESLint、ADR-0003
  落地、D 系列缺陷等）在重写路径下同样要做，但另外 6 条在重写下会自动消失，本决定选择逐条做。
- **多约 15 个 WI 的前置工作**（评审者估算，非实测）：6 项机制 + 3 个热点绞杀，在排期文档的
  ≥ 33 个 WI 之前。计划 P 与 M 的日程要相应后移。
- **热点重写时现有的源码文本测试作废**：`data-loss-logic.test.ts` 26 条断言中 19 条读 `App.tsx` 源码，
  绞杀 App.tsx 前必须先用行为测试替换它们，这是真实成本，也是 F2 阈值存在的原因。
- **热点与非热点之间会长期存在两种代码风格**（新规范下的模块与旧模块并存），直到排期文档走完。
  rule 22 的注释维护与 rule 50 的跨 feature import 在过渡期会更难守。
- **不回答「要不要换编辑器内核」**。本决定把它明确推迟到 D6 判据修正并实测之后；如果实测证明
  ProseMirror 全量挂 DOM 本身就是天花板，F3 触发，本决定被取代，前面绞杀 `App.tsx` /
  `MilkdownEditor.tsx` 的工作有一部分会白做。
- **禁止 vitest 读 `src/` 源码**会让 46 个现有测试文件在机制落地当天变红。要么分批迁移（机制先只
  对新文件生效），要么承担一次性的测试重写；两种都要花时间，本决定不预设哪种。
- **`ledger:check` 第四道机检**会把今天至少一行 Shipped（按文件记忆窗口几何）判为失败，
  且可能暴露更多只写不读的表面；这是想要的结果，但意味着账簿修正不能等。
- 若外部用户存在，「放弃 updater 链」的裁剪选项不可用，本决定的范围裁剪收益减少。

**被本决定取代或约束的记录：**

- 不取代任何已 Accepted 的 ADR。ADR-0003（导出片段净化范围）仍是决定，本决定只把「它未落地」
  记为一项要机检的事实。
- 排期文档 `:206`（WI-4.22 为基础链末端）与本决定的顺序冲突：本决定把 App.tsx 绞杀提前到阶段 4 之前。
  按 CLAUDE.md 的规则，ADR 是决定、计划被修正——本 ADR 转为 Accepted 时须同步改排期文档。
