## Unit: `src/utils/largeDocumentGuard.ts#decideLargeDocumentGuard`

### Gap 1: row-start detection may require a closing pipe — nothing in the matrix says it must not

- **Attack**: Wrong-but-close boundary (variant: under-specified predicate on a partition edge). This is plan risk 2's own words: *"whether a row start also requires a closing pipe [is] unspecified"*. WI-1 answer (2) resolves it (first non-whitespace char is `|`, full stop) and the matrix's traceability table claims it is enforced — it is not.
- **Passing-but-wrong implementation**:
  ```
  // single pass, constant space, charCodeAt — satisfies every ADR-0016 invariant
  at each line: firstNonWs = first char code that is not SPACE/TAB
                lastNonWs  = last  char code that is not SPACE/TAB/CR
  on line end (\n or EOF):
      if (firstNonWs === CHAR_PIPE && lastNonWs === CHAR_PIPE) rowStarts++
  score = newlines + pipes - rowStarts
  ```
  i.e. "a table row is a line delimited by pipes on both sides" — one extra `lastNonWs` variable, still one forward pass, still allocation-free, still passes C12 and C8b' (no new `<=`, no new numeric literal).
- **Why every listed case passes**: I checked all 22 N1 rows and every other scoring case. **No case in the entire matrix contains a line whose first non-whitespace character is `|` and whose last non-whitespace character is not `|`.** Specifically: N1 rows 4 (`"|"`), 5 (`"||"`), 7 (`" |"`), 8 (`"\t|"`), 9 (7 spaces + `|`), 13, 16, 17, 18, 19, 21, 22 all end on `|`; rows 3, 6, 10, 11, 12, 14, 15, 20 are not row-start lines at all under either reading. G4' second doc, G5' mixed sibling, N6, N8, N9(a) and (b), N10 doc 2, N14 `largeTable`, N16, N4 F2/F3/F4, N5 rows — every table row is `| … |`. The naive form of this variant (comparing the *raw* last char, so CRLF's `\r` defeats the match) **is** killed by N1 row 19 / N5 / N4-F4; the trailing-whitespace-tolerant form shown above is not.
- **What it would break in production**: GFM makes outer pipes optional. A 30,000-row table written `| a | b` (leading pipe, no trailing pipe) gets no subtraction — the score is inflated by one per row, ~30,000 over-count, degrading documents the ADR's fitted threshold says should stay in WYSIWYG. It is the mirror of the under-count the ADR *did* accept (N11) and is not recorded anywhere as accepted, so it would ship as an unrecorded deviation from Decision 1's stated arithmetic.
- **Missing case**: two new rows in N1's transition table (they belong inside N1, because N1's S4 claim is "a partition of the scanner's input space by state-machine transition" and "row start whose line does not close with `|`" is a transition class the partition currently omits — adding them there is what makes the S4 claim honest):

  | # | fragment | `s` | transition pinned |
  |---|---|---|---|
  | 23 | `"\| a \| b\n"` | 2 | row start **without** a closing pipe — 1 newline + 2 pipes − 1 row start |
  | 24 | `"\| a \| b"` | 1 | same, unterminated at EOF — 2 pipes − 1 row start |

  - **Level**: S4 — it extends an existing exhaustive-partition case rather than adding an example; the partition is over scanner state transitions and is currently incomplete. (An S2 standalone boundary case would also close it, but weaker.)
  - **Lane**: unit
  - **Assertion**:
    ```
    expect(atMargin("| a | b\n")).toEqual({
      action: "degrade-to-source",
      message: "This document is too complex for WYSIWYG. Switched to Source mode for performance.",
      elements: 25_002,
    });
    expect(atMargin("| a | b")).toEqual({ ...same..., elements: 25_001 });
    ```
    The closing-pipe implementation reports 25,003 / 25,002 and fails both.
- **Secondary finding this produces**: the matrix's traceability table is wrong at two places and should be corrected in the same edit — line 651 (`WI-1 answer (2) … Enforced by N1 rows 4, 7, 8, 9, 10, 11, 17, 18`) and line 713 (same claim in the Coverage table). Those eight rows pin that leading whitespace is *tolerated*; none pins that a leading `|` is *sufficient*. A false coverage claim is worse than an admitted hole because it stops anyone looking.

### Gap 2: escaped `\|` and inline-code pipes are unpinned — the one member of the ADR's over-count family with no tripwire

- **Attack**: Silent failure / half the operation (variant: a "helpful" refinement that the ADR forbids, with no tripwire).
- **Passing-but-wrong implementation**:
  ```
  prev = 0
  for i in 0..len:
      c = content.charCodeAt(i)
      if (c === CHAR_PIPE && prev !== CHAR_BACKSLASH) pipes++   // "escaped pipes aren't cells"
      ...
      prev = c
  ```
  One character of lookback: single pass, constant space, no tokenizer — passes C12, passes C8b' only if the extra `92` literal is added to the permitted list, which a reviewer "fixing a red anchor" would do.
- **Why every listed case passes**: no case in the matrix contains a backslash at all, and none contains a backtick-delimited inline-code span with a pipe. The three pipes-in-non-table cases are `"```\na|b\n```\n"` (N1 row 20 / N10 doc 1 — fenced, bare pipe), `"a | b"` (N1 row 14 / N11 — bare pipe), `"|---|---|"` (N1 row 15 / N10 doc 2 — bare pipes). All are unaffected by escape handling.
- **What it would break in production**: ADR-0016 Consequences specifies the over-count direction as intentional ("it over-counts on a literal `|` in prose or inside a fenced code block"). A document of 30,000 lines of prose containing escaped pipes would score below the real risk. More importantly it is a *parsing rule* smuggled in under Decision 1's frozen invariants — exactly the class of change the matrix builds tripwires for elsewhere (N10 = fence tracking, N12 = inline-density counter). The absence here is an asymmetry in the matrix's own declared design intent, not a likely first-draft bug — I rank it below Gap 1 and say so plainly.
- **Missing case**: two more N1 rows (or one extra characterization case in section E alongside N10/N11, labelled the same way):

  | # | fragment | `s` | transition pinned |
  |---|---|---|---|
  | 25 | `"\\| a\n"` (source: `\| a`) | 2 | escaped pipe still counts; and the line is **not** a row start, because the first non-ws char is `\`, not `\|` |
  | 26 | `` "`a|b`\n" `` | 2 | inline-code pipe still counts — no span tracking |

  - **Level**: S1 — characterization of a deliberately accepted defect; generalising it would read as endorsement, same reasoning the matrix already applies to N10/N11/N12.
  - **Lane**: unit
  - **Assertion**: `expect(atMargin("\\| a\n")).toEqual({ action: "degrade-to-source", message: <full literal>, elements: 25_002 })` — an escape-aware scan reports 25,001. Comment must say, as N12's does, that this case going red means someone added a parsing rule and owes a new ADR.

## Matrix defects (not attack survivors, but they will produce wrong tests)

### Defect 1 — N10's first document is self-contradictory, and the obvious "fix" deletes its tripwire

The **Input** line says `"```\na|b\n```\n".repeat(5_000)`; the **Expected output** line contains a visible mid-draft self-correction: *"degrade with `elements: 20,000`… no — `4 × 5_000 = 20_000` is below the threshold, so the first input must be `.repeat(7_000)` → `elements: 28_000`"*. An implementer who copies the Input line writes a test that **fails against a correct implementation** (score 20,000 → allow, expected degrade). The likely repair is to change the expectation to `{action:"allow"}` at 5,000 repeats — and at that point the case discriminates nothing: a fence-tracking implementation scores 15,000 and *also* allows. The fenced-code tripwire would be silently deleted while the case still carries the label claiming it exists.

- **Fix**: state the input once, as `.repeat(7_000)`, expected `elements: 28_000`. (Verified: 3 newlines + 1 pipe − 0 row starts = 4 per block; 4 × 7,000 = 28,000.) The attack itself remains covered meanwhile by N1 row 20 — say so in the case so the redundancy is deliberate rather than accidental.

### Defect 2 — N1 row 15's fragment is ambiguously escaped, and the ambiguity changes both the expected number and the rule under test

Row 15 is written `"\|---\|---\|"` with `s = 2`, while rows 13, 14, 16-19 write pipes unescaped inside the same markdown table. Two readings:
- backslashes are markdown-table escaping → the JS string is `"|---|---|"` → 3 pipes − 1 row start = **2** ✓ matches, and the case is the delimiter-row over-count as labelled;
- backslashes are literal → the JS string is `"\\|---\\|---\\|"` → 3 pipes − **0** row starts (first non-ws char is `\`) = **3** ✗, and the case silently becomes an escaped-pipe test with a wrong expectation.

- **Fix**: give row 15's fragment as an explicit JS string literal in the matrix (`"|---|---|"`), and normalise the escaping convention across all 22 rows. The delimiter-row attack itself is independently killed by N10 doc 2 (9 per table requires the delimiter row to be both counted and treated as a row start), so this is a correctness defect in the matrix text, not an open attack.

## Audit of the questions you asked specifically

**Are the claimed laws actually laws?** Yes — all five. I checked each:
- **L1** (gate totality) — true, and observably pinned by G18'a (`reads === 0`), which answers your third question: a non-wysiwyg mode provably skips scoring entirely, and a test can tell.
- **L2** (additivity over `\n`-aligned concatenation) — exactly true: `A` ending in `\n` makes the segment boundary a line boundary, so `rowStarts` is additive along with `newlines` and `pipes`. N4's design (four fragments each *independently above threshold*) is what makes it kill early exit without circularity. This is the strongest case in the matrix and the claim is accurate.
- **L3** (non-negativity, monotonicity, single cut point) — true. Each line contributes `pipes_in_line − [row start] ≥ 0` because a row start implies ≥1 pipe.
- **L4** (CRLF metamorphic invariance) — true for `\r`-free `d`: the injected `\r` is always line-final, so it can never displace a line's first non-whitespace character.
- **L5** (purity/freshness) — true.

**Is any real law missing?** No new law, one **coverage-narrower-than-statement** note: L3 asserts "`score` is non-decreasing under append", but the only cases exercising it (G6'/G7') append `\n` to `\n`-only documents, and N4 requires `\n`-alignment *and* both fragments above threshold. General append-monotonicity is genuinely true (appending can only convert an all-whitespace trailing line into a row start, and must supply the `|` itself to do so, so the delta is ≥ 0) — and I could **not** construct a wrong implementation that violates it while passing N1 + N4, including the Gap 1 survivor, which is itself append-monotone. So I am **not** filing it as a gap: adding a general-append property case would be an S5 case that kills nothing known. Narrow the wording of L3 instead, or accept it as stated.

**Prohibited assertions (ADR-declared-unmeasured):** **clean — none found.** No case asserts ragged-table accuracy; no case asserts that two table geometries with equal element counts differ or agree in *cost* (N9's 2-column and N16's 4-column documents assert only the predicate's arithmetic, which is legitimate); no case asserts the 24,000-element-at-5 MB shape is safe. N3 family 1 (600 KB at score 10 → allow) and N15 (600 KB single line → allow) are extrapolations of the *measured* `very-long-line` shape and are behaviour of the predicate, not safety claims. Deferred #10 states the prohibition explicitly. This part of the matrix is exemplary.
