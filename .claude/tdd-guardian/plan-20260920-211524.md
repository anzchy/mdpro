## Risks & Assumptions

**Genuinely underdetermined by the ADR — an implementer would have to guess:**

1. **Newline count vs line count.** The ADR says "newline count" but its own evidence
   table column is headed "lines". A 3-line document has 2 or 3 newlines depending on the
   trailing newline. Off-by-one at a 25,000 threshold is immaterial to the decision but
   material to every test that pins the exact reported number. Decide in WI-1.
2. **"Table-row start" has no definition in the ADR.** The only constraint is that
   `pipes − rowStarts` produced 45,752 cells for an 11,438-row 4-column table, which
   implies "one subtraction per line beginning with `|`". Leading-whitespace tolerance,
   tabs, and whether a row start also requires a closing pipe are all unspecified. The
   ADR's note that "detecting a table-row start needs a little whitespace state" implies
   leading whitespace is skipped, but not how much.
3. **Early exit semantics.** Permitted, not required. If taken, the reported number is a
   partial score, and every test that pins an exact value above the threshold has to be
   rewritten as an inequality — which weakens the strongest mutation-killers in the
   matrix. Recommend declining early exit in this change and recording the deferral.
4. **The payload number's fate and name.** `bytes` is now false. Dropping the field
   entirely is defensible (the ADR never requires it); keeping it as `elements` preserves
   the "tests can see which number produced the decision" property the current module
   header claims. Recommend keeping it renamed.
5. **Threshold constant name.** `LARGE_DOCUMENT_THRESHOLD_BYTES` must not survive — the
   name asserts a unit that is gone. Renaming is a source-visible break for
   `docs/guide/view-modes.md` and the two test files, all of which are in scope anyway.

**Risks:**

6. **The predicate now runs a full content scan on every keystroke, and the ADR never
   considers this.** `activeDocument` is derived by `useMemo` over the `documents` array
   (`src/hooks/useDocument.ts:55-58`), whose identity changes on every content update, and
   `activeDocument` is in the effect's dependency array. Under the old predicate a
   non-null `fileSize` short-circuited and the effect was O(1) for every saved document.
   Under the new one, every document that *stays* in WYSIWYG (score ≤ 25,000) is rescanned
   per keystroke — and a low-score document can still be huge: the ADR's own worst case
   measures 12.87 ms for an 8.8 MB scan, and the `very-long-line` shape scores 3 while
   being 472 KB. This is a real, newly-introduced main-thread cost on the typing path.
   Options: (a) accept and record — the 10 MB open limit caps it at ~13 ms; (b) memoize on
   `activeDocument.content` identity at the call site, which changes the dependency array
   and therefore breaks C3, the one anchor asserting the reviewed effect shape;
   (c) move the score into the store. **Recommend (a) plus an explicit note**, because
   E39/Decision 7 forbid turning a millisecond number into a gate and because (b) mutates
   the reviewed effect shape for an unmeasured benefit — but the user should see this
   before it ships, since it is the one cost ADR-0016 did not weigh.
7. **Rule 20 vs ADR-0016.** Rule 20 says every new feature gets structured logging; the
   ADR records that the guard emits no decision event and states that whether it gains one
   "is a separate decision this ADR deliberately does not take", and Consequences lists the
   silent false degrade as an accepted, unclosed gap. **Defer, citing the ADR**; do not
   add a log event opportunistically in this commit.
8. **The call-site test file has no Level 1-5 assertion at all** and never did — it is
   pure source-text inspection, self-labelled "below Level 6", with a written waiver.
   Policy-core mandatory rule 1 would otherwise fail it. The waiver is carried forward, not
   created here, and the rewritten header must restate it, including the rejected
   `useLargeDocumentGuard`/`renderHook` middle option. If the reviewer wants that
   exception closed, the hook extraction is the way — and it is a different work item.
9. **Do not let tests contradict the ADR's accepted costs.** Three characterization cases
   in WI-3 (fenced-code and delimiter-row over-count, omitted-outer-pipe under-count,
   20,000-inline-links blind spot) exist to *record* behaviour ADR-0016 Consequences
   accepts. Each must be labelled so a future reader does not "fix" the predicate to make
   them pass differently. Equally, no test may assert that a ragged table is counted
   correctly, that table geometry is distinguished, or that a 24,000-element 5 MB document
   is safe — the ADR states all three are unmeasured.
10. **Premature D6 closure.** The unit lane can prove the predicate; it cannot prove the
    app degrades on a real WKWebView. ADR-0004 ties D6 to the 3.8 exit re-test. The
    sequencing row must not go ✅ on a green suite.
11. **Ledger enum + `限制：`.** State must stay inside the five-word enum with a literal
    `限制：`; `pnpm ledger:check` also re-validates every path claim in the rewritten row.

### Correction to the planner's risk 6 (performance regression)

The planner framed the new scan as an O(1) → O(n) regression. That is only half true.
`fileSize` is `null` for every untitled, newly created, and MCP-created document —
confirmed at `src/hooks/useDocument.ts:23`, `src/App.tsx:657`,
`src/hooks/useMcpEvents.ts:296`. For those, the **old** predicate already ran
`new TextEncoder().encode(input.content)` — a full allocating encode of the whole
document — on every keystroke. The new scan is allocation-free, so it is strictly
**cheaper** there. The regression applies only to **saved** documents, and is capped by
the project's 10MB open limit.

Consequence: risk 6 resolves to the planner's **option (a) — accept and record**, and
the early exit is **declined**, with the deferral recorded rather than silently dropped.
