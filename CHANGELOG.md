## [Unreleased]

### Added
- Quitting mdpro with unsaved work now asks before discarding it. Previously ⌘Q, the menu's Quit, the Dock's Quit and AppleScript `quit` all reached AppKit's terminate directly, and tao 0.34.5 implements no `applicationShouldTerminate:`, so the app exited without a prompt, without writing the file, and without even logging `app.quit` — unsaved changes were lost silently ([ADR-0025](docs/adr/0025-app-quit-is-deferred-through-a-native-terminate-hook.md)). The quit is now deferred: every window is asked whether it is dirty, then each dirty window is brought forward and prompted one at a time. Discarded drafts are deleted only once the whole quit commits, and draft auto-save refuses to write from that moment, so a timer cannot resurrect a draft between the delete and the exit
  - If a window does not answer within about 2 seconds — a hung or stalled webview — a native alert takes over ("mdpro isn't responding to the quit request"), offering Keep Open or Quit Without Saving ([ADR-0027](docs/adr/0027-a-quit-ack-timeout-draws-a-native-alert.md)). Quit Without Saving deletes no drafts, so recovery still has something to recover from. A window that recovers after the alert appears has its late answer ignored
  - **Known limit, accepted**: Escape does nothing on that alert. AppKit only assigns Escape to a button titled literally "Cancel", and Keep Open has to hold the Return default. The discarding button carries no key equivalent, so the failure direction is safe — a stray keystroke cannot discard your work
  - **Verified on a real device on 2026-09-23**, partly. What passed: the hook binds to tao's actual delegate class (`TaoAppDelegateParent`, `outcome: added`, on every cold launch); a dirty document prompts instead of quitting silently; Cancel leaves the app alive with the document still dirty; Discard quits and removes the draft; an all-clean quit completes in 5 ms with no dialog. Record: `docs/test/20260923-d16-gui-acceptance.md`
  - **What failed, and is fixed below**: with two dirty windows, *both* showed the dialog rather than one at a time, and a Cancel from the window that was never prompted did nothing. The coordinator was right; the webview subscribed with the global `listen` and so received a prompt addressed to another window
  - **Still unproven**: the alert's own appearance and behaviour, and the whole timeout path — deliberately not exercised, because [ADR-0029](docs/adr/0029-quit-deadlines-bound-machine-progress-not-people.md) was re-specifying the timeout model at the time. A second ⌘Q was also proven *not* to be a route out of a stuck quit: AppKit suppresses the entire quit path while a deferred reply is outstanding, so the delegate is never re-entered
- **mdpro → Stop Waiting and Quit…**, directly below Quit, is the way out of a quit that is stuck waiting on a window ([ADR-0030](docs/adr/0030-a-menu-item-is-the-escape-hatch-for-a-stuck-quit.md), [ADR-0036](docs/adr/0036-the-stuck-quit-escape-hatch-is-an-always-enabled-app-menu-item-without-a-shortcut.md)). It has no shortcut, is always enabled, and is handled entirely in Rust, so it does not depend on a responsive webview. While a quit is waiting on a window it hands the quit to the same native alert as a timeout (Keep Open / Quit Without Saving), and a window that answers late is ignored. On an idle app it does nothing. It is also ignored while the alert is already showing, and during the up-to-2-second draft-everything step before a quit commits. Every click writes one `app.quit.escape` log line, which carries counts only
  - **Verified on a real device on 2026-09-25** (`docs/test/20260925-r7-d29-d24-gui-acceptance.md`), and ADR-0036 is now Accepted. This includes the case the item exists for: with the save dialog delivered and its renderer then frozen with `SIGSTOP`, the item still raised the native alert. Quit Without Saving quit the app, and the draft was offered on the next launch
  - **Known wording defect**: when reached from this item, the alert still says the app didn't answer in time
- Switching between Source and WYSIWYG (⌃2 / ⌃4, ⌘/, the menu, or the large-document degrade) now keeps your place instead of jumping to the top of the document (WI-8). The top visible block is captured on the way out and scrolled back to the top on the way in
  - **Known limits, accepted**: positions map by top-level block; if the two editors disagree on the block count it falls back to the nearest heading, and if that disagrees too the view opens at the top rather than guessing. Documents over the WYSIWYG threshold only get heading-level precision
  - Checked by hand on a release bundle: position within ±3 lines, no drift over 10 round trips, no shift after images load. Not yet checked: both themes, a large paste, and the outline highlight after a switch (blocked by a separate, older outline-highlight defect)
- Math / LaTeX rendering (Typora-parity Phase 1, WI-1.1): `$inline$` and `$$display$$` math now render. The canonical Rust renderer emits `.math-inline` / `.math-display` wrappers carrying raw TeX; the preview typesets them with bundled KaTeX (offline), failing soft on invalid TeX (raw source kept, never blank). HTML export pre-renders math to **MathML** (KaTeX `output:'mathml'`), which renders natively in the browser with zero JS and — unlike KaTeX's styled HTML — needs no inline `style`, so it survives the server-side sanitizer (which forbids `style` to close the `url()` exfiltration vector) with its structure intact. Exported math therefore uses the browser's native MathML rendering (the inlined KaTeX stylesheet styles any KaTeX-HTML wrappers that remain), which is layout-correct but not pixel-identical to the preview's KaTeX-HTML typesetting. Math inside code spans/fences stays literal. Math inside a table cell renders via pulldown-cmark's default `math math-inline` class, which the KaTeX/MathML pass still matches (the `span.math-inline` selector matches the double-class element), so in-cell math typesets in both preview and export
  - Known degradation (accepted, plan decision A1): the `exportService` `marked` fallback path — used only when the Rust `render_markdown` IPC throws — renders neither math nor footnotes. The canonical Rust path is the supported export route; the fallback is a last-resort plain-Markdown render
  - Deferred to Phase 2 (B3): Milkdown WYSIWYG mode does not yet typeset `$…$` math or render footnotes — in source mode these stay visible as raw `$…$` / `[^1]` text (readable, not broken). The canonical Rust render surface (preview + export) is the supported math/footnote path for Phase 1
- Footnotes (Typora-parity Phase 1, WI-1.3): `[^1]` references and definitions render with working return ("↩") back-links; the reference gets a stable `fnref-` anchor and the definition links back to it. Undefined references stay literal
- Auto-link + emoji (Typora-parity Phase 1, WI-1.4): bare `http(s)://` URLs are linkified, and a curated set of `:shortcode:` emoji render as glyphs. Both skip code spans/fences and existing links; unknown shortcodes stay literal
- In-app update checker: Settings → About page with version display, update check, download progress, and one-click install via `tauri-plugin-updater`
- Pre-relaunch save guard: automatically saves all modified documents before restarting, blocks if untitled docs exist or saves fail
- CI release workflow: `latest.json` generation with dynamic GitHub asset discovery via `jq`, signing env vars for updater artifacts
- Large-document degrades are now recorded in `~/.mdpro/mdpro.log`. When the guard takes WYSIWYG away and drops you into Source mode it writes one `editor.large_document.degrade` entry (`warn` / `fail`) carrying which of the two predicates fired (`trigger`: `structure`, `line-length`, or `both`), both measurements (`elements`, `longestLine`), and the thresholds in force on that build. Previously the degrade left no trace at all, so "why did this open in Source mode?" had no answer in the log — and since [ADR-0019](docs/adr/0019-large-document-guard-adds-a-longest-line-trigger.md) added a second trigger, "the guard fired" stopped being a complete answer even when it could be inferred. Find it with `grep large_document.degrade ~/.mdpro/mdpro.log | tail -1 | jq .`
  - **Still unobservable, and it is the bigger gap**: the predicate only runs on entry to WYSIWYG (`src/utils/largeDocumentGuard.ts:260` allows every other view mode unconditionally). Opening a 9.96 MB document directly in Source mode is neither judged nor logged. **Correction (2026-09-22)**: this bullet originally cited 153–183 s (`docs/test/20260921-d6-matrix-retest.md` §6.2) as the cost of that path. §7.4 of that same document withdraws the number — its dominant component was a quadratic line counter since removed in `3d37b86` — so quoting it here overstated a figure the source had already retracted. What replaces it is smaller in scope and actually measured: one `parseTableAtOffset` on a 9.8 MB table-shaped document returns 931,924 cell objects and retains 120,458,072 B, and the whole per-transaction path (`linesFromText` + parse, which is what the Source cursor path re-runs on every keystroke and cursor move) retains 139,037,640 B (defect D12, found 2026-09-22, **not fixed**). **Second correction, same day**: this bullet first quoted 148.1 MB for the parser alone, which over-attributed the line-source construction to it by roughly 23%; a density sweep split the two and also found the growth strictly linear above 1,000 rows, so the curve has no knee to put a threshold on. The whole-app cost of that path remains unmeasured. This entry adds observability to the surface that already had a decision, not to the one that has none — a design for which is now proposed in [ADR-0022](docs/adr/0022-source-mode-gets-its-own-guard-keyed-on-table-row-density.md)
  - Both guard log lines (`editor.large_document.degrade` and `editor.large_document.source_tables_withheld`) now carry `documentId`, the affected document's UUID, so a line can be tied to the document it describes. The id is metadata, not content; the context fields stay an exact allowlist.

- Logging now fails **closed** on the Rust side when it cannot read your settings (defect D7). `src-tauri/src/services/logger.rs` initialised its settings cache with `load_preferences().map(..).unwrap_or_default()`, and `LogSettings::default()` is `enabled: true` — so a user who had explicitly turned logging off had it silently turned back on whenever `~/.mdpro/config.json` was unreadable or unparseable. The resulting value was byte-identical to a healthy fresh install, so nothing downstream could tell the two apart. The fallback is now a separate `FAIL_CLOSED_SETTINGS` constant with `enabled: false`, mirroring the frontend half of the same defect (D2) that was fixed earlier
  - Only `enabled` flips. `level` carries no safety meaning and stays at the ordinary default, and `LogSettings::default()` itself is deliberately unchanged so it keeps mirroring the TypeScript default
  - **A fresh install is unaffected**: `load_preferences` treats a *missing* config.json as the success path — it writes defaults and returns `Ok` — so a first launch reaches `enabled: true` through the success branch. Reaching the fallback means the file exists and is corrupt
  - **A second fail-open the defect record did not name is closed in the same change**: `get_log_settings` also returned `LogSettings::default()` when the settings mutex was poisoned — the same silent re-enable via a different trigger. A poisoned mutex is not a reason to discard the user's setting, since the value behind the lock is intact, so both the read and the write now recover it through `PoisonError::into_inner` rather than substituting a fallback. Fixing only the reported line would have left the defect class alive
- The file watcher and the "External change detected" prompt now leave a trail in `~/.mdpro/mdpro.log` (D32, step 1). A clean file whose modification time had not changed was seen twice on 2026-09-25 raising the reload prompt after a *different* file was opened from outside, and nothing in the log could say why: neither the `file:changed` emission nor the reload decision was logged. Four kinds of line, all `info` unless noted below, now cover the path end to end
  - `file.watch.event`: exactly one per filesystem event the watcher receives, including the ones it drops as debounced, as its own save, or as an ignored kind. It records which of notify's event kinds arrived (for example `modify_metadata` / `extended` versus `modify_data` / `content`), what the watcher did with it, the file's size and modification time at that moment, and the timestamp that is also sent to the window
  - `file.watch.register` / `file.watch.unregister`: one per watch or unwatch, with whether it succeeded. The watcher used to discard that result. A failed register is logged at `error` and a failed unregister at `warn`
  - `file.watch.error`: one `warn` line per error the watcher's backend reports, with its kind and paths. The callback used to drop these silently. macOS's FSEvents backend does not report errors this way, so on a Mac this line is expected never to appear. It is there for the Linux (inotify) and polling backends
  - `file.change.received`: one per event reaching a window's listener, saying whether it was for another file, suppressed because of a recent save, scheduled, or delivered. `delivered` reuses the `actionId` of its `scheduled` line
  - `file.change.decision`: one per distinct reload decision, including whether the document was dirty and whether the event's path matched it. Typing does not add lines; switching away from a tab and back does, which is how a stale event re-prompting would show up
  - Find them with `jq -c 'select(.event|startswith("file.watch.") or startswith("file.change."))' ~/.mdpro/mdpro.log`
  - **The D32 root cause is not fixed.** This change is logging only: the event emitted to the window and the prompt behaviour are unchanged. Several explanations are still open, and a real-device reproduction with these lines is the next step
  - **These lines temporarily log full file paths**, because the path and its `/tmp` versus `/private/tmp` spelling are among the things being tested. That is scoped to D32 and the path fields are to be removed or reduced when D32 closes. File contents, extended-attribute values and prompt messages are never logged
- `pnpm control:build` builds the app with a build identity compiled in ([ADR-0047](docs/adr/0047-agents-verify-in-the-real-app-through-a-feature-gated-control-channel.md), WI-001). It builds the `mdpro_mcp` sidecar and `mdpro.app` in one step and writes `build-manifest.json` next to the `.app`. The `buildId` is computed from the working tree's contents (uncommitted edits included; `docs/` and `.claude/` left out), the profile, the cargo features and the sidecar's hash. The build fails and leaves no manifest if a source file changes while it runs or if the built binary does not carry the id. The manifest holds no absolute path and no user name
  - The `app.ready` line in `~/.mdpro/mdpro.log` now carries `pid` and `buildId`, so a running process can be matched to the build it came from
  - Builds made with plain `pnpm tauri build`, including releases, log `buildId: "unknown"`
  - The build is refused when the working tree holds a nested git repository or submodule that the `buildId` would cover, and the error names each path. Uncommitted edits inside one would not change the id, so one id could name two different sources. Nested repositories under `docs/`, `.claude/` or an ignored, untracked path are not affected
  - Checked on real builds: repeated builds of one tree give the same `buildId`, `app.ready`'s `pid` and `buildId` match the process and the manifest, and building `verify` then `release` leaves each bundle carrying its own manifest's id with the same `dist` digest as a release built alone in a clean checkout. The same source built in two checkouts gets different `buildId`s, because the sidecar is rebuilt each time and its Mach-O UUID and ad-hoc signature differ
- `pnpm control:build --profile verify` builds an isolated verification app for development and agent checks only ([ADR-0047](docs/adr/0047-agents-verify-in-the-real-app-through-a-feature-gated-control-channel.md), WI-002). Release builds are unaffected: `tauri.conf.json` is unchanged, and the cargo feature `verify-run` is off by default. The verification app, `mdpro-verify.app`, has its own identifier (`com.mdpro.app.verify`), no `.md` file association, no updater endpoint and no updater artifacts. Its first statement is a launch guard that exits with code 78 before touching any persisted path unless it was started inside a prepared run directory. The guard checks the four run variables, the run directory's location, mode and owner, the launch nonce, and that `HOME` and the data directory resolve inside it. The guard only validates; `instance.json` is published later, as the first step of app setup, after the single-instance check has already handed a second launch off to the running app. Publication is exclusive: if `instance.json` already exists, the app exits with code 78 rather than overwriting it, so a second process in the same run can no longer replace the running app's pid with its own. A run that passes binds its MCP server to a system-assigned port instead of 55045
  - A checked-in registry, `src-tauri/persistence-roots.json`, names every `dirs::` call site in the Rust code. A test fails on any call site that is not registered, and every production root is shown to resolve inside a temporary `HOME`
  - Checked on a real verify build (2026-10-07/08): the bundle identity and `Info.plist`, the launch guard refusing a Finder double-click or a missing run, an isolated run beside the everyday app leaving the real home directory unchanged, and a second process in the same run leaving `instance.json` untouched. Not checked on macOS 13

### Security
- The MCP server's `server.token` file is now owner-only from the moment it exists ([ADR-0040](docs/adr/0040-the-mcp-server-switch-takes-effect-live.md) decision 4). Previously it was created at the default file mode, the token was written, and only then was the mode narrowed to `0600`, so for that window the token was readable by other local users; an existing `server.token` was reused rather than replaced, so a descriptor opened while it was readable stayed valid. The token is now written to a freshly created temporary file that is `0600` before any byte is written, then renamed into place, and `server.port` is written last, after the listener is bound, so a client never finds a port without a matching token. Every start mints a fresh token, and stopping the server removes both files and invalidates the old token in memory
- Sanitizer policy redesign (Typora-parity Phase 0, WI-0.1): the Rust `sanitize_html` and frontend DOMPurify config now share one per-feature allow-list matrix that preserves legitimate KaTeX math, footnote anchors, and Mermaid inline-SVG output while neutralizing script/`on*`/`<foreignObject>`/`url(http…)`-in-style payloads on every render surface. `style` is never allowed (no exfiltration), href schemes are restricted to the safe set, and in-doc `#anchor` links pass through. Mirrored tag/attr lists are regression-tested on both surfaces
- `name` is no longer an allowed attribute in the export sanitizer ([ADR-0011](docs/adr/0011-remove-name-from-export-sanitizer-allowlist.md)). With the DOM-clobbering defence switched off for export (see the export-anchor entry under Fixed), an allow-listed `<img name="body">` surviving into the exported HTML could shadow `document.body` — or `document.createTreeWalker` — inside the syntax-highlighting pass that re-parses the sanitizer's output with `DOMParser`, because a `DOMParser` result is a real document tree. ADR-0003's original analysis applied its "must be in a document tree" test to only one of the two post-processors; this closes the one reachable instance it missed. The Rust/ammonia path never allowed `name`, so this also removes a drift in which the JavaScript allow-list was the more permissive of the two
  - **Behaviour change**: legacy `<a name="x">` anchors written as raw HTML no longer survive export. `id="x"` is the supported form and is what every generated heading anchor already uses. Nothing in the renderer emitted `name`, so only hand-written raw HTML is affected
  - **What the regression test does and does not prove**: it asserts the attribute is gone, not that clobbering fails. jsdom does not implement the named-property behaviour this defends against, so a clobbering reproduction would pass in the test suite while the condition stayed live in the shipping WebKit engine — a green test asserting nothing. Only a WKWebView probe could prove the defence, and this change does not build one
  - **Not closed, and it is the larger hole**: the Rust↔JS parity test compares the math, SVG and URI-scheme sets but **not** the base attribute set, which is why this drift was invisible to the test that exists to catch drift. The next base attribute to drift will be equally invisible. Closing it honestly means comparing against the union of ammonia's generic set and its per-tag grants, which is its own design task — deliberately deferred, not overlooked
- Upgraded DOMPurify from `^3.2.7` to `^3.3.2` (resolved to `3.3.3`), patching GHSA-h8r8-wccr-v5f2 and GHSA-v2wj-7wpq-c8vv — both Moderate XSS CVEs affecting the HTML paste-sanitization path in the WYSIWYG editor
- Link opening in the WYSIWYG editor now enforces a scheme **allow-list** rather than blocking three named prefixes (ADR-0001). A clicked link is handed to the system opener only when the URL it actually resolves to carries one of `http`, `https`, `mailto` or `tel`. Anything else is blocked and logged instead of opened. Two gaps closed: the scheme is now read after whitespace and control characters are removed, so a link whose displayed target and actual navigation target differ can no longer slip through; and the editor now opens exactly the value it validated instead of re-reading the element afterwards, which could change in between
  - **Behavior change**: links with other schemes stop working, including `file:`, `blob:`, `sms:` and Windows drive-letter paths such as `c:/Users/…`. If you need one of these, it must be added to the shared scheme list, not special-cased
  - `ftp` is a deliberate exception, and the one place the two scheme lists diverge: it remains in the shared Rust/JS **sanitizer** list, so `ftp://` links still render and export normally, but it is **not** handed to the system opener. The app's `opener:default` capability grants only `mailto:`, `tel:`, `http://` and `https://`, so an `ftp://` link was never actually openable — it previously failed silently at the IPC authorization layer, and now blocks visibly with a log entry
  - The browser-window fallback used when the system opener refused a link was removed. A link the OS declines to open now does nothing visible; the only record is one `editor.milkdown.link.open` entry in `~/.mdpro/mdpro.log`
- Closed a critical link-click bypass in the WYSIWYG editor (finding C1, ADR-0002). A link written in protocol-relative form (`//evil.com/x`) carries no scheme, so under the application's own `tauri://localhost` origin it resolved to `tauri://evil.com/x` — the app's own scheme wearing an attacker-chosen host. The previous check compared only the protocol, accepted the match, and handed that URL to the system opener. Protocol-relative links are now rejected outright, along with the backslash variants (`\\host`, `/\host`, `\/host`), and the application's own scheme is never treated as an external handoff
  - **Behavior change**: protocol-relative links no longer open, at any origin. Write an explicit `https://` scheme instead
  - **Behavior change**: links to the application's own origin — relative paths such as `./other.md` and `#fragment` anchors — are no longer sent to the system opener. They are now recognized as in-document navigation: the click is cancelled and recorded at `debug` level. In-document navigation is not implemented yet, so these links are currently **inert** rather than opening an external window. This replaces the previous behavior, in which a `#fragment` click sent the application-origin URL to the external opener

### Changed
- An MCP write (`write_document`, `insert_content`, the table tools) is now confirmed inside mdpro, in the window that has the document open, instead of by a native app-modal Yes / No alert ([ADR-0042](docs/adr/0042-mcp-write-confirmation-is-an-in-window-queued-prompt.md)). Previously the alert froze the whole app while it was up — no Settings, no switching the server off, no quit — and a write skipped it whenever *any* mdpro window was focused. Now a write applies without asking only when the window holding that document is focused; otherwise that window prompts (the Dock bounces if mdpro is in the background), prompts are shown one at a time per window in arrival order, and each waits at most 60 seconds
  - The HTTP result says what happened: rejected → `403 USER_REJECTED`; no answer within 60 s → `408 CONFIRM_TIMEOUT`; the prompt was withdrawn because the server was switched off, the app quit or the window closed → `503 CONFIRM_CANCELLED`; the document was closed while the prompt was up → `404 NOT_FOUND`. The `mdpro_mcp` tool descriptions tell the client not to retry automatically
  - An approved insert is applied to the document as it is *after* you answer, so text you typed while the prompt was up is kept (previously an insert was computed from the content before the prompt, and could overwrite that edit)
  - **Verified on a real device on 2026-09-30** (`docs/test/20260930-adr0042-wi10-gui-acceptance.md`), and ADR-0042 is now Accepted. The prompt appeared only in the owning window. With a prompt pending, Settings could turn MCP off (`503`), AppleScript `quit` quit the app instead of failing with `-128` (`503`), and closing the owning window returned `503`. Unanswered prompts returned `408` at 60 s, and two writes to one window queued in order. **Not verified on a device**: the table tools' prompt (they are HTTP-only, so an MCP client cannot reach them) and the Dock bounce. **The table tools' prompt has since been verified on a real device on 2026-10-02** (release build of `ef91e24`; `docs/test/20261002-dtrack-device-retest.md`): approve returned `202`, reject `403` with the document unchanged, and no answer `408` at 60 s. The Dock bounce is still not verified
  - **Fixed since**: Escape did not reject the prompt; only the Reject button did. This defect was older than this change and also affected the Unsaved-changes dialog; it is fixed and was verified on a real device on 2026-10-02; see Fixed (D34)
  - **Fixed since**: an `insert_content` into the active document in WYSIWYG mode reached the document but was not shown in the editor, and the next WYSIWYG edit overwrote it. This defect was older than this change; see Fixed (D35)
- The MCP server can now be turned off and on from Settings → Integrations, and the change takes effect immediately — no restart ([ADR-0040](docs/adr/0040-the-mcp-server-switch-takes-effect-live.md), which supersedes the launch-only design of [ADR-0039](docs/adr/0039-mcp-server-enablement-is-read-once-at-launch.md)). Turning it off stops the local HTTP server and removes its `server.port` / `server.token` files; turning it on starts it again with a fresh token. With `mcp.serverEnabled: false` in `~/.mdpro/config.json` the server is not started at launch, and the log records `mcp.http_server.start` with `outcome: skipped`. Before this the server started on every launch, and the Integrations toggle changed nothing
  - The old `mcp.enabled` key is retired and ignored. Every existing config holds `"enabled": false`, a default written at first run that no user chose, so honouring it would have silently switched MCP off on upgrade. A missing, corrupt or unreadable config still starts the server
  - The toggle saves first, then starts or stops the server. If the save fails, the server is left as it was and the toggle goes back. If the save succeeds but the port is taken, the setting stays on and the badge shows Failed to start; it is not rolled back
  - With a corrupt `config.json` the toggle refuses and leaves the file's bytes alone, so MCP cannot be switched from Settings until the file is fixed. At launch a missing, corrupt or unreadable config still starts the server
  - Settings → Integrations shows the real server state: Running, Off, Starting, Stopping or Failed to start. The "Takes effect after you restart mdpro" note is gone
  - Only the toggle writes `mcp.serverEnabled`. Saving other settings keeps the value on disk, so a stale Settings window can no longer switch MCP back
  - Turning MCP off interrupts requests in flight. A write aborted at the shutdown deadline may leave its caller unsure whether it landed; writes are never replayed automatically
  - Each toggle writes one `mcp.server.toggle` log group (start, then success or fail) carrying only the direction, phase, error kind and duration — never the token or a path
  - `mcp_get_status` reports `phase` (`disabled`, `starting`, `running`, `stopping`, `failed`) and `error` instead of `launch`. Anything reading the old field must switch
  - The `mdpro_mcp` sidecar follows the server across a restart: on a `401` or a refused connection it re-reads the port and token and retries a read request once. A write request is not re-sent; the call fails once and the next one uses the new port and token. **Sidecars built before this change keep the old token and must be relaunched by their MCP client**
  - The "Listening on localhost:…" server info is shown only while a port is bound, so an Off or failed server no longer shows a placeholder port
  - The toggle can now be changed from Settings → Integrations, since preference writes reach disk again (see *Fixed*). Until then it could not save its value, and editing `config.json` was the only way to change the setting
  - **Verified on a real device on 2026-10-02** (release build of `ef91e24`; `docs/test/20261002-dtrack-device-retest.md`): with a write prompt pending in one window, switching the server off from Settings in another window returned `503 CONFIRM_CANCELLED` and reached Off in 18 ms; switching it back on reached Running in 47 ms. The Stopping badge was not seen, because that state lasts too briefly to observe
- Settings no longer overwrites your MCP settings with defaults when it is opened before your preferences have loaded, or after they failed to load. The three MCP checkboxes stay disabled, with the reason shown, until the real values arrive. While a change is being saved the checkboxes are disabled ("Saving…"), so a second change cannot be undone by the first one failing
- Quit deadlines are measured on a monotonic clock, so a wall-clock change (NTP, a manual time change) can no longer fire a quit alert early or hold it back
- A rejected discard answer's error no longer echoes the offending document id. Discard ids are capped at 128 bytes each, and the number of ids per window now matches the 100-documents-per-window limit used elsewhere
- The large-document WYSIWYG guard now judges **source structure**, not file size ([ADR-0016](docs/adr/0016-large-document-guard-predicate-is-a-source-structure-score.md)). The old rule — degrade any document over 500 KB — was measured wrong on 2026-09-20: a 471,880 B table document blocked the main thread for **12.0 seconds** and was let through, while file size alone decided the outcome for everything above 500 KB regardless of what was in it. The new score is `newlines + (pipes - table-row-starts)` — roughly lines plus table cells — computed in one forward pass over the content with no Markdown parsing and constant extra memory; documents scoring above **25,000** switch to Source mode. Across the five perf-corpus fixtures the score sorts strictly with the measured block time (57,190 → 12,004 ms; 32,657 → 7,409 ms; 20,664 → 1,793 ms; 3 → 0 ms), and the threshold sits between the 1.8 s and 7.4 s cases
  - **Behaviour change**: a zero-table document is no longer safe by default — a 32,658-line prose file now degrades where it previously opened in WYSIWYG. Conversely a very large file with almost no line breaks was **allowed** into WYSIWYG where file size previously blocked it. That reversal was accepted at the time on the strength of a 471,862 B fixture measured at 0 ms — but the reasoning generalised from a fixture to a whole shape of document, and when a real 10 MB single-line file was finally measured it took **259 seconds** to mount. The longest-line trigger below closes it
  - The toast text changed from "Document exceeds 500KB. Switched to Source mode for performance." to "This document is too complex for WYSIWYG. Switched to Source mode for performance.", because the old copy named a threshold that no longer exists
  - **Known limits, accepted**: the threshold is fitted on five fixtures that are all ~472 KB, one measured run each, on one machine. Pipe counting errs in both directions — `|` inside a fenced code block counts as a cell (over-count), a table row written without outer pipes is under-counted. A degrade writes nothing to `~/.mdpro/mdpro.log`, so a false positive leaves no trace beyond the toast
  - `fileSize` was removed from the predicate's input type outright rather than left unused, so there is no longer a second, staleness-prone source of truth for the guard to disagree with
- The large-document WYSIWYG guard gained a second trigger: **longest line** ([ADR-0019](docs/adr/0019-large-document-guard-adds-a-longest-line-trigger.md), which extends ADR-0016 rather than replacing it). A document now degrades to Source mode when **either** its structure score exceeds 25,000 **or** its longest single line exceeds **1,000,000** UTF-16 code units. The same forward pass computes both — two more integers, no second scan, no parsing — so every constraint ADR-0016 froze still holds
  - **This fixes a measured defect, not a hypothetical one.** ADR-0016 explicitly accepted that a 9,961,475 B, 4-line document scored 3 and would be let into WYSIWYG. Measured on real hardware, that document takes **259,483 ms** to mount and leaves the UI unresponsive for over two minutes. The limitation was argued for in the abstract and turned out to be the worst case the guard had
  - **Behaviour change**: a file whose longest line exceeds one million characters now opens in Source mode instead of WYSIWYG, whatever its size or line count
  - The toast text is unchanged — "too complex for WYSIWYG" was already true of both triggers
  - **Known limits, accepted**: the new threshold is **not fitted**. The largest measured allow is 359,285 units (155 ms) and the smallest measured refuse is 7,583,742 units (259,483 ms); `1,000,000` is a round number chosen in the unmeasured order of magnitude between them. The guard is still blind to everything except line breaks and line length — a document of twelve 900,000-character lines passes both triggers while carrying 10.8 MB of inline content. `\r` counts as an ordinary character, so a CRLF file measures one unit longer per line than the same text in LF; correcting for it would need a lookback, and a lookback is the parsing rule ADR-0016 forbids
  - **Verified on a real device on 2026-10-02** in the stage 3.8 exit retest (release build of `ef91e24`, on battery; `docs/test/20261002-stage3-exit-perf-retest.md`), compared surface by surface against the 2026-09-15 baseline. The 472 KB table document that used to block for 55.8 s is now sent to Source mode in 21 ms. Every 9.96 MB document opened, switched and closed in both modes and returned to idle within 15 s; the baseline never settled. One 8–12 s input delay on the first switch to the 9.96 MB math document was seen once and did not recur; it was not sampled, so its cause is unknown
  - **Known defect, not fixed (D45)**: after every tab is closed, the web content process keeps about 1.75 GB of memory instead of dropping back toward the baseline's 0.98 GB. It may be WebKit holding on to freed memory rather than a leak: reopening documents reuses it rather than adding to it
- Source mode now turns its table editing tools off for a document with **more than 50,000 table rows** ([ADR-0022](docs/adr/0022-source-mode-gets-its-own-guard-keyed-on-table-row-density.md)). Such a document stays in Source mode and stays fully editable as plain text, but table detection, Tab-to-next-cell, cell highlighting, the column-count check, the table right-click menu and the table shortcuts are off for it. A one-time notice says so: "This document has too many table rows. Table editing tools are turned off for it." One `editor.large_document.source_tables_withheld` entry (`warn`) is written to `~/.mdpro/mdpro.log`. Documents with 50,000 table rows or fewer are unchanged, and so is WYSIWYG
  - **Why**: on a ~233k-row table document, every keystroke and cursor move in Source re-parsed the whole table into ~932k cell objects, retaining ~139 MB each time (defect D12). Turning the tools off limits that damage to documents under the threshold. It does not fix D12
  - The decision is made once per document per session, when the document is first shown in Source, not on every keystroke
  - **Known limits, accepted**: 50,000 is a policy choice, not a measured knee. The decision holds until the document is reopened, so deleting rows won't bring the tools back and adding rows past the threshold won't turn them off. One table parse still runs at mount before the decision lands. Lines inside fenced code blocks that start with `|` count as table rows. Checked by hand on a release bundle (MQ-1..MQ-4 pass; whether both toasts are visible when WYSIWYG drops into a withheld document could not be sampled)
- The `micromark-extension-gfm-table` override is pinned to the exact measured version `2.1.2` instead of the open range `>=2.1.2`. [ADR-0006](docs/adr/0006-bump-micromark-gfm-table-for-quadratic-edit-map.md) scoped its G0 exception to "this package and this reason" and required any further bump to carry its own justification, but an open range grants exactly that on the next lockfile regeneration. Resolution is unchanged (`2.1.2` before and after), so this is a guard against future silent drift, not a version change
- Encoding-safe save round-trip (Typora-parity Phase 0, WI-0.3): files opened as UTF-16LE/BE are now saved back in their original encoding (BOM preserved) instead of being silently rewritten as UTF-8. `save_file`/`save_file_dialog` accept the document's encoding; the open path detects encoding with a confidence level and refuses to guess (no blind Latin-1) for non-UTF-8 files with no BOM, surfacing an encoding error rather than corrupting content. CRLF line endings survive the round-trip
- ⌘/ now cycles view modes from any context, including when the CodeMirror source editor has focus. The line-comment shortcut moved from ⌘/ to ⌘⌥/ to free up the cycle binding (split via a `Prec.highest` keymap in `Editor.tsx`)
- Clicking an outline entry in WYSIWYG now jumps there instantly and lands the heading 40 px below the top of the editor, instead of smooth-scrolling it to the very top. This matches Source mode, and the highlight uses the same 40 px line in both modes, so the entry you clicked is the one that stays lit. The smooth scroll is gone because each of its intermediate frames lit whichever heading it was passing, and clicking one of the last headings left the wrong one highlighted ([ADR-0026](docs/adr/0026-wysiwyg-scroll-spy-is-geometric.md))

  - **Verified on a real device on 2026-10-02** (release build of `ef91e24`, 8 of 8 checks; D41 row of `docs/plans/20260912-frontend-backend-sequencing-order.md`), and ADR-0046 is now Accepted. - An external client editing a table through the MCP interface could destroy a heading instead. Source mode counted three shapes as tables that the GFM reference parser does not treat as tables at all: a single-column header over a `---` line (which is a setext heading underline — setext wins), a delimiter row indented 4 or more columns, and a delimiter **or** header row indented with a Tab (the indent check counted only spaces, so a Tab measured as no indent and escaped the rule entirely). Because those phantom tables were counted alongside the real ones, a client that counted correctly and asked to edit "table 0" reached a different table than the one it meant. Measured, not inferred: in a document whose first "table" was a two-line setext heading, `delete_row` on table 0 deleted the heading and left the real table untouched. The HTTP layer returns `202` before the frontend applies anything, so the call reported success either way — silent data loss. Source-mode detection now follows GFM on all three shapes.
